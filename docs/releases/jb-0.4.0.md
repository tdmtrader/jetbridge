# JetBridge 0.4.0

JetBridge 0.4.0 follows jb-0.3.1 (5133d0ddbc, 2026-09-04) with about 1,900 commits on `core`. It was declared 0.3.2 while in progress and released as 0.4.0 because it breaks upgrades: the database migrations collapse into a baseline, every fork migration is forward-only, legacy runs are deleted, the encryption key becomes required, about forty upstream web flags and their features are removed, and the chart's values schema closes. Read [Operator notes](#operator-notes) and the chart's [`MIGRATING.md`](../../deploy/chart/MIGRATING.md) before upgrading, and take a database backup with the encryption key: the only way back is restoring it.

## Highlights

- Landing queues: core lands changes on a repository's trunk once every gate, each a pipeline Run, has passed on the exact tree that lands (ADR-0011).
- Pipeline Runs v2: idempotent admission by invocation key, durable execution and results, build closures, queued and fenced cancellation, and the `run_pipeline` step.
- Step pod grants: only the web's configuration chooses the ServiceAccount a build's step pods run under, and the default step pod identity carries no API token.
- `fly abort-build` works again, and an aborted or timed-out task's pod is actually torn down instead of running on.
- Upstream surface removed: Let's Encrypt, `idtoken`, pipeline `var_sources`, the audit log, syslog drainer, OPA, non-OTLP tracers, `fly workers`/`fly volumes`, `prototypes:` and more (see [Upstream features removed](#upstream-features-removed)).
- Upgrade path: a database older than JetBridge 0.3.1 / Concourse 8.0.x is refused; upgrade it with 0.3.1 first.
- Chart 0.2.0: closed values schema; `web.env` and `web.extraArgs` replaced by typed values; image, URL, users and signing key required (see [Chart](#chart-011--020)).

## New

- **Landing queues.** A team can declare a landing queue that lands submitted changes on a repository's trunk once every gate it names has passed on a candidate (ADR-0011). Compose, each gate and land are pipeline Runs of templates the queue names; core keeps the queue's state in its own tables, never runs git and never persists a repository credential, and the trunk moves only by fast-forward. `fly set-landing-queue`, `fly land` and `fly landing-queue` drive it, with matching API routes and `go-concourse` calls; `deploy/` carries example compose and land templates (8d258d75d3, 8f770ef77b, 22eb1b7cf7).
- **Pipeline Runs v2.** Every run is admitted through `POST /api/v2/.../runs` with an invocation key (see Behaviour changes), execution and results are durable, an aborted build's leftover work is scoped to a build closure that holds the Run until it closes, and Run cancellation is queued and fenced. The new `run_pipeline` step starts a run from inside a build and renders in the web UI (33c50371d9, c2ce04a2d3, 2274c6a7fc).
- **Step pod grants.** `--kubernetes-step-pod-grant` (chart: `kubernetes.stepPodGrants`) maps a build's owner -- `<team>/<pipeline>/<job>`, or `main/one-off` -- to the ServiceAccount its step pods run under. Only the web's configuration selects a grant; nothing in a pipeline can. The default step pod identity mounts no ServiceAccount token, and a live pod whose identity no longer matches its build's grant is refused for reattach and hijack. A grant's `privileged: true` is recorded but not yet enforced (95a39d7e53, f737f5ae73).
- **Steering step pods to a node.** `--kubernetes-preferred-step-node key=value` (chart: `kubernetes.preferredStepNode`) adds a soft preference for that node to every step pod, and step pods tolerate the matching `NoSchedule` taint, so tainting the node reserves it for builds (a7d626b12e, 8f18bd9275).
- **Session cookies are Secure over https.** The web marks its cookies Secure whenever `--external-url` is `https://`; `--cookie-secure` is needed only behind a TLS-terminating proxy with an http URL (6830fd488b).
- **MCP and auth.** Renewable fly and browser sessions; resource-bound MCP OAuth with separate consent categories and revocation; precise `pipeline`, `build` and `job` MCP tools and a `capabilities_explain` tool. `fly set-pipeline --strict-config-write` makes a config write create-only or exact-version, failing with a typed 409 instead of overwriting (62afc93a6b, bef4f3ac8d).
- **Agent workloads.** `jb review` submits a change for a Codex review Run and reads its findings; `jb review land` pushes exactly the reviewed head with a lease on the reviewed base. The implement workload runs an edit-only session and hands back a validated patch to apply locally (5cd3eadc29, a2bbc308b9, a8afc90a88).
- **Artifact daemon.** `artifactDaemon.metrics.port` (`--metrics-port`) serves the daemon's `artifact_daemon_*` series on a plain-HTTP listener with its own ServiceMonitor and alerts; `--peer-discovery` turns on EndpointSlice peer discovery without node labelling (653e683aac, 9b2e074800).
- A build log page that resumes inside a large log event reads only its own window instead of re-reading and decoding the whole stored event (05f1fe9b83).

## Fixes

- `fly abort-build` works again. The engine's abort watcher checked once and never read the build's `aborted` flag up front (a regression from cdbc18fe95, which removed `conditionNotifier`), so an abort issued while no wake-up was pending — or while no web tracked the build — was silently lost and the build ran to a normal completion. The watcher now reads the flag before the plan starts and re-reads on every notification, through a query that does not rewrite the in-memory build (060ae44993, 4fdb63fa12).
- A supervised task step's pod is torn down when its step context ends. Task steps run under an in-pod supervisor that deliberately survives the exec stream, and the reaper only collects pods that recorded an exit status, so an aborted or timed-out task kept running — including privileged workloads such as a nested `dockerd`. The pod is now deleted with a zero grace period; get, put and check pods, and containers reached through `fly hijack`, are unaffected (2a9355e1e6).
- The Postgres notification listener now emits the disconnect notice the notifications bus reconnect path was written for, so a `NOTIFY` lost across a reconnect triggers a rescan instead of being unrecoverable (e8a9dff094).
- The Kubernetes reaper deletes a destroyed step's artifacts again. It was handed its own empty artifact locator instead of the workers', so it never found a step's artifacts to remove (only the daemon's TTL sweeper reclaimed them) and the web's in-memory locator grew until restart (b32773118a).
- `fly execute --output` extracts only inside the output directory. Entries whose names climb out with `..`, symlinks and hard links whose targets are absolute or leave the directory, and writes through such links were accepted before; extraction now goes through an `os.Root` on every host instead of shelling out to the system `tar` (83ee332452).
- With `artifactDaemon.tls.enabled`, artifact daemons can reach each other: peers are verified against the daemon service's DNS name rather than a pod IP the certificate cannot carry, and peer fetch uses https. Before, cross-node fallback, mirroring and preemption evacuation all failed verification (1edea75952).
- The web discovers only ready artifact daemons, so a terminating daemon is no longer picked for a probe, an alias or a `fly execute` input upload (214384a91d).
- A resource cache is mirrored before its alias is broadcast even when `artifactDaemon.hostPath` is written with a trailing slash or other unclean form (2f390debb2).
- A deprecated resource config scope no longer holds its config's global-scope slot. Two resources sharing a config that both moved to another config (or one resource moving back and forth) failed every later check with a duplicate key until the first deprecated scope was collected, and a global scope created on that config could adopt the deprecated row, which the collector then deleted along with its versions. Migration `1789793161` narrows the unique index to live global scopes.

## Behaviour changes

- A completed pipeline run no longer accepts new builds. Triggering a job inside a finished run (`fly trigger-job`, the web's + button, a webhook), or running `fly rerun-build` on one of its builds, used to reopen the run: its status went back to running, its completion time was cleared, and the run completed a second time under the same number with two sets of builds behind one status. All of those are now refused with a 409 reading `run #N is complete (<status>); run the template again`. A run is one execution of a template, so running the work again means creating a new run — its own number, its own parameters, its own outputs. Ordinary (non-run) pipelines are unaffected: their jobs keep building after they complete, as they always have.
- A task step that times out or is aborted no longer leaves its pod behind, so `fly hijack` into it afterwards is not possible; hijack a running step instead. This is what makes the runaway command actually stop.
- `POST /api/v1/teams/:team/pipelines/:pipeline/runs` is removed. Every pipeline run is now created through `POST /api/v2/teams/:team/pipelines/:pipeline/runs`, which takes an `invocation_key`: repeating a request with the same key and variables returns the run it already created (HTTP 200, `Idempotency-Replayed: true`, `admission_outcome: "replayed"`) instead of creating another. The v1 run list, detail, result and cancel routes are unchanged; runs created before the upgrade through the v1 route are deleted by the upgrade (see Operator notes). `fly run-pipeline` and the web UI use the v2 route; `fly run-pipeline` takes `--invocation-key` to make a retry safe and generates one otherwise.
- The `run_pipeline` step admits through the same v2 admission. Re-executing a step after a web restart re-attaches to the run it already created; while run admission is not activated the step fails with a message saying so.
- `fly execute --output` refuses an output that contains an absolute symlink, a link pointing outside the output, a device node or a FIFO; the download fails instead of writing it.
- An artifact daemon given only one or two of `--tls-cert`, `--tls-key` and `--tls-ca-cert` refuses to start instead of serving plaintext, and one with an unusable `--resolve-capability-key` refuses before it labels its node ready.
- Note on `timeout:` with `attempts:`: `timeout` is a task field and `attempts` wraps the task, so each attempt gets the full timeout and a timed-out attempt is retried. This is stock Concourse behaviour and unchanged.

### Upstream features removed

A web started with a removed flag fails to parse its command line and does not start; drop the flag from the deployment first.

- `--telemetry-opt-in` (the hidden anonymous version ping to telemetry.concourse-ci.org) is removed.
- `--enable-lets-encrypt` and `--lets-encrypt-acme-url` are removed with the autocert listener; TLS is served from `--tls-cert`/`--tls-key` only. Migration `1789793163` drops the `cert_cache` table.
- `GET /api/v1/teams/:team/cc.xml` (CCTray) and `fly checklist` (the Checkman Checkfile over it) are removed.
- `GET`/`PUT /api/v1/log-level` is removed; the web's level is `--log-level` at start.
- `GET /api/v1/teams/:team/pipelines/:pipeline/versions-db` (the scheduler debug export) is removed.
- `GET /api/v1/pipelines/:pipeline/jobs/:job/badge`, the redirect to the main team's badge, is removed; link the team-qualified badge.
- The `idtoken` credential manager is removed, with `/.well-known/openid-configuration`, `/.well-known/jwks.json`, the signing-key lifecycler and the `--oidc-issuer-url`, `--signing-key-rotation-period` and `--signing-key-grace-period` flags. Migration `1789793165` drops the `signing_keys` table.
- Pipeline `var_sources` and the `dummy` credential manager (and its `--dummy-creds-var` flags) are removed, with `--gc-var-source-recycle-period`. `set-pipeline` and `fly validate-pipeline` refuse a pipeline that still declares `var_sources:`; move those lookups into the cluster's Kubernetes credential manager, under the pipeline's team and pipeline. Migration `1789793165` drops `pipelines.var_sources` and `pipelines.nonce`.
- `fly workers` and `fly volumes` are removed, with `GET`/`POST /api/v1/workers`, `DELETE /api/v1/workers/:worker_name` and `GET /api/v1/teams/:team/volumes`. A namespace has one synthetic worker, registered by the web itself (`/api/v1/health` reports it as `"workers": "ok"`), and its volume records exist only as artifact bookkeeping, which tells an operator nothing. `fly containers` and the container routes behind `fly hijack` and `fly intercept` stay.
- The resource-version causality page is removed with its flag `--enable-resource-causality` (`CONCOURSE_ENABLE_RESOURCE_CAUSALITY`), the routes `GET .../resources/:resource/versions/:id/downstream` and `.../upstream`, and the `feature_flags` object on `GET /api/v1/info`; it was the last feature flag. A version's "inputs to" and "outputs of" lists on the resource page are unchanged. The web no longer serves `causality.mjs`, `graphviz.min.js` or `graphvizlib.wasm`.
- `--old-encryption-key` is removed from `web` and `migrate`, with database encryption-key rotation and the plaintext (no key) mode. `--encryption-key` is required: a web started without it does not start, naming the flag, and `concourse migrate --migrate-to-latest-version` needs the same key. A cluster that needs a different key restores the database from a backup taken under it, as for any forward-only migration (see Operator notes).
- `jb` no longer upgrades a submission receipt written as `review-invocation/v1`: submit refuses it naming the version and the remedy (delete it or pass a new `--receipt`).
- The API audit log (`--enable-*-auditing`, nine flags) is removed; no request is logged per category any more.
- The Lager metric emitter is removed with `--emit-to-logs`, and with `--metrics-host-name` and `--metrics-buffer-size`, which only it and the metric event buffer read. Prometheus is the only metric sink; every family, label and help text on `/metrics` is unchanged.
- The syslog drainer (`--syslog-hostname`, `--syslog-address`, `--syslog-transport`, `--syslog-ca-cert`) is removed with the `drained` build column (migration `1789793162`); build logs are reaped on the ordinary retention schedule and are not re-sent anywhere.
- The OPA policy check (`--opa-url`, `--opa-timeout`, `--opa-result-*`, `--policy-check-filter-*`) is removed; every request that paid for an always-passing check no longer does.
- `--concurrent-request-limit` is removed, with the `concourse_concurrent_requests` gauge and `concourse_concurrent_requests_limit_hit_total` counter it fed.
- `--streaming-artifacts-compression` is removed; gzip is the one stream codec (`zstd`, `s2` and `raw` go). Every deployment already ran gzip: the artifact daemon, `fly` artifact upload and download speak nothing else.
- `--tracing-jaeger-*`, `--tracing-honeycomb-*` and `--tracing-stackdriver-*` are removed; the only trace exporter is OTLP, on when `--tracing-otlp-address` is set (Jaeger speaks OTLP natively; Honeycomb's endpoint and headers are `--tracing-otlp-address` plus `--tracing-otlp-header`).
- `--enable-global-resources` is removed and global resources are unconditional: identical resource configs share one version history unless the base resource type asks for a unique one. `--enable-rerun-when-worker-disappears` is removed and that rerun is off.
- `prototypes:` and the `run:` step are removed. The step only ever printed "pretending to run"; a pipeline that still declares `prototypes:` is refused by name at `fly set-pipeline`, `fly validate-pipeline` and the API, and a plan with a `run:` step fails to parse ("no step configured"). The `CheckPrototype` route goes with them, and migration `1789793164` drops the `prototypes` table.
- A resource type's image is a registry-image reference and nothing else: a `resource_types` entry declares a direct `image:` or `type: registry-image` with a source, and a task's `image_resource` is `type: registry-image`. Anything else is refused at `fly set-pipeline`, `fly validate-pipeline`, the API and run materialization with a sentence naming the type. The check+get image fallback that fetched a type's image through another type is gone, so the only pod a check runs is the check itself; old builds' image-check and image-get events render as unknown steps instead of failing the build page's event batch.
- `fly check-resource --shallow` and `fly check-resource-type --shallow` are removed with the image check they skipped; the request body's `shallow` field goes with them.
- `--kubernetes-image-registry-prefix` and the chart value `kubernetes.imageRegistryPrefix` are removed; nothing read the prefix. `kubernetes.imageRegistrySecret` stays.
- `fly login` no longer detects a pre-3.14.1 server and falls back to the `/auth/methods` and `/auth/token` flow; every target speaks the sky issuer. The redirect server for `/login`, `/logout` and `/auth/:provider/callback` is removed; those paths now serve the web shell.
- The deprecated build-event versions (the 1.0 to 4.0 shapes of `input`, `output`, `log`, `error`, the task/get/put initialize, start and finish events) are no longer parsed. No database created by this fork holds one.
- The artifact daemon stores an artifact only as a directory: `PUT /artifacts/` answers 405 (bytes come in through `PUT /stream-in/`), `GET`/`HEAD` of a key that is a file is a 500 rather than a raw file, `/register` refuses a file-valued alias with `not_directory`, and the sweeper no longer removes flat files under `artifacts/`.
- A sidecar's logs are never folded into the step's stdout under a `[name] ` prefix; each declared sidecar streams to its own log writer under its own plan ID, and a step that has a stdout but no writer for a declared sidecar is refused naming the sidecar.
- The chart no longer tombstones a removed value: a stale key fails the render as an unknown property of its closed parent, and [`MIGRATING.md`](../../deploy/chart/MIGRATING.md) names each replacement.

### Chart (0.1.1 → 0.2.0)

Every item below fails `helm template` on a values file that still uses the old form, naming the key. [`MIGRATING.md`](../../deploy/chart/MIGRATING.md#values-migration) has the replacement for each.

- The values schema is closed and typed: an unknown or misspelled key fails the render instead of being ignored (f192c910ea).
- `web.env` is removed. Each setting a deployment passed through it has a typed value (`secrets.encryptionKeySecret`, `web.caCertFile`, `web.authDuration`, `web.checks.*`, `web.gc.*`, `web.secretRetry.*`); move every entry while the previous chart still renders, then upgrade. See [web.env becomes typed values](../../deploy/chart/MIGRATING.md#webenv-becomes-typed-values-2026-10-31) (46a6beac71, fc411ec1e3).
- `web.extraArgs` is removed; its flags are typed values (`kubernetes.podSchedulingTimeout`, `kubernetes.defaultTaskCPURequest`, `kubernetes.preferredStepNode`, `tracing.otlpAddress`, `tracing.serviceName`), and `--cookie-secure` follows an `https://` `web.externalUrl` (ef13fc0896).
- `image.repository`, `web.externalUrl`, `web.localUsers` and `web.mainTeamLocalUser` are required; the `concourse-local` image, `http://localhost:8080` and `test:test` defaults are gone (d393c91f55, 3c22ded95b).
- `secrets.signingKeySecret` is required and `secrets.create` is removed: the chart neither generates a session signing key nor renders the placeholder `<fullname>-keys` Secret. A release that ran with `create: true` resets its sessions once and keeps an orphaned `<fullname>-keys` Secret to delete by hand (853f613e8d, f2c6799f63, f60b7ae237).
- `rbac.brineLive` and `rbac.brineLiveServiceAccount` are removed; create the ServiceAccount yourself and map it with `kubernetes.stepPodGrants` before upgrading (05492cd7f6, d903576875).
- `artifactDaemon.durable`, `artifactDaemon.preemption`, `artifactDaemon.enabled`, `artifactDaemon.tls.enabled`, the eleven `artifactDaemon.hangar.*` input-plane values and `hangarOutput.cacheBucket` are removed: the daemon and its mTLS always render, and Hangar names its own store and bucket (84f8aa3946, c153761b9b).
- Hangar's activation Job, inventory and reclaimer Deployments and activation database role are gone; whether the output plane is in service is `hangarOutput.webEnabled` alone, and the web runs reclaim itself (e3f2b5d723).
- `otelMetrics` is removed with the OTel metric instruments; `metrics.enabled` (Prometheus) is the metrics path and `tracing.*` still exports traces.

## CI and build

- `build-image` builds the runtime base (`jetbridge-base:jammy-<hash>`) once per change to its Dockerfile instead of running apt on every build (8ecbf14430).
- The `k8s-e2e` pipeline (container-based K8s tier) tracks `core` again; every `dockerd` it starts inside a pod runs with `--mtu=1450`, and its apt steps retry (7275310445, a8d66711b0, d4ddf1d3b6).
- `build-and-vet` compiles the `-tags live` suites so API drift in them is caught immediately (06d3c556b1).
- The `cmd/concourse` Web Command suite gives the web thirty seconds to exit in `AfterEach` (f0bb15c6df).
- The `docker compose` development stack (the root `docker-compose.yml`, `Dockerfile`, `hack/dc`, `hack/db`, `hack/overrides/`, `hack/trace`), the compose-driven `integration/` suite and the checked-in `hack/keys` are gone: a JetBridge web needs a Kubernetes cluster to run a step, so the stack never exercised the runtime. Build the image with `./build.sh` and install the chart. `make test-integration` goes with the suite; `atc/integration` (an in-process ATC over `postgresrunner`) runs under `make test-unit` and in CI.
- Counterfeiter is out of the module: unit tests run real collaborators, and a hand-written double in the spec file stands in only where the real object will not do.

## Operator notes

- Run admission is available to authorized callers of runnable templates. New results, inputs and credential delivery require Hangar in service; finalization and invocation replay survive a drain. C7 removes the Run epoch, contract-class and causation fields and terminal result version. Upgrade the server and bundled clients together; migration `1789793159` refuses retained invocations until the operator follows [the evidence-discard procedure](../../deploy/chart/MIGRATING.md#c7-run-contract-simplification). Result reads use fixed concurrency 2 and a 1Gi disk scratch volume; reclamation remains bounded to 20 Runs and preserves build history.
- Hangar has no control-key generation (ADR-0010). The node daemon is trusted over mTLS from the web only, so an acknowledgement is its answer on that channel, not a signed statement: the node control key, its key ring, the `--activation-epoch`, `--control-key-id` and `--control-key-file` daemon flags, the `--kubernetes-hangar-output-activation-epoch` and `--kubernetes-hangar-output-control-keys` web flags and the chart values `hangarOutput.activationEpoch`, `hangarOutput.executionControl.keySecret`, `.keyID`, `.publicKeys` and `hangarBootstrap.referencedKeys` are removed (`hangarOutput.executionControl.enabled` stays the execution-control switch). A prior run's result binds as a Run input while its Run is succeeded and its claim is live, and nothing is stranded or made unreadable by a key change. The daemon mounts the output plane with `--execution-control`, verifying every warrant with the one Hangar key.
- One Hangar key (`hangar.key`) signs every warrant -- read, execution control and output capture -- under one encoding whose first field is the purpose, and a route admits only its own purpose. The daemon flags `--capability-key`, `--capability-ttl`, `--materialization-key-file`, `--materialization-key-id` and `--hangar-warrant-ttl` and the web flags `--kubernetes-hangar-output-warrant-key` and `--kubernetes-hangar-output-materialization-key` are removed; `--hangar-warrant-key` and `--kubernetes-hangar-warrant-key` become `--hangar-key` and `--kubernetes-hangar-key`; the daemon mounts its output plane with `--execution-control`; and the chart values `hangarOutput.capabilityKeySecret`, `.materializationKeySecret` and `.materializationKeyID` are removed (`artifactDaemon.hangar.keySecret` is the one source). The run-input signing key stays web-only: a node holding it could forge cross-team input grants.
- **Legacy runs are deleted on upgrade.** Migration 1789793147 drops every `legacy_v1` pipeline run with its payload pipeline, retained definition, builds and build events (and any composition call left with no iteration). v2 runs are untouched. C13 makes all fork migrations after upstream `1765921815` forward-only. Recover the previous schema and deleted runs by restoring the matching pre-upgrade database backup, image and encryption key; see the [restore procedure](../migration/DATABASE-MIGRATION-RUNBOOK.md#rollback-procedure).
- During the rollout that applies migration `1789793161`, a web still running the previous image fails to create a new global resource config scope (a new resource type's config) because its upsert no longer matches the unique index; the check succeeds on retry once every web runs the new image.
- **A database older than Concourse 8.0.x is refused.** The 300 upstream migrations up to `1765921815` are one baseline, `1765921815_baseline.up.sql`, that builds the 8.0.x schema on an empty database only; migrating an empty database through it and through the files it replaced gives byte-identical `pg_dump --schema-only` output. A JetBridge 0.3.1 or Concourse 8.0.x database is past it and upgrades as before. One below it (`migrations_history` below `1765921815`, or tracked in `schema_migrations` or `migration_version`) is refused before anything changes, with a message naming JetBridge 0.3.1: upgrade it with JetBridge 0.3.1 (or Concourse 8.0.x) first. `migrate-preflight.sh` fails such a database the same way.
- Migrations are forward-only by omission: no migration has a down file, and asked to go below the database's version the migrator refuses (`migration <version> is forward-only: restore the pre-upgrade database backup instead`) before reversing anything or recording a failure. `concourse migrate` loses `--current-db-version`, `--supported-db-version` and `--migrate-db-to-version`; `--migrate-to-latest-version` stays (`--old-encryption-key` goes with key rotation, below). Read the version from `migrations_history` (the runbook's schema version check).
- **The encryption key is required and never rotates.** Every row in an encrypted column is ciphertext under the one `--encryption-key`, and the key has to be present at upgrade: the web does not start and `migrate-db` does not run without it. The first keyed migration run encrypts any plaintext row a keyless deployment left behind itself; nothing has to be run on the previous release first. The chart names the key through `secrets.encryptionKeySecret` (a Secret holding `encryption-key`), rendered on the web container and on `migrate-db`, and is the only way the chart passes the key: the `CONCOURSE_ENCRYPTION_KEY` entry in `web.env` went with `web.env` (see Chart below). Back the Secret up with the database: a lost key is a lost database. See [the chart migration note](../../deploy/chart/MIGRATING.md#the-encryption-key-is-required-2026-10-30).
- The web's Kubernetes clientset is built once per start and carries 15 QPS, burst 30: the combined budget of the three clientsets it used to build at client-go's default.
- `--kubernetes-artifact-daemon-namespace` tells the web where the artifact daemon runs; the chart sets it to the release namespace. Empty keeps the old behaviour (the daemon beside the step pods).

- The CI node needs `fs.inotify.max_user_instances` above Ubuntu's default 128 (home-infra pins 1024); at 128 the kubelet fails every follow-logs stream, which drops sidecar logs and breaks testcontainers' readiness waits.
