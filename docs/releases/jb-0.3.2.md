# JetBridge 0.3.2 (in progress)

Running notes for the next release; rewritten into full notes at cut time.

## Fixes

- `fly abort-build` works again. The engine's abort watcher checked once and never read the build's `aborted` flag up front (a regression from cdbc18fe95, which removed `conditionNotifier`), so an abort issued while no wake-up was pending — or while no web tracked the build — was silently lost and the build ran to a normal completion. The watcher now reads the flag before the plan starts and re-reads on every notification, through a query that does not rewrite the in-memory build (060ae44993, 4fdb63fa12).
- A supervised task step's pod is torn down when its step context ends. Task steps run under an in-pod supervisor that deliberately survives the exec stream, and the reaper only collects pods that recorded an exit status, so an aborted or timed-out task kept running — including privileged workloads such as a nested `dockerd`. The pod is now deleted with a zero grace period; get, put and check pods, and containers reached through `fly hijack`, are unaffected (2a9355e1e6).
- The Postgres notification listener now emits the disconnect notice the notifications bus reconnect path was written for, so a `NOTIFY` lost across a reconnect triggers a rescan instead of being unrecoverable (e8a9dff094).
- The Kubernetes reaper deletes a destroyed step's artifacts again. It was handed its own empty artifact locator instead of the workers', so it never found a step's artifacts to remove (only the daemon's TTL sweeper reclaimed them) and the web's in-memory locator grew until restart (b32773118a).
- `fly execute --output` extracts only inside the output directory. Entries whose names climb out with `..`, symlinks and hard links whose targets are absolute or leave the directory, and writes through such links were accepted before; extraction now goes through an `os.Root` on every host instead of shelling out to the system `tar` (83ee332452).
- With `artifactDaemon.tls.enabled`, artifact daemons can reach each other: peers are verified against the daemon service's DNS name rather than a pod IP the certificate cannot carry, and peer fetch uses https. Before, cross-node fallback, mirroring and preemption evacuation all failed verification (1edea75952).
- The web discovers only ready artifact daemons, so a terminating daemon is no longer picked for a probe, an alias or a `fly execute` input upload (214384a91d).
- A resource cache is mirrored before its alias is broadcast even when `artifactDaemon.hostPath` is written with a trailing slash or other unclean form (2f390debb2).

## Behaviour changes

- A completed pipeline run no longer accepts new builds. Triggering a job inside a finished run (`fly trigger-job`, the web's + button, a webhook), or running `fly rerun-build` on one of its builds, used to reopen the run: its status went back to running, its completion time was cleared, and the run completed a second time under the same number with two sets of builds behind one status. All of those are now refused with a 409 reading `run #N is complete (<status>); run the template again`. A run is one execution of a template, so running the work again means creating a new run — its own number, its own parameters, its own outputs. Ordinary (non-run) pipelines are unaffected: their jobs keep building after they complete, as they always have.
- A task step that times out or is aborted no longer leaves its pod behind, so `fly hijack` into it afterwards is not possible; hijack a running step instead. This is what makes the runaway command actually stop.
- `POST /api/v1/teams/:team/pipelines/:pipeline/runs` is removed. Every pipeline run is now created through `POST /api/v2/teams/:team/pipelines/:pipeline/runs`, which takes an `invocation_key`: repeating a request with the same key and variables returns the run it already created (HTTP 200, `Idempotency-Replayed: true`, `admission_outcome: "replayed"`) instead of creating another. The v1 run list, detail, result and cancel routes are unchanged; runs created before the upgrade through the v1 route are deleted by the upgrade (see Operator notes). `fly run-pipeline` and the web UI use the v2 route; `fly run-pipeline` takes `--invocation-key` to make a retry safe and generates one otherwise. A v2 create may also carry `correlation` and `caused_by_run` (an earlier run of the same team).
- The `run_pipeline` step admits through the same v2 admission. Re-executing a step after a web restart re-attaches to the run it already created; while run admission is not activated the step fails with a message saying so.
- `fly execute --output` refuses an output that contains an absolute symlink, a link pointing outside the output, a device node or a FIFO; the download fails instead of writing it.
- An artifact daemon given only one or two of `--tls-cert`, `--tls-key` and `--tls-ca-cert` refuses to start instead of serving plaintext, and one with an unusable `--resolve-capability-key` refuses before it labels its node ready.
- Note on `timeout:` with `attempts:`: `timeout` is a task field and `attempts` wraps the task, so each attempt gets the full timeout and a timed-out attempt is retried. This is stock Concourse behaviour and unchanged.

## CI and build

- `build-image` builds the runtime base (`jetbridge-base:jammy-<hash>`) once per change to its Dockerfile instead of running apt on every build (8ecbf14430).
- The `k8s-e2e` pipeline (container-based K8s tier) tracks `core` again; every `dockerd` it starts inside a pod runs with `--mtu=1450`, and its apt steps retry (7275310445, a8d66711b0, d4ddf1d3b6).
- `build-and-vet` compiles the `-tags live` suites so API drift in them is caught immediately (06d3c556b1).
- The `cmd/concourse` Web Command suite gives the web thirty seconds to exit in `AfterEach` (f0bb15c6df).

## Operator notes

- The Run contract has its own activation, turned on at every deploy. `web.pipelineRunActivationEpoch` (default `1`) renders `--pipeline-run-activation-epoch`, which replaces `--enable-pipeline-run-creation` and `web.enablePipelineRunCreation` (both removed; a values file that still sets `web.enablePipelineRunCreation` now fails the render rather than being ignored). At startup each web node writes the epoch into the run activation marker; `0` stops admission on the next web start and keeps the recorded epoch. The marker only moves forward: a web node configured below the recorded epoch refuses to start, so raise the value rather than lower it. The Run epoch is independent of `hangarOutput.activationEpoch`. A template that declares results (or a run given inputs) is admitted only while the node's Hangar output epoch has its base and output facets enabled, and is refused with 409 "not activated" otherwise. Admission checks nothing more, but executing any run, with or without results, needs the Hangar output plane's execution control (`hangarOutput.executionControl`) with the node's output capability key configured and its Hangar output epoch enabled by the activation Job: every step of a run build starts through the exact-execution check. On a deploy missing any of these, runs of templates without results are admitted and every step then fails with "Run result execution is not activated". Set `web.pipelineRunActivationEpoch: 0` on such a deploy to keep admission closed.
- A Hangar output epoch rotation no longer strands runs. A running run still finalizes and its invocation key still replays after the epoch it was admitted under is disabled; captures, credential deliveries and bound inputs carry their own Hangar epoch. Accepted and deferred: outputs published under a since-disabled Hangar epoch may become unreadable, and a prior-run input may be refused across a rotation.
- **Legacy runs are deleted on upgrade.** Migration 1789793147 drops every `legacy_v1` pipeline run with its payload pipeline, retained definition, builds and build events (and any composition call left with no iteration). v2 runs are untouched. Its down migration restores the schema only; the deleted runs are not restored.
- The web's Kubernetes clientset is built once per start and carries 15 QPS, burst 30: the combined budget of the three clientsets it used to build at client-go's default.
- `--kubernetes-artifact-daemon-namespace` tells the web where the artifact daemon runs; the chart sets it to the release namespace. Empty keeps the old behaviour (the daemon beside the step pods).

- The CI node needs `fs.inotify.max_user_instances` above Ubuntu's default 128 (home-infra pins 1024); at 128 the kubelet fails every follow-logs stream, which drops sidecar logs and breaks testcontainers' readiness waits.
