# JetBridge 0.4.6 (running notes)

JetBridge 0.4.6 follows jb-0.4.5 (e610ff1acb). These are running notes, kept as changes land; they become the release notes when 0.4.6 is declared.

## Changes

### Step runtime

- **The reaper collects step Jobs under either step runtime, and one pod it cannot delete no longer stops a pass.** A deployment switched from `job` back to `exec` keeps the step Jobs left behind, and their pods reach the reaper's destroying path. Deleting their Jobs was forbidden under `exec`, and the reaper returned at the first pod it could not delete. Every pass then stopped there, so no other destroyed container was reaped and no artifacts were dropped. Now a pod that cannot be deleted is logged and left for the next pass. The rest of the pass goes on, and the pass ends in an error. Under `exec`, a Role that cannot list or delete step Jobs (a chart older than the web) is reported once per process at info (`step-jobs-not-collected`), not as an error on every pass. Under `exec` this also stops the `failed-to-list-step-jobs` error 0.4.5 logged every 10 s. Under `job` a refusal stays an error. A refused pause pod delete is an error under either runtime.
- **The reaper deletes a step pod's Job only if it is still the Job the pod's owner reference names** (a UID precondition). A Job recreated under the same name is left alone. The same holds for the step Job an aborted or failed step deletes.
- **The managed-input init waits out a busy or restarting artifact daemon.** It retried a 503 or no answer five times, two seconds apart. Two Runs' inputs queued on one node, or a daemon restart, outlasted that, and the step failed before its command ran. It now retries with capped, jittered backoff for 10 minutes. Any other status still fails at once, with the same message. A node whose artifact daemon is gone for good now fails a managed-input step after about 10 minutes rather than 10 seconds.
- **Admitting an exact execution dials a restarting artifact daemon again.** A refused, reset or closed connection, no route, or no answer within the client's timeout is retried with backoff for 2 minutes under the step's context. Any HTTP answer, and any TLS or certificate failure, is still final. A repeated admission is the same admission: the node's ledger already holds it.
- **The capture control init waits about 3 minutes for the daemon, not 1,** so it outlasts a restart the admission waits through.
- **A transient API failure while checking a step envelope's token is retried.** Under `job`, a TokenReview or pod read that failed for want of an answer was a 401, which the launcher treats as final, so the step's pod exited without running its command. It is now a 503, which the launcher retries. A refused token, or a pod that is gone, is still a 401.
- **The launcher records a command it could not start.** A missing or non-executable command exits 127 or 126 as before, and now also leaves its one-line termination record, saying the command did not run. So does a command it could not set up, exit 125: its stdin could not be staged from the envelope, or its stdout file could not be opened (with or without an envelope). A failure before that (bad usage, the token, the envelope fetch: 125) still leaves none.
- **The web reaches a node's artifact daemon by its pod IP.** Alias registration, mirror triggers, artifact reads and uploads, capture classification, the job runtime's answer read and the reaper's step-directory delete dialled the node's InternalIP and hostPort. Where the web could not route to that address, registration timed out and a web-side read such as `load_var` failed with `artifact not found on node X or any peer`. They now dial the ready address the daemon Service's EndpointSlices publish for that node, and fall back to the InternalIP when there is none or the EndpointSlice list fails. The output plane (exact-execution control and the capture seal, publish, release and stat routes) still dials the node InternalIP, so a cluster that blocks it cannot yet run with `hangarOutput.executionControl.enabled`.
- **A task that times out or is aborted after its command started records the outputs it had written.** Its `on_failure` and `ensure` hooks, and a later step when the task is under `try`, can now read them, as in upstream Concourse; before, the fetch found nothing. The outputs are whatever the command left, not a consistent snapshot, and under `job` the pod may still be writing through its termination grace. A task aborted before its command was started in the pod records nothing: under `exec`, before the kubelet accepted the command's exec; under `job`, before the main container started. A get or put that is aborted or times out records nothing either. A command that exits as its step is cancelled now records its outputs too. Recording adds at most about 10 seconds to an abort or timeout (about 20 under `job` when the API server stalls).

### Hangar

- **A managed read's timeout starts once it holds the artifact daemon's scratch slot.** Materializations and archive reads share one slot with input publication and seals. A read queued behind another spent its timeout in the queue and answered 503. Now the wait is bounded by the caller's own request, and a caller that gives up while queued holds nothing and spends no warrant.

### Privilege mode

- **A new privilege mode, `--kubernetes-step-privilege`, decides which step pods may run privileged. Its default, `any`, changes nothing.** Under `any` a privileged container is admitted as before, whatever step pod grants declare. Under `granted` the web refuses a privileged container outside a grant that declares `privileged=true` when it creates the Pod or Job, naming the owner and the missing grant. Builds that can hold no grant (instanced pipelines, other teams' one-offs, Runs, builds not found) and privileged checks outside a resource-type grant (below) fail closed; a failed build lookup fails the step. Opt in: run `hack/step-pod-audit pods`, add the grants it shows, then set `granted` (see `deploy/chart/MIGRATING.md`). A pod reused, or a step resumed after a web restart, is admitted again (below). Web logs `step-privilege-mode` at startup.
- **Under `granted`, a step pod or step Job a step comes back to passes the gate again.** A live pause pod reused by a repeated check, a step a restarted web reattaches to, and a running step Job a restarted web resumes were admitted only when they were made, so one made under `any`, or under a grant since removed, kept running privileged steps. Now each passes the privilege rule again, with the owner resolved as at creation (checks through their resource-type grant). Re-admission judges privilege only: a capability or host path a mutating webhook added to the stored pod, or a host path moved across a restart, deletes nothing. A pod it refuses is deleted (a step Job by its UID), and the step fails naming the owner and the grant it lacks, or saying the pod holds privilege its step no longer asks for. No fresh pod replaces it, because its command may have begun. A resumed step Job's envelope is served only once it has passed, so a pod still waiting for its envelope starts nothing while the web decides. A Run's exact execution is refused but not deleted. A resumed exact step Job gets no envelope: its launcher is answered 503 and, after its 10-minute envelope timeout, exits without running the command, unless a later web resumes the step and admits it. A step that finished before the web came back keeps its result, read with no admission. Under `any` nothing is re-admitted and nothing more is looked up. A pod no step comes back to runs until its build ends, and `fly intercept` into it is still allowed: after switching, delete the privileged pods `hack/step-pod-audit pods` lists beyond a grant.
- **No step pod may add a Linux capability or join a host namespace, in either mode and under every grant.** No step the runtime builds asks for either, so nothing that runs today changes.
- **Under `granted`, a step pod grant can cover a privileged resource type's checks.** Its owner is `<team>/<pipeline>/resource-type/<type>` (a lowercase identifier), and it sets `privileged=true` and no ServiceAccount. Each check pod has exactly one owner: the type its plan runs, which the engine now sets on the container spec. A check of a resource runs that resource's type. The check of a resource type, and the fetch of its image, run that type's own type, so a type built on a privileged type needs the privileged type's grant. A task's `image_resource` check runs the image resource's type. In a job build, a task image of a privileged custom type needs both: the job's grant for its image get and the resource-type grant for its image check. A grant binds the pipeline's name, as a job grant does. Only a privileged check is looked up. The pod keeps the default step pod identity and is annotated `concourse.dev/step-pod-grant`, which `hack/step-pod-audit pods` holds it to. A check of a base type, of an instanced or Run pipeline, or in a one-off build stays refused, and the refusal says why. Under `any` nothing changes.

### Resources

- **A custom resource type's new image no longer empties the version history of resources using it.** A resource on a pipeline-declared type is keyed on the type's image, so a new image version gave it a new, empty history: versions vanished from the UI, pinned and disabled versions stopped resolving, and `passed` constraints on earlier builds had nothing to match. When the resource is next checked or put against the new image, its old history is now copied into the new one in the same transaction, merged in order: a version only the old history holds goes directly above the newest version both hold that preceded it, otherwise below everything. The merge needs PostgreSQL 11 or later (the chart ships 16). Once lidar resolves a type, its image is keyed on the repository and digest alone, so the history carries whenever the digest changes within the same repository, whatever moved it: a new image pushed to the tag, an edit of the type's `tag` or `params` that resolves to another digest, or an older digest selected. An edit that resolves to the same digest changes nothing. It does not carry to an image in another repository, or between tags of a direct `image:` reference pinned by tag alone, and a resource whose own source or type name changed still starts a new history. A type whose image is instead fetched by a check and get (one whose `repository` holds a `((var))`, for example) carries only when the image version changed and the type's own source and params did not. Both histories are the resource's own team's (see "A version history belongs to one team" below), so a carry writes into no other team's history. A `version: every` job does not go back for a version merged in below one it has already used. After a carry, the old history is deprecated once no active resource or resource type of the team still uses it; it is then kept for the deprecated-scope grace period (default 30 days) and is listed by `fly copy-resource-versions` run without `--from-scope`.
- **`fly copy-resource-versions` merges by the same rule.** When the source and target share versions, copied versions newer than a shared one land above it, and may become the latest and trigger jobs. With nothing shared, they go below the target's own as before.
- **`fly copy-resource-versions` no longer writes into a version history other resources share, unless it is the same history.** A resource on a base type with a unique version history copies into its own history as before, from any of its deprecated scopes. A resource whose current history is shared with other resources of its own team can copy only a history of the same resource config, or of the same custom type on another image digest in the same repository (for a type fetched by check and get, another image version with the same type source and params); anything else is refused with `409 Conflict` and the reason, and nothing is copied. The current history is always the resource's own team's, so a copy writes into no other team's history. On 0.4.5 a resource that moved from a unique-history type to a shared one could copy its old history, found under another config, into the history the other resources read.
- **A version history belongs to one team.** On 0.4.5 and earlier, identical resources and resource types (the same type, source and type image) shared one version history across every team, so one team's checks, puts, `fly clear-versions` and version metadata reached another team's resources, and a resource's last check could be another team's build. Now each team has its own history of a resource config, shared only by that team's identical resources and resource types, in any of its pipelines. A version one team's check finds or put saves appears for another team only once that team's own check finds it. `fly clear-versions` clears only the caller's team's history, and the resources and types it lists as sharing the history are that team's. A task `image_resource` check, `fly execute`'s image check and a type-image fetch in a build read and write the history of the build's team, so a team's first such check of a config resolves afresh. The store refuses a resource pointing at another team's history. Resource caches (fetched content, keyed by config, version and params) stay cluster-wide (ADR-0012).
- **Upgrading copies each shared history once per team.** Migration 1789793171 gives every team that used a history shared with another team its own copy: the same versions, check order and metadata, so pins, disabled versions and `passed` constraints resolve as before. The team with the lowest id keeps the original; a last check build stays only on its own team's copy. A resource that pointed at a deprecated history of another team is detached, and starts a fresh history at its next check. A shared history that no resource or resource type uses is dropped, and the next check that needs it starts it again. From then on each team checks a shared config on its own, so checks of such a config multiply by the teams sharing it (those checks take turns on the config's checking lock).
- **Upgrade a multi-team deployment with the web stopped.** Set `web.strategy: {type: Recreate}` for the upgrade, or scale `web.replicas` to 0 first. A single-team deployment copies nothing and may roll as usual. Why:
  - The migration first waits until it can take the resources, resource config scopes and teams tables together, retrying rather than deadlocking against an outgoing web's transaction; a lock held on one of them for the whole upgrade (a `pg_dump`, for example) makes it give up cleanly after its retries, with nothing changed. From then until it commits, an outgoing web's reads of histories (resource listings, checks, puts) and any write that references a resource (the scheduler's next build inputs, saving a build's inputs and outputs, in-memory check bookkeeping, set-pipeline) block.
  - Its cost grows with the versions in shared histories times the extra teams sharing them. As a rough guide, copying 400k versions took about 20 seconds on a local SSD with fsync off (about 20k versions a second, the version index included); expect it to be several times slower on real storage. Each copied version adds about 1 KB to the versions table.
  - Once it commits, an outgoing 0.4.5 web still finds histories by config alone. Its resource checks and puts fail closed: the store refuses attaching a resource to another team's history, a put rolls back, and a history cannot be created. Its resource-type check builds, task `image_resource` checks, native resolves of resource types and type-image fetches attach no resource, so they write versions and last-check fields into whichever team's copy that lookup returns. What persists is only what a check of the identical config returns, plus a last-check link to another team's build until that team's next check. Its resource-type listing can show a type once per team sharing the config.
  - There is no rollback to 0.4.5 without restoring the database: a 0.4.5 web against the migrated schema cannot create a history.
- **A version id reaches only the resource's own history.** Getting, pinning, enabling or disabling a resource version, listing the builds it was an input to or an output of, and paging the version list take a version's row id. Each now resolves the id only within the history of the resource named in the URL, so an id from another history, of the same team or another, is a version the resource does not have: `404` for get, pin, enable and disable, and an empty list for the builds it was an input to or output of and for a page of the version list that starts or ends at it, as for an id that does not exist. Before, one team could read another team's version and metadata, pin to it and disable by it. Pinning, enabling or disabling an id that does not exist now answers `404` rather than `500`.

### `fly execute`

- **`fly execute -o` downloads its outputs.** It was broken in every released JetBridge, 0.4.5 included, under both step runtimes and with the output plane on or off. The task ran and exited 0, then the web panicked in the artifact output step (`nil pointer dereference`, `artifact_output_step.go`), and the build ended `errored` with nothing downloaded. A task output on JetBridge is a step volume that the artifact daemon holds by its artifact key, and it had no volume row for the download to find. Now the artifact output step gives the output an artifact volume row whose handle is that key, and the download streams from the node's artifact daemon. Nothing is copied. A download still needs the step directory, so it races the reaper's deletion of the finished one-off's step directory, just as a later step's read does. `fly execute` without `-o` is unchanged.

## Chart

- **`kubernetes.stepPrivilege` (`any | granted`, default `any`) sets the privilege mode.** Only `granted` renders a flag, so an `any` render is byte-identical to 0.4.5's. The value budget rises by one (`maxValues` 177), an exception recorded in the ADR-0008 amendment of 2026-11-09.

- **The pod-manager Role grants `batch/jobs` `list` and `delete` under `exec` too,** so the reaper can collect step Jobs a `job` deployment left behind. `get`, `watch`, `create`, `update` and `patch` stay `job`-only. No new value.
