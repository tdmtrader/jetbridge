# JetBridge 0.4.7 (running notes)

JetBridge 0.4.7 follows jb-0.4.6 (ae366b2cf8). These are running notes, kept as changes land; they become the release notes when 0.4.7 is declared.

## Changes

### Step runtime

- **A task's `run.user` is honoured.** `root` or a decimal uid (0 to 2147483647, leading zeros accepted) becomes the main container's `runAsUser`, under both step runtimes and on a Run's exact executions. Before, it was ignored and the task ran as its image's user. A task with `user: root` on an image whose USER is non-root now runs as uid 0. A task that sets no `run.user` runs as its image's user, as before.
- **Breaking: a task that set a numeric non-root `run.user` now runs as that uid.** On hostPath storage (the artifact daemon) its working directory, outputs and caches are root-owned, so it cannot write them, and a task that was green may fail with `permission denied`. Drop `run.user`, or set it to `root`.
- **A user name, or `user:group`, is not resolved.** The task runs as its image's user, and the step's stderr and the web log (`warning-ignored-task-user`) say that `run.user` was ignored.
- **A signed or out-of-range uid fails the step before a pod or Job is made.** The error names the user and the range Kubernetes accepts.
- **A uid is not privilege.** The privilege mode judges the same things as before, whatever the uid: a task that runs as root keeps the unprivileged security policy, and a privileged task stays privileged. `fly intercept` into a step runs as the step's uid.
- **The launcher records an envelope it never received.** A launcher sent for a step envelope that exits without one leaves its termination record marked `envelope_never_received`: the fetch gave up after `--envelope-timeout` or was refused (125), the token or CA file could not be read (125), or the pod's termination signal arrived before the envelope did (while the token was read, during the fetch, or between attempts). On that signal the launcher used to end without a record. It now ends the wait, and the launcher exits 143 (128 plus the signal) with the record and runs nothing. A step's exit code is unchanged. In 0.4.6 these exits left no record. The record is also meant to close a Run's start that an earlier web recorded but never delivered, as stopped rather than unresolved, for example the start of a resumed exact step Job that re-admission refused. That part is not reachable in 0.4.7: a Run's exact executions still run on the `exec` step runtime, and running them as step Jobs is test-only. Once they run as step Jobs, the start is closed when the Run's recovery reads the pod's record.
- **On the `job` step runtime a step's log is complete once main has ended.** A task's output, and a resource command's stderr, is main's container log, followed while the command runs. A follow that opened and then delivered nothing or only part of the log, or that was cut five seconds after main ended, used to count as streamed, and the rest of the log was dropped without a word. Now one plain read of the finished log follows every step and appends what lies beyond the bytes the follow delivered, so the log is completed from the finished log while the kubelet has not rotated it (`containerLogMaxSize`, 10Mi by default). Past that, a follow that was cut loses the end of the output and says so on the step's stderr, and a follow that never opened shows only the current log file. A read that fails is said on the step's stderr and never fails the step. The extra request re-reads the whole current log file, once per step, bounded at a minute. Sidecar logs are unchanged. Not live-verified.

- **A task's params reach its pod from a Secret of the step's own, never as literal values.** Every param of a task step, whatever credential manager or var resolved it, goes in `step-env-<handle>`, an immutable Secret in the step namespace, and the main container reads each through a `secretKeyRef`; before, each was a literal `env[].value` in the Pod and, under the `job` step runtime, in the step Job's template too. The step's own env (`BUILD_*`, `ATC_EXTERNAL_URL`) stays literal, a param still overrides a variable of the same name, and a value reaches the command as written (no `$(VAR)` expansion or `$$` collapse) and an empty one as set-and-empty. The Secret is owned by the pause pod (`exec`) or the step Job (`job`) and goes with it; the reaper deletes the one a web left unowned by dying in between, never one whose handle has a step Job. A reaper pass with any candidate costs one step Jobs LIST and one Secret DELETE per candidate: each departing task container (destroying, or missing for over a minute) whose pod last said it reads a Secret or was not seen by this web in the last 30 minutes (after a restart, every one), on every pass while it departs. A web clears a container's missing mark before it makes the Secret; a pass already under way can still delete a Secret made in the same instant, and the step then fails with `CreateContainerConfigError` (ADR-0013, accepted race). Check, get and put steps, and a task with no params, make none. See ADR-0013. Exercised live under both step runtimes; the reaper's collection and the accepted race are not live-verified.
- **A step whose params Secret cannot be made fails, and says why.** A Role without the Secrets rule fails each task step that has params with `cannot create the step's params Secret ... the web's Role lacks "secrets: create, patch, delete"`; param values totalling more than the 1 MiB of values one Secret holds (`corev1.MaxSecretSize`; keys are not counted) fail it before anything is made. A pod younger than 30 seconds whose main container waits with `CreateContainerConfigError` for its own params Secret (not found yet, or the kubelet's secret cache not synced) is waited on, and judged again when the 30 seconds run out. A param is never written as a literal instead. Web still starts. The Role refusal was seen live; the size limit and the 30-second wait are not live-verified.
- **Upgrade: apply the chart's Role with or before the new image.** The pod-manager Role gains `secrets: create, patch, delete` (no `get`, `list` or `watch`), in every permutation and with no new value. A web on this image under an older Role fails every task step that has params until the Role is applied. Not live-verified.
- **The Secrets rule reaches every Secret in the step namespace.** It cannot be narrowed by name, so web may patch or delete any Secret there, and a patch returns the Secret it patched. With `kubernetes.namespace` unset that is the release namespace, which holds web's own Secrets; set a separate `kubernetes.namespace` for the narrower grant. Not live-verified.
- **The pod-manager Role follows `kubernetes.namespace`.** With step pods in a namespace of their own, the chart rendered web's pod-manager Role and binding in the release namespace, so web could create no step pod where it was told to. The Role is now rendered in the step namespace, and what web reads in the release namespace (the artifact daemon's EndpointSlices, and its own pod under `job`) gets a Role there. Nothing changes when the two namespaces are the same. Not live-verified.
- **An exec's trace span records the command's path only.** `exec.command` carried the whole command when it had five elements or fewer, which for a task is the supervisor script with `run.path` and `run.args` in it, so a credential in `run.args` was exported to the tracing backend. Not live-verified.
- **Known limit: `run.path` and `run.args` are still in the step Job.** Under the `job` step runtime the task's command and arguments stay in the Job's pod template and its pod, where admission control sees them; on `exec` they are not stored but are in the exec request's URL. `run.dir`, the image reference and sidecar definitions are in the pod spec, and a resource's printed version and metadata are a pod annotation. A credential belongs in `params`. Not live-verified.

### Resources

- **A version history nothing uses any more is kept for 30 days.** A resource is keyed on its type and evaluated source, so an edited source, a rotated credential or a destroyed pipeline left its history unused, and it was deleted about an hour after its last check (at once for a resource that is only put to, or after an archived pipeline was set again). A shared history is now kept for the deprecated-scope grace period (`--deprecated-scope-grace-period`, default 30 days) after its last check or after its last resource left it: a check or put that moves a resource to another source, or a pipeline save that detaches it, counts as leaving. A destroyed pipeline's resources do not leave, they are deleted, so its shared histories are kept 30 days after their last check; for a resource that is only put to, that may already have passed. A unique-version-history scope goes with its resource, so it goes with a destroyed pipeline; otherwise it is deprecated at its resource's next check after a source change and kept 30 days as before, and one whose resource is detached and not checked again within the hour is lost, as in 0.4.6. A history with no versions keeps the old hour. A resource of the same team that returns to the same type and source finds the history as it left it, with the same version ids, at its next check, or at its next put for a resource that is only put to. Until then its version list is empty and its builds show no inputs of it, because a build's inputs are read through the resource's current history; its pin and its disabled versions belong to the resource, not the history, and hold throughout. A kept history of a custom type keeps that type's image cached for the same time. Exercised live for the `mock` type: a source edited and reverted, a put-only resource, and an archive and set again, each past the old deletion (see Verification). Not live-verified: deletion at the end of the grace, a destroyed pipeline's histories, custom types, and a history left by 0.4.6.
- **`fly copy-resource-versions` restores a history a resource used before a source change.** Run without `--from-scope` it now also lists the shared histories the resource left, with their version counts and last check (a kept history shows `kept` where a deprecated one shows when it was deprecated), and calls them previous version histories. With `--from-scope` it copies one into the resource's current history when no other active resource uses that history and no active resource type of the team is on its config, merged by the 0.4.6 rule. The copied versions are new rows with new ids; a copied version the current history does not rank against goes beneath the versions it already holds. The source history stays listed after a copy, and copying it again copies nothing. Pins, disabled versions, build inputs and `passed` constraints on the copied versions resolve again. When the resource's current history is shared with other active resources or resource types of the team, the copy still refuses with `409 Conflict`, for the resource the source history is listed for; another resource sharing that history gets `404 Not Found`, as the source is not listed for it. A resource that attaches to the same history later reads the copied versions. Both histories are the resource's own team's, checked inside the copy. `404 Not Found` is one answer for four cases: a listed history collected before the copy, a history listed for a different resource, another team's history, and an id that names no history. The listing's JSON gains `versions` and `last_checked`; `deprecated_at` is empty for a kept history. Exercised live for the `mock` type: a rotated var's history listed and copied back, the `409` and the `404`s (see Verification). Not live-verified: a source collected before the copy, and custom types.
- **Known limits.** Not live-verified.
  - A history is listed for the resource that left it last. Any later leave of the same history by a teammate, even one that comes back to it, takes the listing from the earlier resource, and the history may then be listed for no one.
  - If a pipeline save detaches a resource at the instant another transaction is moving, copying or recording a check on that history, it is kept but not listed.
  - A history listed as `kept` may still be in use by teammates; the copy refuses if one is active on the resource's current history, not on the source.
  - The copy's only-user check does not see a task `image_resource` check on the destination's config, a resource type attaching to it while the copy runs, or a teammate a save detached that attaches again at its next check. Those read the copied versions.
  - When the leaving transaction finds the old config's row held by another (a put or a get looking it up), it stamps the config's clock right after it commits, waiting up to 10 seconds for that holder, so a pipeline save, a check or a put that leaves a history can take up to 10 seconds longer to return. If the holder still has the row then, the stamp is skipped and logged (`failed-to-stamp-left-resource-configs`), as is any other failure of it, and the save, check or put still succeeds; a history whose last check is older than the grace can then be collected at the next pass. So can one a collector pass starts on in the instant between that commit and that stamp.
  - A resource removed from its pipeline keeps its row, and with it its history, indefinitely, and that history is never listed. This was so before 0.4.7.
  - A source that changes on every check (dynamic credentials, say) leaves one history per change: one config, one scope and its versions per distinct source per resource, each kept 30 days instead of about an hour. A resource checked every minute whose source changes every check keeps about 43,000 of them. Lower `--deprecated-scope-grace-period` to bound that; it also shortens how long deprecated scopes are kept.
  - A history left before the upgrade is found if its resource returns to the same type and source, but is not listed.

### Changed behaviour

- **A step whose type's image was fetched through a type other than `registry-image` fails with the cause, instead of pulling the type's name.** Such a get produces a rootfs artifact, which a step pod cannot run: a type chain such as `level-a` of `type: level-b`, where `level-b` is itself a custom type, or a custom type declared on a base type such as `type: docker-image`. The pod was built with the custom type's name as its image and failed as `ErrImagePull` on `docker.io/library/<type>:latest`. That pod is no longer made; the step errors with `resource type "level-a" has no registry image: its image was produced by resource type "level-b"`, and says to declare the type with `type: registry-image` or a direct `image:`, or to map it with `--kubernetes-base-resource-type level-a=<image>` (chart `kubernetes.baseResourceTypes`). A mapping for the type's name still wins, as before. The type's own check and get still run first, each time (for a scheduled check, every interval); only the final step's pod is not made. This covers every check, get and put of such a type, scheduled or manual. A task `image_resource` of such a type fails with `task image_resource of type "<type>" yields no registry image` and is never mapped (before, it pulled `image:latest`). A task whose `image:` artifact has no registry reference now says so, instead of `empty image for resource type "(unknown)"`. Nothing else changes for type names: a resource whose type is undeclared and unmapped is still pulled by that name, as before. Such a chain has never run on JetBridge: it pulled the type's name from March 2026 until 0.4.0 refused it at `set-pipeline`, and again from 0.4.1, which allowed it once more. Not live-verified.

## Verification

Exercised live means run on the concourse.home deployment, or on the k8s-behavioral tier, which installs the chart on K3s in CI.

**Exercised live:**

- Kept version histories and copying them back, on the deployment on 2026-11-20 (core 8bd8594045 when it began), through `fly` only, all on resources of the built-in `mock` type in scratch pipelines whose job `b` takes the resource `passed` job `a`. A self-upgrade restarted the web once during the wait; the histories were listed before and after it.
  - A source edited, then reverted 82.5 minutes later, past the old deletion at about 65 minutes. Until the resource's next check its version list was empty and its builds showed no inputs, and the pin held. After one check it had the same 4 versions with the same ids, its pin with its comment, its disabled version, and job `b`'s next inputs resolving the pinned version through `passed`; a build of `b` then ran on it.
  - A source rotated by a pipeline var. After one check on the new source the old history was listed as `kept` with 4 versions; `--from-scope` copied the 4 beneath the new version, as new rows with new ids. The pin, the disabled version, the old builds' inputs and the `passed` constraint resolved again. The source stayed listed, and copying it a second time reported 0 versions copied.
  - Two resources of the team rotated to the same new source, so the destination was shared. The copy for the resource the old history was listed for (the last to leave it) answered `409 Conflict`; the copy for the other one answered `404 Not Found`, because the history is not listed for it.
  - A resource that is only put to (`check_every: never`). Its 3 versions survived 82.5 minutes on another source, and returned with their ids at the next put on the original source, with no check.
  - A pipeline archived for 82 minutes 49 seconds, then set again. After the first check the resource had the same version ids, its pin and its disabled version.
  - Two teams on one type and source. The second team's resource saw only its own versions, listed no previous history, and got `404 Not Found` for the first team's history; the first team's history came back unchanged when its resource returned. The second team was driven by the main team's admin with `--team`; two users of separate teams were not exercised.
  - A resource that never left a history lists none, and a scope id that names no history answers `404 Not Found`.
- The step params Secret, on the deployment (core 394eaa1a0b, `job` step runtime).
  - `k8s-live-tests` build 873 passed both tests in `live_step_env_secret_test.go`, one on each step runtime, in the `concourse` namespace: the command saw `$(HOME)`, `$$` and an empty value as written, the stored Pod and Job held no value, and the Secret was immutable, owned by the pause pod (`exec`) or the step Job (`job`), and collected with it.
  - A one-off build through web on 2026-11-25 (`fly execute`, build 1257106, a task with two literal params, in the release namespace): the task printed `s3cr$(HOME)$$et||set`; the stored Pod and Job held no value and `main` read both params through a `secretKeyRef` to `step-env-<handle>`; the Secret was immutable and owned by the step Job; the Job and the Secret were gone within 5 seconds of the build ending. A param resolved by a var or a credential manager was not exercised.
  - The refusal under a Role without the Secrets rule: the deployment ran this image under its old Role for a day, because its chart sync was stuck, and `k8s-live-tests` build 872 errored in one second with `the web's Role lacks "secrets: create, patch, delete"`. Adding the rule to the Role fixed it with no web restart.
- A type's image fetched through a non-registry-image type refused rather than pulled by name: k8s-behavioral spec 6.2 asserts the refusal on `fly check-resource` and passed in builds 248 and 249.

**Not live-verified** (covered by unit and integration specs only):

- `run.user`: `root` and numeric uids reaching the main container under both step runtimes; a name or `user:group` keeping the image's user, with the line on the step's stderr and the web log; a signed or out-of-range uid refused before a pod or Job exists; the privilege policy unchanged by the uid. Nothing here has run on a cluster yet: not a Run's exact execution, not the permission failure of a non-root uid on hostPath storage, and not `fly intercept` as the step's uid.
- The launcher's never-received record: its exits (the envelope timeout, a refused fetch, an unreadable token or CA file, the termination signal before the envelope) are covered by the launcher's unit tests only. Not run in a pod: the launcher's signal handling as PID 1, and the record being writable by a launcher running as a non-root uid (`run.user`). The live-tier test that closes an undelivered exact job start (`live_job_runtime_test.go`) has not run on a cluster.
- The step params Secret, beyond what is exercised live above: its keys, ordering and replacement, the size limit, the reaper's collection and the chart's Role rules are covered by `atc/worker/jetbridge`, `atc/db` and `deploy/chart/tests` specs and the brine CF-05 scenarios only. Not run anywhere: a web killed between the Secret and its pod, a pod waited on for its Secret, and a deployment with `kubernetes.namespace` set.
- Kept version histories and copying them back, beyond what is exercised live above: deletion at the end of the 30-day grace, and a scratch deployment with a short `--deprecated-scope-grace-period`; an upgrade from 0.4.6 with a history inside its 65-minute window; histories of custom resource types, and the type image kept cached with them; a destroyed pipeline's histories; a source collected mid-copy (`404`); the after-commit stamp's 10-second bound and its timeout, and a save that skips a scope another transaction holds. These are covered by `atc/db`, `atc/gc`, `atc/api` and `fly/integration` specs only. The collector's cost at scale has not been measured.
