# JetBridge 0.4.7 (running notes)

JetBridge 0.4.7 follows jb-0.4.6 (ae366b2cf8). These are running notes, kept as changes land; they become the release notes when 0.4.7 is declared.

## Changes

### Step runtime

- **A task's `run.user` is honoured.** `root` or a decimal uid (0 to 2147483647, leading zeros accepted) becomes the main container's `runAsUser`, under both step runtimes and on a Run's exact executions. Before, it was ignored and the task ran as its image's user. A task with `user: root` on an image whose USER is non-root now runs as uid 0. A task that sets no `run.user` runs as its image's user, as before.
- **Breaking: a task that set a numeric non-root `run.user` now runs as that uid.** On hostPath storage (the artifact daemon) its working directory, outputs and caches are root-owned, so it cannot write them, and a task that was green may fail with `permission denied`. Drop `run.user`, or set it to `root`.
- **A user name, or `user:group`, is not resolved.** The task runs as its image's user, and the step's stderr and the web log (`warning-ignored-task-user`) say that `run.user` was ignored.
- **A signed or out-of-range uid fails the step before a pod or Job is made.** The error names the user and the range Kubernetes accepts.
- **A uid is not privilege.** The privilege mode judges the same things as before, whatever the uid: a task that runs as root keeps the unprivileged security policy, and a privileged task stays privileged. `fly intercept` into a step runs as the step's uid.
- **The launcher records an envelope it never received.** A launcher sent for a step envelope that exits without one leaves its termination record marked `envelope_never_received`: the fetch gave up after `--envelope-timeout` or was refused (125), the token or CA file could not be read (125), or the pod's termination signal arrived before the envelope did (while the token was read, during the fetch, or between attempts). On that signal the launcher used to end without a record. It now ends the wait, and the launcher exits 143 (128 plus the signal) with the record and runs nothing. A step's exit code is unchanged. In 0.4.6 these exits left no record. The record is also meant to close a Run's start that an earlier web recorded but never delivered, as stopped rather than unresolved, for example the start of a resumed exact step Job that re-admission refused. That part is not reachable in 0.4.7: a Run's exact executions still run on the `exec` step runtime, and running them as step Jobs is test-only. Once they run as step Jobs, the start is closed when the Run's recovery reads the pod's record.
- **On the `job` step runtime a step's log is complete once main has ended.** A task's output, and a resource command's stderr, is main's container log, followed while the command runs. A follow that opened and then delivered nothing or only part of the log, or that was cut five seconds after main ended, used to count as streamed, and the rest of the log was dropped without a word. Now one plain read of the finished log follows every step and appends what lies beyond the bytes the follow delivered, so the log is completed from the finished log while the kubelet has not rotated it (`containerLogMaxSize`, 10Mi by default). Past that, a follow that was cut loses the end of the output and says so on the step's stderr, and a follow that never opened shows only the current log file. A read that fails is said on the step's stderr and never fails the step. The extra request re-reads the whole current log file, once per step, bounded at a minute. Sidecar logs are unchanged. Not live-verified.

### Resources

- **A version history nothing uses any more is kept for 30 days.** A resource is keyed on its type and evaluated source, so an edited source, a rotated credential or a destroyed pipeline left its history unused, and it was deleted about an hour after its last check (at once for a resource that is only put to, or after an archived pipeline was set again). A shared history is now kept for the deprecated-scope grace period (`--deprecated-scope-grace-period`, default 30 days) after its last check or after its last resource left it: a check or put that moves a resource to another source, or a pipeline save that detaches it, counts as leaving. A destroyed pipeline's resources do not leave, they are deleted, so its shared histories are kept 30 days after their last check; for a resource that is only put to, that may already have passed. A unique-version-history scope goes with its resource, so it goes with a destroyed pipeline; otherwise it is deprecated at its resource's next check after a source change and kept 30 days as before, and one whose resource is detached and not checked again within the hour is lost, as in 0.4.6. A history with no versions keeps the old hour. A resource of the same team that returns to the same type and source finds the history as it left it. A kept history of a custom type keeps that type's image cached for the same time. Not live-verified.
- **`fly copy-resource-versions` restores a history a resource used before a source change.** Run without `--from-scope` it now also lists the shared histories the resource left, with their version counts and last check (a kept history shows `kept` where a deprecated one shows when it was deprecated), and calls them previous version histories. With `--from-scope` it copies one into the resource's current history when no other active resource uses that history and no active resource type of the team is on its config, merged by the 0.4.6 rule. Pins, disabled versions and `passed` constraints on the copied versions resolve again. A history other active resources or resource types share still refuses with `409 Conflict`. A resource that attaches to the same history later reads the copied versions. Both histories are the resource's own team's, checked inside the copy. A listed history collected before the copy answers `404 Not Found`. The listing's JSON gains `versions` and `last_checked`; `deprecated_at` is empty for a kept history. Not live-verified.
- **Known limits.** Not live-verified.
  - A history is listed for the resource that left it last. Any later leave of the same history by a teammate, even one that comes back to it, takes the listing from the earlier resource, and the history may then be listed for no one.
  - If a pipeline save detaches a resource at the instant another transaction is moving, copying or recording a check on that history, it is kept but not listed.
  - A history listed as `kept` may still be in use by teammates; the copy refuses if one is active on the resource's current history, not on the source.
  - The copy's only-user check does not see a task `image_resource` check on the destination's config, a resource type attaching to it while the copy runs, or a teammate a save detached that attaches again at its next check. Those read the copied versions.
  - When the leaving transaction finds the old config's row held by another (a put or a get looking it up), it stamps the config's clock right after it commits, waiting up to 10 seconds for that holder, so a pipeline save, a check or a put that leaves a history can take up to 10 seconds longer to return. If the holder still has the row then, the stamp is skipped and logged (`failed-to-stamp-left-resource-configs`), as is any other failure of it, and the save, check or put still succeeds; a history whose last check is older than the grace can then be collected at the next pass. So can one a collector pass starts on in the instant between that commit and that stamp.
  - A resource removed from its pipeline keeps its row, and with it its history, indefinitely, and that history is never listed. This was so before 0.4.7.
  - A source that changes on every check (dynamic credentials, say) leaves one history per change: one config, one scope and its versions per distinct source per resource, each kept 30 days instead of about an hour. A resource checked every minute whose source changes every check keeps about 43,000 of them. Lower `--deprecated-scope-grace-period` to bound that; it also shortens how long deprecated scopes are kept.
  - A history left before the upgrade is found if its resource returns to the same type and source, but is not listed.

### Changed behaviour

- **A step whose type's image was fetched through a type other than `registry-image` fails with the cause, instead of pulling the type's name.** Such a get produces a rootfs artifact, which a step pod cannot run: a type chain such as `level-a` of `type: level-b`, where `level-b` is itself a custom type, or a custom type declared on a base type such as `type: docker-image`. The pod was built with the custom type's name as its image and failed as `ErrImagePull` on `docker.io/library/<type>:latest`. That pod is no longer made; the step errors with `resource type "level-a" has no registry image: its image was produced by resource type "level-b"`, and says to declare the type with `type: registry-image` or a direct `image:`, or to map it with `--kubernetes-base-resource-type level-a=<image>` (chart `kubernetes.baseResourceTypes`). A mapping for the type's name still wins, as before. The type's own check and get still run first, each time (for a scheduled check, every interval); only the final step's pod is not made. This covers every check, get and put of such a type, scheduled or manual. A task `image_resource` of such a type fails with `task image_resource of type "<type>" yields no registry image` and is never mapped (before, it pulled `image:latest`). A task whose `image:` artifact has no registry reference now says so, instead of `empty image for resource type "(unknown)"`. Nothing else changes for type names: a resource whose type is undeclared and unmapped is still pulled by that name, as before. Such a chain has never run on JetBridge: it pulled the type's name from March 2026 until 0.4.0 refused it at `set-pipeline`, and again from 0.4.1, which allowed it once more. Not live-verified.

## Verification

**Not live-verified** (covered by unit and integration specs only):

- `run.user`: `root` and numeric uids reaching the main container under both step runtimes; a name or `user:group` keeping the image's user, with the line on the step's stderr and the web log; a signed or out-of-range uid refused before a pod or Job exists; the privilege policy unchanged by the uid. Nothing here has run on a cluster yet: not a Run's exact execution, not the permission failure of a non-root uid on hostPath storage, and not `fly intercept` as the step's uid.
- The launcher's never-received record: its exits (the envelope timeout, a refused fetch, an unreadable token or CA file, the termination signal before the envelope) are covered by the launcher's unit tests only. Not run in a pod: the launcher's signal handling as PID 1, and the record being writable by a launcher running as a non-root uid (`run.user`). The live-tier test that closes an undelivered exact job start (`live_job_runtime_test.go`) has not run on a cluster.
- A type's image fetched through a non-registry-image type refused rather than pulled by name: `atc/imageresolver`, `atc/engine` and `atc/worker/jetbridge` specs only. The k8s-behavioral spec 6.2 now asserts the refusal on `fly check-resource`, but has not run in CI yet.
- Kept version histories and copying them back: the config collector's two graces, the leave stamps at a check, a put and a pipeline save (including an archived pipeline set again, and a save that skips a scope another transaction holds), the listing, the sole-user copy and its refusals, a source collected mid-copy (404) and two-team isolation are covered by `atc/db`, `atc/gc`, `atc/api` and `fly/integration` specs only. None of the live proofs has run: a source edited and reverted past 65 minutes, a rotated credential copied back, a second pipeline's resource refusing the copy, a put-only resource, an archive and un-archive, two teams on one config, a scratch deployment with a short `--deprecated-scope-grace-period`, and an upgrade from 0.4.6 inside the 65-minute window.
