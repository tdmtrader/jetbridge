# Review-loop prior art and native alternatives

Generated 2026-08-06 by a fan-out of four web-enabled research agents and five
independent design agents, followed by one synthesis pass, in response to the
question: should JetBridge keep binding its review loop to a forge pull request,
or model the review object natively?

Input context: `docs/superpowers/plans/2026-08-05-pr-interface-cleanup-audit.md`
and `docs/superpowers/plans/2026-08-05-repository-snapshot-duplication-audit.md`.

The five designs were written independently and are NOT mutually consistent;
several of their risk sections assert live-cutover hazards that do not exist
(see the synthesis section for the verification).

# RESEARCH

## Durable/event-driven systems: self-trigger suppression and exactly-once handling over at-least-once transports — and what that implies for binding a review loop to a forge PR API

# 1. There is no single "recognise events I caused" mechanism. There are five, and they live in different places.

Ordered by where the check sits. JetBridge's current design uses none of them.

**(a) Provenance stamped in the transport, checked at the receiver — actor id.**
MySQL replication is the cleanest instance: every binlog event carries `server_id`, and by default the replica's receiver thread does not write to the relay log events bearing its own server id. `--replicate-same-server-id=1` is the explicit opt-out, and the manual warns that combining it with `log-replica-updates` in a circular topology "can cause infinite loops in replication"; GTIDs are the stronger form (skip transactions already applied, regardless of origin). https://dev.mysql.com/doc/refman/8.4/en/replication-options-replica.html
Yjs is the same idea in a CRDT: `Y.applyUpdate(doc, update, origin)` stamps `transaction.origin`, and a provider ignores updates whose origin is itself; `transaction.local` and the local `clientID` are alternates. https://docs.yjs.dev/api/y.doc and https://discuss.yjs.dev/t/determining-whether-a-transaction-is-local/361
BGP's AS_PATH self-AS rejection (RFC 4271 §9.1.2) belongs to this family — I could not extract the verbatim paragraph through fetch, so treat it as a pointer, not a citation.

**(b) Provenance enforced by the *producer* — and GitHub already does this, just not for you.**
Verbatim: "When you use the repository's `GITHUB_TOKEN` to perform tasks, events triggered by the `GITHUB_TOKEN` will not create a new workflow run" … "This behavior prevents you from accidentally creating recursive workflow runs." Exceptions: `workflow_dispatch`/`repository_dispatch` always run; `pull_request` opened/synchronize/reopened create runs in an **approval-required** state; labeled/edited/closed do not run at all. The documented workaround for people who *want* the loop is to use a GitHub App token or PAT instead. https://docs.github.com/en/actions/concepts/security/github_token
This is the single most important finding for the "is the shape right" question: **GitHub itself concluded that identity-scoped echo suppression was necessary and implemented it server-side — but only for its own first-party actor.** Any third party writing back via App/PAT is explicitly outside that protection and must reimplement it at the receiver.

**(c) Actor filtering at the receiver — what bots actually do.**
Probot debated making this the default (issue #63): filter on `payload.sender.login != '<app>[bot]'` or `payload.sender.type != 'Bot'`. Notably it was **never made the default** — "own" is ambiguous because an App acting on behalf of a user reports the user as `sender`. https://github.com/probot/probot/issues/63 and https://probot.github.io/docs/webhooks/
Renovate applies the same filter to *content* rather than events. Actual source of `isBranchModified` (lib/util/git/index.ts): it runs `git log` from `origin/<baseBranch>` to `origin/<branchName>` collecting `%ae` and `%ce`, builds `includedAuthors`, deletes `gitAuthorEmail`, then deletes everything in `config.ignoredAuthors` and `platformIgnoredAuthors`; `if (includedAuthors.size === 0)` → "authors all match - branch has not been modified" → returns false and caches. https://github.com/renovatebot/renovate/blob/main/lib/util/git/index.ts
Note it checks **both author and committer email** — a detail that matters, because a rebase/cherry-pick by another actor preserves your author identity.

**(d) A marker smuggled into the artifact, when the transport carries no usable identity.**
This is what everyone does when they cannot trust `sender`. RFC 3834 is the canonical spec: "Automatic responses SHOULD NOT be issued in response to any message which contains an Auto-Submitted header field … where that field has any value other than 'no'" (§2), plus per-sender rate limiting ("SHOULD NOT issue the same response to the same sender more than once within a period of several days… A 7-day period is RECOMMENDED as a default"), plus the null-return-path rule. https://www.rfc-editor.org/rfc/rfc3834
Dependabot is RFC 3834 written into a commit message: it "will stop rebasing a pull request once extra commits have been pushed to it", and the escape hatch is the literal markers `[dependabot skip]`, `[skip dependabot]`, `[dependabot-skip]`, `[skip-dependabot]` in the commit message. It also stops rebasing after 30 days. https://docs.github.com/en/code-security/dependabot/working-with-dependabot/managing-pull-requests-for-dependency-updates
Renovate does the same with base64 JSON in an HTML comment (`getRenovateDebugPayload` → `JSON.parse(fromBase64(...))`, carrying `createdInVer`/`updatedInVer`). Note the cost is visible in the source: `logger.warn('Unable to read and parse debugData...')`. https://github.com/renovatebot/renovate/blob/main/lib/modules/platform/pr-body.ts

**(e) Content fingerprint that deliberately excludes the fields you write.**
Renovate's `getPrBodyStruct` hashes the PR body only *after* stripping its own debug block (`result = result.replace(prDebugDataRe, '')`) and the Reviewable section. Its own markers are structurally excluded from the equality test that decides whether to rewrite. Same file as above.
Kubernetes does this as a first-class API contract, and this is the strongest transferable idea in the whole survey:
- `metadata.generation`: "a sequence number representing a specific generation of the desired state. Set by the system and monotonically increasing, per-resource." https://github.com/kubernetes/community/blob/master/contributors/devel/sig-architecture/api-conventions.md
- The `status` subresource: PUT/POST/PATCH to `/status` ignores everything but status; requests to the main resource ignore status changes; **`metadata.generation` is incremented only on spec changes, never on status writes.** https://kubernetes.io/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/
- `observedGeneration`: "if `.metadata.generation` is currently 12, but the `.status.conditions[x].observedGeneration` is 9, the condition is out of date with respect to the current state of the instance."
- controller-runtime's `GenerationChangedPredicate` doc comment, verbatim: "This predicate will skip update events that have no change in the object's metadata.generation field… This allows a controller to ignore update events where the spec is unchanged, and only the metadata and/or status fields are changed." Implementation is one line: `return e.ObjectNew.GetGeneration() != e.ObjectOld.GetGeneration()`. Two caveats are documented and both apply to JetBridge: generation is not always spec-only (Deployments bump it on annotation writes), and "any update events with writes only to the status field will not be reconciled. So in the event that the status block is overwritten or wiped by someone else the controller will not self-correct." https://github.com/kubernetes-sigs/controller-runtime/blob/main/pkg/predicate/predicate.go
The mechanism generalises: **partition the object into a half others write and a half you write; derive a monotone generation from the first half only; record observedGeneration in the second half. Self-writes then cannot change the trigger, by construction rather than by filter.**

**(f) Causation/correlation ids — and why they do NOT solve this across a foreign system.**
The standard formulation: "When responding to a message, you copy its correlation id as your correlation id and its message id becomes your causation id." https://railseventstore.org/docs/core-concepts/correlation-causation and https://blog.arkency.com/correlation-id-and-causation-id-in-evented-systems/
The limitation is decisive here: causation ids only close the loop when the caused event flows back through *your* store. GitHub does not propagate your causation id into the webhook it sends you. Which is precisely why every real-world bot falls back to (d) — a marker materialised into the artifact. **Causation must be written into the artifact when the transport won't carry it.**

# 2. Renovate and Dependabot: the actual mechanism is that they are not event-driven.

This is the answer, and it is structural rather than a filter.

Renovate's design doc, verbatim: "A key feature of Renovate is that it does not require any state storage (e.g. on disk or in a database)." / "Instead, Renovate's source of truth is the repository itself, e.g. branches, Issues and Pull Requests." / "Due to this design, it is possible to stop the script at any time without risking Renovate state being out of sync with repository state." https://github.com/renovatebot/renovate/blob/main/docs/development/design-decisions.md
Each run is a full reconcile: compute desired branches/PRs from config + registries, diff against actual, converge. A self-caused change is just another input to the next reconcile, and reconcile is idempotent, so it settles. **There is no version to consume, no cursor to burn, no retry semantics entangled with the trigger.** The `isBranchModified` author filter and the PR-body hash are second-line defences layered on a design where the loop is already impossible.

The confirming negative: Renovate's *one* genuinely edge-triggered surface is the rebase checkbox, and it is the one that produces documented infinite loops — if another tool ticks the checkbox, Renovate rebases, unchecks it, and the cycle repeats. https://github.com/renovatebot/config-help/issues/874 and https://github.com/renovatebot/renovate/issues/6690
Also relevant to JetBridge's "self-trigger via comments": Renovate has an open discussion precisely because comment authorship confuses its edit-detection, with a proposed `ignoredCommentAuthors` / extension of `gitIgnoredAuthors` to comments. https://github.com/renovatebot/renovate/discussions/36999

Dependabot: schedule-driven (`schedule:` in dependabot.yml), service-side, with the `[dependabot skip]` marker family as the escape hatch (above). Same shape: reconcile on a timer, filter by actor on content, allow an explicit in-artifact override.

**bors-ng** is the most instructive hybrid, and closest to JetBridge's problem:
- Trigger is an explicit human **command** (`bors r+`), not an observed state transition. Commands are naturally idempotent and carry intent; state observations are not and do not.
- It owns its own branch namespace (`staging`), force-pushing over it, so its writes land where nothing else is watching.
- FLOW_EXAMPLE is explicit that it learns CI results from **both** the Status API webhook **and** polling — "Polling exists because webhooks can fail without retry." https://github.com/bors-ng/bors-ng/blob/master/FLOW_EXAMPLE.md
- It keeps GitHub as source of truth and holds only minimal batcher state.

**GitHub Merge Queue** solves self-trigger by *event-type namespace separation*: merge groups fire `merge_group` (checks_requested) on `gh-readonly-queue/*` branches, which is a different event from `pull_request`/`push`, so the bot's own action fires an event type nobody's PR workflow listens for. https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue

**Mergify: I could not verify a source-level loop-prevention mechanism.** The only adjacent thing in their docs is `update_bot_account` (impersonation, to work around GitHub blocking in-place updates), which is not loop prevention. Treat as unknown. https://docs.mergify.com/workflow/actions/merge/

# 3. Webhooks vs polling-with-a-cursor: the industry does neither alone.

**Delivery guarantees are wildly asymmetric and GitHub is the weak end.**
GitHub: "GitHub does not automatically redeliver failed deliveries." A delivery fails if your server is down or "takes longer than 10 seconds to respond." Redelivery is manual or scripted and limited to "the past 3 days". GitHub publishes a sample workflow that runs every 6 hours to find and redeliver failures. https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries and https://docs.github.com/en/webhooks/using-webhooks/automatically-redelivering-failed-deliveries-for-a-repository-webhook
So **GitHub webhooks are effectively at-most-once with a 3-day manual repair window** — you cannot build an exactly-once loop on them without an independent reconciler.
Stripe, by contrast: automatic retry with exponential backoff "for up to three days"; manual resend 15 days (Dashboard) / 30 days (CLI); explicit "Stripe doesn't guarantee the delivery of events in the order that they're generated"; explicit dedupe advice — log processed event IDs — plus a warning that the delivery id alone is *not* sufficient: "In some cases, two separate Event objects are generated and sent. To identify these duplicates, use the ID of the object in `data.object` along with the `event.type`." https://docs.stripe.com/webhooks

**Signature and replay.**
GitHub: `X-Hub-Signature-256`, HMAC-SHA256, and "Never use a plain `==` operator. Instead consider using a method like `secure_compare` or `crypto.timingSafeEqual`". Critically, **there is no timestamp in GitHub's signature** — a captured delivery is replayable indefinitely, so dedupe on `X-GitHub-Delivery` is the only defence. https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries
Stripe signs a `t=` timestamp into the payload (`signed_payload = timestamp + "." + body`), libraries default to a 5-minute tolerance, and the docs say "Don't use a tolerance value of `0`. Using a tolerance value of `0` disables the recency check entirely." Also: on retry Stripe generates a *new* timestamp and signature. https://docs.stripe.com/webhooks

**The actual industry pattern is webhook-as-hint over a level-triggered reconciler.**
Fowler's taxonomy is the vocabulary: Event Notification — "An event need not carry much data on it, often just some id information and a link back to the sender that can be queried for more information" — with the named risk that logical flows become implicit and hard to trace; Event-Carried State Transfer buys autonomy at the price of duplication; Event-Sourcing makes the log the source of truth but "replaying becomes problematic with external system dependencies." https://martinfowler.com/articles/201701-event-driven.html
Kubernetes states the rule outright: "Level driven, not edge driven. Just like having a shell script that isn't running all the time, your controller may be off for an indeterminate amount of time before running again" and "If an API object appears with a marker value of `true`, you can't count on having seen it turn from `false` to `true`, only that you now observe it being `true`." Informers "periodically resync", and the justification for not trusting your own view is "There are other actors in the system." https://github.com/kubernetes/community/blob/master/contributors/devel/sig-api-machinery/controllers.md

**Cursor semantics: the distinction JetBridge is missing.**
There are two things called a cursor and they are not the same object.
- A **cache validator**: GitHub ETag + `If-None-Match`. "Making a conditional request does not count against your primary rate limit if a 304 response is returned and the request was made while correctly authorized." Losing it costs one request; resetting it is always safe. Caveats: ETags are per-page not per-collection, per-token, and GraphQL doesn't support them. https://docs.github.com/rest/guides/best-practices-for-using-the-rest-api
- A **position in a log**: consumed, advanced, and lossy if mishandled. GitHub is not a log — the Events API caps at 300 events / 90 days, and webhook deliveries at 3 days. **A position-cursor over a state store is a category error**, and JetBridge's measured pathology (a failed build burns its version; only the frozen cursor causes re-emission) is exactly that error surfacing: the cursor became load-bearing for retry because a log consumes and a state store does not.
Kubernetes' `resourceVersion` is instructive as the correct shape: it is server-owned, opaque, used for optimistic concurrency (409 StatusConflict on mismatch), and it is never the client's retry mechanism.

# 4. Durable execution: exactly-once is always "idempotent effect under a deterministically-derived key". Never the transport.

Every system converges on the same answer, differing only in where the dedup record commits.
- **Temporal**: the Workflow Id acts as an idempotency key; `WorkflowIdReusePolicy` (AllowDuplicate default / AllowDuplicateFailedOnly / RejectDuplicate) governs it. https://docs.temporal.io/workflow-execution/workflowid-runid. Recommended activity key: Workflow Run ID + Activity ID, "guaranteed to be consistent across retry attempts but unique among Workflow Executions." https://docs.temporal.io/activity-definition. And on messages, verbatim: "For Updates, Temporal handles this for you on the server, by deduplicating according to the Update ID"; but "For Signals, you should use a custom idempotency key that you send as part of your own signal inputs, implementing the deduplication in your Workflow code" — with the caveat that Update ID dedup is per Workflow *run*, so Continue-As-New breaks it. https://docs.temporal.io/handling-messages
- **Restate**: standard `Idempotency-Key` header (IETF draft); "After the invocation completes, Restate persists the response for a retention period of one day (24 hours)", and a resubmission within that window "sends back the same response and doesn't re-execute the request to the service." Auto-assigned random keys make retries safe but explicitly "does not deduplicate across different requests." https://docs.restate.dev/invoke/http
- **Inngest**: two layers — event-level `id` (same id ignored for 24h regardless of payload) and function-level `idempotency` as a CEL expression over the event, one run per unique key per 24h. https://www.inngest.com/docs/guides/handling-idempotency
- **DBOS**: workflow ID as idempotency key; exactly-once is real only when "your step writes to the same Postgres that stores the workflow state… The step's database writes and the step's durability record commit together or not at all." https://docs.dbos.dev/python/tutorials/workflow-tutorial
- The pre-durable-execution version is the same thing: transactional outbox + **idempotent consumer / inbox** — insert the message id into `PROCESSED_MESSAGE` inside the business transaction; PK violation means duplicate, roll back and ignore. https://microservices.io/patterns/communication-style/idempotent-consumer.html and https://microservices.io/patterns/data/transactional-outbox.html

Note what this rules out: a "45-column cursor row projected into pipeline config" is neither an idempotency key nor an inbox. It is a position, and positions only work over logs you control.

# 5. Prior art for "the external system is the state store, we hold no mirror" — and exactly where it breaks.

**It exists, it works, and it is the dominant design in this exact problem domain.**
- Renovate: the design-decisions quotes above are unambiguous. Source of truth = branches, Issues, PRs.
- bors-ng: GitHub is source of truth; minimal internal state.
- Kubernetes controllers: apiserver is the store; the informer is a *cache* (resynced, and explicitly not trusted to have seen every transition).

**Where it breaks down, with evidence:**
1. **Cost of re-derivation, not correctness.** Renovate eventually added `repositoryCache` — "Set this to `"enabled"` to have Renovate maintain a JSON file cache per-repository to speed up extractions", plus `repositoryCacheType` and `repositoryCacheForceLocal`. Note the shape of the compromise: a *derived* cache with an explicit `"reset"` value to bust staleness — never authoritative, always safe to discard. https://docs.renovatebot.com/self-hosted-configuration/ **This is the correct concession: mirror as cache-with-reset, not mirror as authority.**
2. **Rate limits and pagination.** ETags are per-page and per-token; re-deriving a large PR is many pages and GraphQL gets no conditional requests at all.
3. **The external store cannot express your vocabulary.** GitHub has no generation, no observedGeneration, no causation link, no place for a typed record. Everyone therefore smuggles state into the artifact (Renovate's base64 HTML comment, Dependabot's commit markers, RFC 3834's header). That *is* a mirror — stored in the foreign system, paid for in fragile parsing.
4. **Lossy, non-monotonic history.** Events API 300/90d, deliveries 3d, and PR objects are mutable (force-push, edited comments, resolved threads). This collides head-on with sealed immutable records: you cannot seal a record whose backing state can be rewritten and whose history the store does not retain.
5. **GitHub's own PR-review data model is undocumented where it matters.** The docs give `pull_request_review_id` and `in_reply_to_id` as bare types with **no descriptive text at all**, and say nothing about whether a reply attaches to a new review. https://docs.github.com/en/rest/pulls/comments — so the live observation (reply files under a NEW review) is the only authority, and it is not a contract. Any design that encodes GitHub's threading model into a sealed record type is encoding an undocumented, unversioned behaviour.

# 6. Structural read on the JetBridge question

The three measured pathologies are one pathology. **An edge-triggered, log-shaped pipeline (Concourse resource versions, consumed once at build start) is being driven off a state store (GitHub PRs).** The cursor exists because a log needs a position; the cursor became the retry mechanism because a log consumes on read; the self-trigger exists because a state store echoes your writes back into the log; the double snapshot exists because a level-triggered reconciler needs desired *and* actual state but `repository/v1` models a worktree at one HEAD. The base_sha impossibility proof is the same mismatch stated as a type error.

Every mature system in this space made the opposite choice: level-triggered, idempotent, external-store-as-truth, event-as-hint, plus a periodic sweep. And in the one mature reconciler that kept an edge-triggered surface (Renovate's rebase checkbox), that surface is the one with documented infinite loops.

The assets JetBridge already has map onto that design with no invention required: sealed typed records = the reconciler's observed state; workflows-as-pure-functions-over-snapshots = the reconcile function; `await_snapshot`/`human-answer/v1` = the durable human wait; the provider-neutral git push path = the write side that needs no forge API; and `repository-change/v1` — base-relative, with patch/bundle/tree forms — is precisely the operation-vs-snapshot distinction that CRDTs and OT make, and it dissolves the three-base_sha impossibility, because an operation names its base while a worktree only has a HEAD.

TRANSFERABLE:
- Compute a `generation` for the review state as a content hash over the human-authored subset only (threads and submissions not authored by the platform identity, base-branch tip, head commits not authored by us) and store an `observedGeneration` on the JetBridge side — self-writes then cannot change the trigger by construction, which is Kubernetes' spec/status split reimplemented for a forge that offers no such split.
- Replace the opaque provider cursor projected into pipeline config with that generation comparison, so the trigger becomes a stateless predicate (`generation != observedGeneration`) rather than a position in a log that a failed build can burn.
- Decouple retry from trigger completely: a level-triggered reconcile re-derives its input every run, so a failed build simply reconciles again, and no frozen cursor is needed to force re-emission.
- Treat every webhook as a hint that invalidates a cache, never as data — dedupe on `X-GitHub-Delivery`, then re-read current state from the API, because GitHub does not auto-redeliver, allows redelivery only for 3 days, and puts no timestamp in its HMAC so deliveries replay forever.
- Add a periodic reconcile sweep alongside webhooks exactly as bors-ng does ('polling exists because webhooks can fail without retry'), sized so that a total webhook outage degrades latency rather than correctness.
- If any mirror is kept, give it Renovate's `repositoryCache` shape — derived, explicitly resettable, never authoritative — so that deleting the whole table is always a safe operation with no behavioural change beyond a slower first run.
- Filter by actor on content rather than on events, copying Renovate's `isBranchModified` exactly: diff `origin/base..origin/head`, collect both author and committer emails, subtract your own identity plus a configurable ignore list, and treat an empty remainder as 'unmodified by humans'.
- Materialise causation into the artifact, because GitHub will not carry it back to you: stamp every platform-authored comment/commit with a machine-readable marker (RFC 3834's `Auto-Submitted`, Dependabot's `[dependabot skip]`, Renovate's base64 HTML comment) and refuse to act on any artifact bearing your own marker.
- Give the platform its own dedicated write identity (a distinct bot account or App) so that `sender`/author filtering is unambiguous — GitHub's own GITHUB_TOKEN recursion suppression only works because the actor is identifiable, and impersonating a human destroys that property.
- Publish into a namespace nothing else watches, the way GitHub Merge Queue confines itself to `gh-readonly-queue/*` and `merge_group` events, so platform writes land where the observer is not listening.
- Exclude your own fields from any equality test that decides whether to write: copy `getPrBodyStruct`, which strips the debug block before hashing the PR body, so the platform never sees its own last write as a change.
- Adopt an inbox table keyed on a deterministic idempotency key (delivery id plus object id plus event type, since Stripe documents that delivery ids alone are insufficient) and insert it inside the same Postgres transaction as the effect, which is the only construction that yields real exactly-once (DBOS, transactional outbox).
- Derive run identity from a deterministic key — `(review-object-id, generation)` — and reject duplicates at dispatch the way Temporal's Workflow Id + RejectDuplicate policy does, so a redelivered webhook or a double reconcile cannot mint a second run.
- Model the review object natively as a JetBridge sealed record and treat GitHub as a projection target rather than the object itself, since the forge's own PR-review data model is undocumented where it matters (`pull_request_review_id` and `in_reply_to_id` have no descriptive text in the REST docs) and mutable in ways a sealed record cannot represent.
- Prefer explicit commands over observed state transitions for anything the platform itself can cause — bors-ng's `bors r+` is an idempotent statement of intent, whereas watching for a state change is what creates the echo — so make human review actions produce explicit, addressable intents rather than being inferred from forge diffs.
- Carry the agent's work as `repository-change/v1` against a named base rather than as two whole-repository snapshots, which removes both the 99.98%-overlap storage waste and the three-way `base_sha` impossibility, because an operation names its base while a worktree only has a HEAD.
- Adopt ETag/`If-None-Match` for any remaining polling, since 304 responses do not count against the primary rate limit, and classify it explicitly as a cache validator (safe to lose, safe to reset) rather than a position cursor.
- Document and enforce the caveat controller-runtime ships with its `GenerationChangedPredicate`: if you ignore everything but generation changes, you will never self-correct when someone wipes the status you wrote, so add a low-frequency full resync that ignores the generation entirely.

## Modern VCS/change models: change-as-first-class-mutable-object (jj, Sapling, Gerrit/NoteDb, Radicle, ghstack) and content-addressed sealing of "store + named revision" (Software Heritage, Nix, Bazel REv2, OCI)

# 1. Change identity vs content identity — jj

jj splits identity in two. A **commit ID** is a content hash (20 bytes on the Git backend); a **change ID** is "a unique identifier for a change… typically 16 bytes long and often randomly generated." The glossary defines **rewrite** as "to create a new version of a commit with different contents, metadata (including parent pointers), or both" — and on rewrite "the change ID generally remains the same" while a new commit ID is minted. https://docs.jj-vcs.dev/latest/glossary/

Three consequences that matter for JetBridge:

- **Divergence is a named, legal state, not an error.** "A change that has more than one visible commit" is a *divergent change*, displayed with a `divergent` label. This is exactly JetBridge's proof-of-stuckness (agent draft on PR head vs rebased candidate on base tip): jj does not force those two to reconcile into one HEAD — it lets one change ID have two visible commits and surfaces the divergence. The contradiction only exists because JetBridge assumed one identity ⇒ one commit.
- **Superseded versions are retained, not deleted.** "A commit that is abandoned or rewritten stops being visible and is labeled as 'hidden'" but stays reachable by commit ID or by change ID with offset notation. Hidden ≠ gone. `jj evolog` walks the full evolution of one change; `jj op log` walks repository-state evolution. https://docs.jj-vcs.dev/latest/operation-log/ , https://man.archlinux.org/man/extra/jujutsu/jj-evolog.1.en
- **The operation log is a DAG of operations, each holding a view** (bookmark/tag/git-ref positions, heads, working-copy commit per workspace), with parent pointers and metadata. This is what gives jj lock-free concurrency: concurrent operations produce diverging op-log heads that are later merged, rather than a lock or a lost update. That is directly the model for N agents mutating one review object.

**Where the change ID lives, and why that is a warning.** jj, GitButler and Gerrit agreed to standardize the change ID as a **non-standard git commit header** literally named `change-id`, a 32-char reverse-hex string (e.g. `mlqnqnkrxpuvuuxzlzoltostwlwyskpx`), reverse-hex specifically so it cannot be confused with a SHA-1. Written by default since jj 0.30.0, controlled by `git.write-change-id-header`. https://www.gerritcodereview.com/design-docs/support-jujutsu-use-cases.html , https://docs.jj-vcs.dev/latest/git-compatibility/ , https://lobste.rs/s/aupah1/gerrit_gitbutler_jujutsu_projects

But it is **fragile through forge-side rewriting**: preserved by `git commit --amend`, *lost by `git rebase`* (unknown headers are dropped), so in a parent+child stack a reworded parent keeps its change ID while the rebased child loses it. Forgejo switched to `git replay` to stop destroying them. Gerrit's design doc also concedes "Jujutsu change ID's are not preserved on cherry-pick." Lesson for JetBridge: if identity travels *inside* the commit object, GitHub's own "Rebase and merge" / "Update branch" buttons will eventually erase it. Identity kept in a side ref that JetBridge writes is not subject to that.

Gerrit's older answer is the `Change-Id` footer in the commit message, which associates every "iteration of a commit" — a *patch set* — with the same change. https://gerrit.cloudera.org/Documentation/intro-user.html

# 2. Sapling/Meta — mutation records, and why they fit agents

Sapling tracks rewrites explicitly. "A mutation record is a record of how a modified commit came to exist" — amending A into B writes a record naming the predecessor, the successor, the operation type, the user and the timestamp. Two effects: smartlog renders the old version as *obsolete* with the new hash and the operation, and restack uses a parent's mutation info to compute where children should land. `predecessors` / `successors` revsets query the graph. https://sapling-scm.com/docs/dev/internals/visibility-and-mutation/

Key design decisions worth stealing verbatim:

- **Mutation and visibility are separate concerns.** Mercurial's obsstore decided visibility; Sapling's Mutation does not. Visibility is a separately maintained set of *visible heads* (plus everything ancestral to a remote bookmark, which is public/immutable). Consequence: hiding is local and reversible, and mutation history is pure lineage data. Trade-off they accepted: Mutation requires at least one successor, so it cannot express "prune" (obsstore can).
- **Mutation history syncs and tolerates gaps.** "When pushing or pulling draft commits to or from the server, Sapling includes records covering the full mutation history," yet the older commits themselves need not be shared — it navigates incomplete histories. And for scale it "only considers mutation records in the mutation history of the draft commits that you are currently working on." That is a bounded-working-set rule JetBridge can copy directly instead of loading whole change lineages.
- **Explicitly designed lighter than Mercurial's Evolve** to survive repos with millions of mutations.

**Parallel agents.** Ezyang's write-up argues the decisive property for multi-agent work is that *when a commit is amended* is decoupled from *when any given worktree moves to the successor*: other worktrees stay on the stale version until they explicitly `sl follow` (chase the successor chain, preserving local changes) or `sl adopt` (rebase orphans when a commit is inserted mid-stack). Git "does terribly" here because a rewrite yanks the ground out from under concurrent uncommitted work. https://blog.ezyang.com/2026/03/parallel-agents-heart-sapling/

This is the structural answer to JetBridge's three-bases contradiction: you do not need one HEAD that satisfies base_sha, PR head, and rebase candidate at once. You need a successor graph plus explicit, per-consumer follow points.

Meta's review side (Phabricator Differential) is the same idea in the review object: one Revision (D12345) accumulates numbered *diffs*, and review comments are anchored to a specific diff version. Sapling `sl pr submit --stack` pushes a stack as separate GitHub PRs including base-branch wiring; `sl pr submit` also maintains a `sapling-pr-archive-<user>` branch via GitHub's GraphQL API to keep superseded commits alive. https://github.com/jj-vcs/jj/blob/main/docs/sapling-comparison.md , https://sapling-scm.com/docs/git/github/

# 3. Storing MANY revisions of one logical change cheaply in git

This is a solved problem, and the solution is boringly uniform: **one ref per revision under a namespace, in one shared object store, appended never overwritten.**

**Gerrit.** Each patch set gets a static ref `refs/changes/XX/NNNN/P` (XX = last two digits of the change number, NNNN = change number, P = patch set). Gerrit's stated reasons are exactly the two JetBridge needs: it "anchors the commit in the repository during the review, so a `git gc` doesn't delete it prior to submission," and it makes each revision fetchable over ordinary git protocols. Cost is O(changed objects) — every unchanged tree and blob is shared, because git objects are already content-addressed. https://gerrit.cloudera.org/Documentation/user-upload.html , https://nv-tegra.nvidia.com/r/Documentation/concept-patch-sets.html

**Gerrit NoteDb — the review object itself in git.** Change metadata (status, votes, comments) lives at `refs/changes/45/12345/meta`, a notes branch whose commits are an append-only sequence: "modifications to changes are stored as a sequence of Git commits, automatically preserving history of the metadata," which "eliminates the need for separate SQL databases for change tracking." Inline comments are a NoteMap where "the key is the commit SHA-1 of the patchset that the comment refers to, and the value is JSON data," each entry carrying a `revId` field naming the patch set. Whole review history exports with `git clone --mirror`. Plugins can add fields without a schema migration. https://gerrit-review.googlesource.com/Documentation/note-db.html

**git-appraise (Google).** Fully serverless distributed review: requests in `refs/notes/devtools/reviews`, human comments in `refs/notes/devtools/discuss`, CI results in `refs/notes/devtools/ci`, and — notably — **robot/analysis comments in a separate ref, `refs/notes/devtools/analyses`**. One JSON object per line; merged with the git-notes `cat_sort_uniq` strategy so concurrent writers merge without conflict; when multiple requests annotate one commit they are "sorted by timestamp and the final request is treated as the current one." Machine-authored review content living in its own namespace is precisely the separation JetBridge needs between agent output and human review. https://github.com/google/git-appraise/blob/master/README.md

**ghstack.** For each commit: `gh/<user>/<n>/base`, `/head`, `/orig`. `base` and `head` are **never force-pushed** — a new revision appends a commit — which is what makes GitHub's own "changes since last review" render correct interdiffs, and incidentally retains every version. `orig` holds the true local commit for retrieval elsewhere. A `ghstack-source-id` commit trailer detects amends and re-keys the mapping. https://github.com/ezyang/ghstack

**Graphite.** Minimal side-band pattern: JSON blobs written with `git hash-object` and pointed at by refs under `refs/branch-metadata/<branch>`, so stack topology (parent branch + parent SHA) is git data that syncs with the repo. https://graphite.com/docs/track-branches

**git namespaces.** `GIT_NAMESPACE=foo` maps refs to `refs/namespaces/foo/refs/...`, letting many logical repositories share one object store. The docs call out that this is *better than alternates*, which "can suffer from duplication when new objects are added to repositories without ongoing maintenance," whereas namespaces "inherently prevent this duplication." Caveat stated explicitly: namespaces are **not** a read-access-control boundary. https://git-scm.com/docs/gitnamespaces

**Radicle COBs.** Issues and patches are CRDTs "encoded as a set of commits in a directed acyclic graph," each COB a disjoint commit graph, appendable by any node and mergeable without conflict, cryptographically signed, replicated peer-to-peer. `xyz.radicle.patch` explicitly supports "non-destructive updates to patches and code reviews tied to patch revisions." https://deepwiki.com/radicle-dev/heartwood/6.1-collaborative-objects-(cobs) , https://docs.radicle.xyz/guides/protocol

**git-bug.** Native entities/operations in git plus **bidirectional, incremental, resumable bridges** to GitHub/GitLab/Jira (`git bug bridge pull` / `push`). It is the working existence proof of "own the object, project it to the forge," including the resume/idempotency machinery. https://github.com/git-bug/git-bug/blob/master/doc/usage/third-party.md , https://www.freshports.org/devel/git-bug/

**Materialization without duplication.** One bare repo as pure object store + `git worktree` per checkout; `--reference`/alternates for `.git/objects/info/alternates`; partial clone with promisor packs (`.promisor` files record that a pack may reference objects the remote has promised). https://git-scm.com/docs/git-clone , https://stuff.mit.edu/afs/sipb.mit.edu/project/git/www/technical/partial-clone.html

# 4. Sealing "a store plus a named revision" — prior art

**Software Heritage is the closest match to what JetBridge needs, and it already has the exact object.** The archive is "conceptually a single Merkle Direct Acyclic Graph," with node types content / directory / revision / release / **snapshot**. Their *snapshot* is defined as: "A 'snapshot' of a given software origin records all entry points found there and where each of them was pointing at the time" — i.e. a **map from ref names to revisions, itself content-addressed** as `swh:1:snp:<hash>`. Around it sit *origin* (type, url) and *visit* (which origin was consulted when, yielding which snapshot). SWHIDs also carry **qualifiers** — `origin`, `visit`, `anchor`, `path`, `lines` — extrinsic context attached to an intrinsic content hash. https://docs.softwareheritage.org/devel/swh-model/data-model.html , https://docs.softwareheritage.org/devel/swh-model/persistent-identifiers.html

So the sealed-record shape JetBridge is missing is not exotic: `snapshot = {object-store digest} + {name → revision}`, with dedupe by construction because every directory and content node is shared.

**Bazel Remote Execution v2.** Action inputs are a Merkle tree: "files are the leaf nodes and are digested using their corresponding content; directories are the tree nodes and are digested using digests from their subdirectories and children files." A whole input tree is named by the root `Directory` digest; "shared subtrees, such as toolchains and external repositories, can be reused without re-uploading the same blobs." Identical content is stored exactly once in the CAS. This is the general form of "seal a tree by its Merkle root, not by a tarball." https://github.com/bazelbuild/remote-apis , https://deepwiki.com/bazelbuild/remote-apis/2-remote-execution-api-v2

**Nix flakes.** A locked input records **both identities**: `rev` (the git commit — provenance) and `narHash` (SRI hash of the NAR serialization of the tree contents — content identity), plus `lastModified` / `revCount`. The stated reason for narHash is that it "allows the store path to be computed," so the source can be substituted from a binary cache rather than re-fetched. Two-identity sealing (where it came from + what it is) is a pattern JetBridge should adopt wholesale. https://nix.dev/manual/nix/2.28/command-ref/new-cli/nix3-flake , https://github.com/NixOS/nix/blob/master/src/nix/flake.md

**OCI 1.1 `subject` + Referrers API.** Attach an attestation/SBOM/signature to a *digest* without copying the artifact: "the specification allows pushing the reference artifact without requiring the presence of the subject in the target registry." No tags needed; the registry tracks the relation. https://oras.land/docs/concepts/reftypes/ , https://aws.amazon.com/blogs/opensource/diving-into-oci-image-and-distribution-1-1-support-in-amazon-ecr/

**in-toto / SLSA.** `ResourceDescriptor` = `uri` + `digest` (where `digest` may be `gitCommit`) + optional name/annotations. Provenance references sources *by digest*; it never embeds them. https://slsa.dev/spec/v1.0/provenance , https://pkg.go.dev/github.com/in-toto/in-toto-golang/in_toto/slsa_provenance/v1

**On the dedupe failure specifically.** Content-defined chunking (restic: Rabin-Karp rolling hash; Borg: buzhash; FastCDC ~10× faster than Rabin at comparable ratios) exists precisely to survive shifted data: boundaries are chosen by content, so an insertion perturbs only nearby chunks. https://restic.net/blog/2015-09-12/restic-foundation1-cdc/ , https://deepwiki.com/restic/restic/5.3-data-deduplication , https://arxiv.org/pdf/2504.02095 — **but** CDC is the wrong layer for JetBridge: git packfiles are already delta-compressed and entropy-coded, so chunk-level dedupe over packfile bytes finds nothing. The 99.98% object overlap they measured is only recoverable at the git-object layer, which is *already* content-addressed. Sealing tar-of-worktree throws away the Merkle structure that would have made dedupe free.

# 5. Self-triggering — the forge's own answer

GitHub solved this at the platform level with **actor identity, not cursors**: "events triggered by the `GITHUB_TOKEN`, with the exception of `workflow_dispatch` and `repository_dispatch`, will not create a new workflow run," explicitly "to prevent recursion loops." The escape hatch is deliberately to use a *different* identity (GitHub App token / PAT) when you genuinely want recursion. https://docs.github.com/en/actions/concepts/security/github_token , https://docs.github.com/actions/using-workflows/triggering-a-workflow

The Gerrit/NoteDb answer is structurally stronger: the observer's cursor *is a git ref that the observer also writes*, so "have I handled this?" is a read of state you own, not an opaque provider token projected into pipeline config. And "what needs work" becomes a **query over current state** (`status:open`, unresolved comments) rather than a consumed position in an event stream — level-triggered reconciliation instead of edge-triggered queue consumption. That dissolves JetBridge's retry problem: a failed build does not "burn" anything, because nothing was consumed; the next reconcile re-derives the same predicate.

# 6. Creating and updating the review object with git push alone

Prior art that needs no forge API at all:

- **Gerrit**: push to `refs/for/<branch>`.
- **AGit (Gitea/Forgejo)**: `git push origin HEAD:refs/for/main -o topic="…"` creates a PR with no fork and no API; `refs/draft/*` for drafts, `refs/for-review/*` to submit review on an existing PR. Requires git ≥2.29 server-side. https://forgejo.org/docs/latest/user/agit-support/ , https://docs.gitea.com/usage/agit
- **GitLab push options**: `git push -o merge_request.create -o merge_request.title="…" -o merge_request.target=…`. https://docs.gitlab.com/user/project/merge_requests/creating_merge_requests/

GitHub has no push-to-create equivalent — that asymmetry is real. But note what it costs: only *creation* needs the API. Every subsequent revision is an ordinary push to the head branch, and ghstack demonstrates that if you never force-push, GitHub renders per-revision history for you.

# 7. The structural read

Every mature system in this space has converged on the same three-part shape, and none of them treat the forge's PR object as the source of truth:

1. A **stable change identity** distinct from content identity (jj change ID, Gerrit Change-Id, Sapling mutation lineage, Radicle COB ID, ghstack-source-id).
2. An **append-only, content-addressed record of every revision and every metadata mutation**, stored in the same object store as the code (Gerrit refs/changes/*/N + NoteDb meta, git-appraise notes refs, Radicle COB DAGs, Sapling mutation store + commit cloud).
3. The forge as a **projection/renderer** of that record, reconciled by an incremental bidirectional bridge (git-bug bridges, `sl pr submit`, ghstack).

JetBridge already owns the hard half of this: sealed content-addressed typed records with validation gates, workflows as pure functions over snapshots, a durable human-wait primitive, a provider-neutral git write-back path, and `repository-change/v1` as a base-relative change type. What it built on top — a 45-column mirror of forge state, an opaque cursor projected into pipeline config, and whole-worktree snapshots — is the part with no analogue anywhere in the prior art, and it is exactly the part that broke. The prior art says: own the review object, store its revisions as refs in one shared object store, and make GitHub a projection.

TRANSFERABLE:
- Split identity in two the way jj does: give each JetBridge review a stable change ID that survives every rewrite, distinct from the commit ID of whatever revision currently realizes it, so "this change, revision 7" is expressible without the forge's PR number being the primary key.
- Adopt jj's divergent-change concept so the agent's draft (on PR head) and the rebased candidate (on base tip) are two visible commits of ONE change ID rather than a contradiction to be resolved — the three-bases proof only bites because JetBridge assumed one identity means one HEAD.
- Replace repository/v1's worktree-tar with a Software-Heritage-style snapshot: {object-store digest} + {name -> revision} map, so a single sealed record can simultaneously name base_sha, pr_head, and rebase_candidate, and the 99.98% object overlap dedupes by construction instead of never firing.
- Seal two identities per source like Nix's flake.lock does — the git rev (provenance) AND a content hash of the materialized tree (narHash equivalent) — so the gate can verify content without re-fetching and the same tree can be substituted from cache.
- Store every revision of a change as its own ref under a namespace, Gerrit-style (refs/jetbridge/changes/<id>/<n>), which anchors objects against gc, makes each revision fetchable by ordinary git protocols, and costs O(changed objects) instead of a second full clone.
- Move the review object out of the 45-column mirror table and into an append-only git meta ref modeled on Gerrit NoteDb: each state change is a commit, inline comments are a NoteMap keyed by the revision commit SHA with a revId field, and the whole history exports with git clone --mirror.
- Give machine-authored review content its own notes namespace the way git-appraise separates refs/notes/devtools/analyses from .../discuss, so agent output and human comments never contend for the same anchor.
- Use the git-notes cat_sort_uniq merge strategy with one-JSON-object-per-line entries and latest-timestamp-wins semantics, so concurrent agents and humans appending to a review merge without a conflict resolution step.
- Never force-push the branch JetBridge publishes: append each new revision as a commit the way ghstack's base/head branches do, which preserves every revision AND makes GitHub's own 'changes since last review' interdiff correct for free.
- Kill the projected-cursor-in-pipeline-config entirely and make the trigger a level-triggered predicate over state JetBridge owns (unresolved comments on refs it wrote), so a failed build re-derives the same work instead of burning a consumed version.
- Adopt GitHub's own recursion rule — suppress observation of events whose actor is the platform's own identity — instead of trying to out-bookkeep the forge with an opaque provider token.
- Copy Sapling's separation of mutation lineage from visibility: mutation records (predecessor, successor, operation, actor, timestamp) are pure append-only lineage, while what any given consumer sees is a separately maintained, locally revisable visible-heads set.
- Adopt Sapling's follow/adopt split so that amending a revision does not yank the ground out from under other in-flight agents — each consumer explicitly advances along the successor chain when it chooses to, which is the multi-agent property JetBridge actually needs.
- Bound the working set the way Sapling does by only loading mutation records in the lineage of the drafts currently in play, and by tolerating incomplete lineage rather than requiring the full history to be present.
- Put JetBridge's change identity in a side ref it controls rather than a git commit header, because the standardized change-id header is destroyed by git rebase and cherry-pick — meaning GitHub's 'Rebase and merge' button would silently break identity.
- Model the GitHub binding as a git-bug-style bidirectional incremental bridge with per-operation counterpart metadata and resume, so re-import recognizes JetBridge's own exports and a restart is cheap.
- Reference sealed evidence by digest instead of copying it, following in-toto/SLSA ResourceDescriptor (uri + digest{gitCommit}) and OCI 1.1's subject field, which lets an attestation attach to a subject digest without the subject being present.
- Use one bare object store plus git worktrees, alternates, or GIT_NAMESPACE for materialization, since the namespaces docs explicitly note alternates re-duplicate over time while namespaces do not.
- Stop trying to recover the duplication at the tar/zstd layer — content-defined chunking cannot help against already-delta-compressed packfiles, and the overlap is only recoverable at the git-object layer that is already content-addressed.
- If provider neutrality is a goal, note that Gerrit, Gitea/Forgejo AGit (refs/for/<branch> with push options) and GitLab (-o merge_request.create) all create and update the review object by git push alone — GitHub is the outlier, and even there only creation needs the API.

## Change-centric review systems (Gerrit, Phabricator/Differential, b4 kernel series, jj, ghstack): stable change identity, numbered revisions, comment anchoring, bot self-triggering

## 0. The one structural difference

Every system below separates the IDENTITY of a logical change from the CONTENT of any particular version of it, and makes each version an immutable, individually addressable object. GitHub does not: a PR's identity is a mutable branch ref plus a mutable head SHA. There is no revision noun, so commits, reviews, comments and CI all collapse onto one moving pointer. All four pathologies JetBridge measured are downstream of that missing noun.

Gerrit's own words: "A change represents a single commit under review... Multiple git commits can share the same Change-Id... commits that share the same Change-Id are referred to as _patch sets_." (https://gerrit-review.googlesource.com/Documentation/concept-changes.html)

## 1. Stable identity independent of commits

**Gerrit Change-Id.** A commit-message footer trailer, e.g. `Change-Id: Ic8aaa0728a43936cd4c6e1ed590e01ba8f0fbf5b`, conventionally prefixed `I` so it is not confused with a commit SHA. "Change-Ids are created at commit time on the client side" by the `commit-msg` hook, which inserts one only if none is present — so amend/rebase/cherry-pick preserve it and the hook is idempotent. Stated rationale: "Gerrit needs to identify commits that belong to the same review." (https://gerrit-review.googlesource.com/Documentation/user-changeid.html, https://gerrit-review.googlesource.com/Documentation/cmd-hook-commit-msg.html)

Two mechanism details that matter for platform design:
- Matching is a TRIPLE, not a key: Gerrit binds an incoming commit to an existing change only when (Change-Id, repository, branch) all match. Same Change-Id against a different target branch is a different change — that is exactly how backports work.
- It is deliberately not globally unique: "a Change-Id is not necessarily unique within a Gerrit instance. It can be reused among different repositories or branches." The identity is scoped, not universal.
- Cherry-pick has an explicit escape hatch: keep the trailer to treat the new commit as a replacement, delete it to force a brand-new change record. Identity continuation is an author-controlled decision, not inferred from content.

**Phabricator/Differential.** Same trick, different trailer. `arc diff` "looks for a 'Differential Revision' line in your commit message to figure out what code review it corresponds to and uses that one. As long as you keep that line in the commit message the same, `arc diff HEAD~1` will update the review." Stacking is expressed as another trailer, `Depends on D12344 and D12345`, so the DAG of changes is data in the message, not a branch topology. (https://secure.phabricator.com/book/phabricator/article/arcanist_diff/, https://secure.phabricator.com/T11343)

**Kernel / b4.** `change-id` is "the unique `change-id` that is used to track your proposal across revisions", carried alongside a `base-commit:` line. `b4 send` "will automatically reroll your series to the next version and add changelog entries to the cover letter", and b4 "automatically discovers older and newer revisions of a tracked series using change-id and in-reply-to chains". Note that this works over EMAIL — no server, no branch, no mutable pointer anywhere. The identity is purely a trailer plus a monotone version integer. (https://b4.docs.kernel.org/en/latest/contributor/prep.html)

**Jujutsu.** The most explicit statement of the idea, at the VCS layer: "A change represents a commit as it evolves over time. Changes themselves don't exist as an object in the data model; only the change ID does." A change ID is 16 random bytes rendered in a k–z alphabet, and "when a commit is rewritten, the change ID generally remains the same", whereas the commit ID changes on every rewrite. jj also names the failure mode when identity is duplicated: a "divergent change" is "a change that has more than one visible commit". (https://docs.jj-vcs.dev/latest/glossary/)

**ghstack (identity invented on top of GitHub).** Real ghstack-produced commits carry both `Pull Request resolved: <url>` and `ghstack-source-id: <hash>` trailers; the tool re-reads them on every run to decide update-vs-create. This is the existence proof that you can own the identity yourself and still project onto GitHub. (https://github.com/ezyang/ghstack)

## 2. "Revision N of change X" as a first-class object

**Gerrit's ref layout is the whole answer.** "When a commit is pushed for review, Gerrit stores it in a staging area which is a branch in the special `refs/changes/` namespace... A change ref has the format `refs/changes/X/Y/Z` where X is the last two digits of the change number, Y is the entire change number, and Z is the patch set." And "A patch set is a git commit. Each patch set in a change represents a new version of the change and replaces the previous patch set." (https://gerrit-review.googlesource.com/Documentation/intro-user.html)

NoteDb states it as storage layout: "The different revisions ('patchsets') of a change 12345 are stored under `refs/changes/45/12345/${PATCHSET_NUMBER}`" and review metadata under `refs/changes/45/12345/meta`. (https://gerrit-review.googlesource.com/Documentation/note-db.html)

What that buys, concretely:

- **Immutable, permanently fetchable versions.** `refs/changes/45/12345/3` is never force-pushed and never deleted. Any tool, months later, can fetch the exact tree a comment referred to. GitHub's PR head can be force-pushed out of existence.
- **Addressability in the API.** A revision-id in the REST API is "commit SHA-1, patch set number, or `current`", so `GET /changes/{id}/revisions/3/...` is a stable URL for revision 3 of change X. Automation never has to say "whatever is on the branch right now".
- **Storage is deltas, not copies.** All patch sets are refs in the SAME destination repository, so revisions 1..N share every unchanged object. This is precisely the counter-design to JetBridge's measured 99.98% object overlap and 4x sealed-storage-per-observation: Gerrit pays for the delta, not for N worktrees, because a revision is a commit in a store, not a materialised tree.
- **A monotone integer.** Patch set numbers are per-change and increasing; change numbers are per-instance and increasing. `(change_number, patchset_number)` is a total order, i.e. a NATIVE high-water-mark cursor with no opaque provider state to mirror.
- **Review metadata is itself an append-only commit chain.** NoteDb stores "modifications to changes... as a sequence of Git commits, automatically preserving history of the metadata" — the meta ref is "a DAG of commits that track all modifications applied to a change over time". Comments live in a NoteMap where "the key is the commit SHA-1 of the patchset that the comment refers to, and the value is JSON data". This is structurally the same idea as JetBridge's sealed content-addressed typed records.

**Differential** has the same two-level model with weaker naming: a Revision (D123) accumulates Diffs over time; the web UI exposes a "Stack" tab; Phabricator closes revisions "based on commit and tree hashes, and Differential Revision identifiers in commit messages" — i.e. the landed commit is matched back to the change by identity, not by branch. (https://secure.phabricator.com/book/phabricator/article/differential/)

## 3. Bots replying to comments: why there is no self-trigger loop

This is the sharpest contrast with what JetBridge measured. The answer is not filtering — it is that **the version stream and the discussion stream are different streams**.

- **A comment or vote never mints a revision.** In Gerrit, a patch set is created only by pushing a commit to `refs/for/<branch>`. Posting a review emits `comment-added`; uploading a revision emits `patchset-created`. They are distinct event types carrying distinct fields (`patchset-created` carries `uploader`; `comment-added` carries `author`, `approvals`, `comment`; both carry `change` and `patchSet`). A bot that triggers on `patchset-created` structurally CANNOT self-trigger by replying, because its write goes to a channel that is not the trigger. (https://gerrit-review.googlesource.com/Documentation/cmd-stream-events.html)
- **Actor identity is on every event, and consumers filter on it.** Zuul's Gerrit driver takes `event` (regex over `patchset-created`, `comment-added`, `change-merged`, `ref-updated`, `change-restored`, `hashtags-changed`), plus `username` — "a regex applied on the performer username (Gerrit account name)" — plus `email`, `branch`, `approval`, `approval-change`, `comment`. Excluding your own bot account is a one-line filter. (https://zuul-ci.org/docs/zuul/latest/drivers/gerrit.html)
- **Bots are a first-class account class.** Gerrit's built-in "Service Users" group changes behaviour: service users are never automatically added to the attention set, and are granted access to the `stream-events` JSON stream. (https://gerrit-review.googlesource.com/Documentation/user-attention-set.html, https://wikitech.wikimedia.org/wiki/Gerrit/Bot_account)
- **Machine messages are tagged as machine messages.** "Review comments sent by bot accounts should add to their review a `tag` prefixed with `autogenerated:` which will filter older messages from the Web UI." Zuul uses `autogenerated:ci-test`, `autogenerated:gate-and-submit`. In PolyGerrit the reply button is hidden for such messages — the UI refuses to let a human start a thread on a bot's noise.
- **The real fix is a separate typed channel.** Gerrit's Checks API exists so CI stops writing comments at all: a plugin registers a ChecksProvider whose `fetch()` returns Runs each containing Results, and results are identified/updated by `(change, patchset, attempt, checkName)` plus a required `externalId`. That key is an IDEMPOTENCY KEY: re-reporting the same result overwrites rather than appends, so re-running is free and cannot generate new state. (https://gerrit-review.googlesource.com/Documentation/pg-plugin-checks-api.html, https://www.gerritcodereview.com/design-docs/ci-reboot-solution-ci-results-tab.html)
- **Turn-taking is explicit state, not inferred from event arrival.** The attention set encodes "whose turn is it": "Replying (commenting, voting or just writing a change message) removes the replying user from the attention set"; when a reviewer responds, the owner/uploader are added; on submit/abandon/WIP everyone is removed; and "Users are not added by automatic rules when the change is work in progress". An agent can therefore ask a direct question — "is it my turn?" — instead of diffing an opaque cursor.

Note also there is no "review" container object in Gerrit. A comment belongs to the CHANGE, is STAMPED with a patch set, and threads via `in_reply_to`. Three independent axes. JetBridge's observed bug — a reply landing in review B while pointing at a root comment in review A — is only expressible because GitHub inserted a fourth, mutable grouping object (the review) between the comment and the change.

## 4. What a comment anchors to, and rebase survival

**Gerrit.** Storage anchor is the patch set commit SHA (NoteDb NoteMap key), plus path/line/range/side; `CommentInfo` carries `patch_set`, `id`, `line`, `range`, `side`, `in_reply_to`, `unresolved`, `updated`. Because `refs/changes/../N` is immutable, the anchor never dangles — the exact blob the reviewer saw is always fetchable. Rebase survival is then a SEPARATE, DERIVED, OPT-IN read: `GET /changes/{id}/revisions/{rev}/comments?ported` and `.../drafts?ported`, added so that "users [can] view unresolved comments from all patchsets on the latest patchset". Gerrit also diffs across differing parents and highlights "rebase edits" in a distinct colour, so a reviewer can tell rebase noise from author edits. (https://gerrit-review.googlesource.com/Documentation/rest-api-changes.html, https://www.gerritcodereview.com/2020-11-18-gerrit-news-jun-nov-2020.html)

**Phabricator.** Same split, and the docs are unusually honest about the limits: "When a revision is updated, we attempt to port inline comments forward and display them on the new diff. Ported comments have a pale, ghostly appearance and include a button which allows you to jump back to the original context." And: "In the general case, it is not possible to always port comments to the same lines humans would automatically." Their worked example is `if (a() || b() || c())` being split into separate conditionals — no algorithm can know which sub-expression the comment meant. Porting is user-disableable via Settings > Diff Preferences > Show Older Inlines. The resolution policy is deliberately pessimistic: "When a line of code with an inline comment on it changes, we can not know if the change addressed the inline or not. We take the cautious route and _always_ assume it did not." (https://secure.phabricator.com/book/phabricator/article/differential_inlines/)

The design rule both encode: **the durable anchor is the original (revision, path, line); the ported location is advisory and visibly marked.** Never overwrite the anchor with the guess.

**GitHub, by contrast**, stores both and lets the live one rot. A review comment carries `commit_id`, `original_commit_id`, `position`, `original_position`, `line`, `original_line`, `side`, `in_reply_to_id`, `pull_request_review_id`, and the API warns: "Not using the latest commit SHA may render your comment outdated if a subsequent commit modifies the line you specify as the position." Because the head branch is mutable and force-pushable, the commit a comment points at can cease to be reachable, which is why force-push produces the "commented on an outdated diff" state. (https://docs.github.com/en/rest/pulls/comments, https://github.com/orgs/community/discussions/3478)

## 5. Base is a property of the REVISION, not of the change

This is the direct answer to JetBridge's proof #4 (draft based on PR head, candidate based on base tip, gate requires base_sha == snapshot HEAD).

- Gerrit: each patch set is a commit with its own parents. Rebasing produces patch set N+1 whose parent is the new base tip; patch set N still exists at its old base, permanently. The change does not have "a base" — each revision does.
- b4: every series carries an explicit `base-commit:` trailer, and when combining dependent series you "specify the `base-commit` to use for your combined series". The change travels as a base-relative artifact.
- ghstack: it manufactures the per-revision base as real refs — `gh/username/N/base` ("think of this like 'main': it's the base branch that your commit was based upon. It is never force pushed"), `gh/username/N/head` ("this branch is your change, on top of the base branch... We open a pull request on this branch, requesting to merge into base"), and `gh/username/N/orig` ("the actual commit as per your local copy. GitHub pull requests never sees this commit"). The PR is opened head-against-base so GitHub renders exactly one logical change.

JetBridge already owns the right primitive for this: `repository-change/v1` is base-relative with patch/bundle/tree forms. The frozen `repository/v1` contract only needs to hold ONE snapshot (the base), with every revision expressed relative to its own recorded base — which dissolves the three-way contradiction without a contract revision, and dissolves the 789.8 MiB / 4x storage result at the same time.

## 6. What JetBridge gains from change-id + numbered revisions

Mapping each measured pathology to the structural fix:

1. **Self-triggering (#1)** — versions are minted only when JETBRIDGE seals a new revision of a change. Comments/replies are a different, unversioned stream (Gerrit's `comment-added` vs `patchset-created`). Writing a reply cannot mint a version because replies are not revisions. GitHub becomes write-only projection; nothing is polled back as a version.
2. **Forge-state mirror + retry conflation (#2)** — the cursor becomes `(change_id, revision_n)`, a monotone integer JetBridge itself assigns, so there is nothing opaque to mirror into pipeline config and nothing to rewrite the pipeline for. And because processing keys on `(change, revision, check)` (Gerrit Checks' `externalId` pattern), re-emitting a version after a failed build is safe and idempotent — retry stops being an accidental side effect of a frozen cursor.
3. **Whole-repo snapshots (#3)** — Gerrit's N patch sets are N commits in ONE repository. JetBridge should seal one `repository/v1` per BASE and one `repository-change/v1` per revision. Storage becomes O(patch), sharing is structural rather than dependent on zstd windows or reproducible packfiles.
4. **The stuck shape (#4)** — base moves from the change to the revision, exactly as in Gerrit patch sets, b4 `base-commit:`, and ghstack's `/base` ref. No frozen-contract revision needed.

Plus three things that are pure gain rather than repairs:
- **Agent-legible history.** "Revision 3 addressed comments 7 and 9; revision 4 was a rebase only" is expressible and machine-checkable when revisions are objects. Gerrit's rebase-edit detection is the precedent for distinguishing "author changed something" from "the base moved" — an agent that cannot tell those apart re-reasons about noise on every cycle.
- **Durable anchors for the agent's own reading.** Because revision refs are immutable, the prompt "comment C was made on revision 3, file F, line 40" can always be resolved to the exact blob, months later. This is impossible against a force-pushable PR head.
- **Provider neutrality for free.** Gerrit-style identity needs nothing but git refs and trailers — b4 does it over plain email with no server at all. JetBridge's existing provider-neutral push path plus a `refs/jetbridge/changes/<change>/<n>` namespace is sufficient; the GitHub PR becomes a projected VIEW that can be deleted and rebuilt without data loss, exactly as ghstack treats the `/orig` branch as the truth GitHub never sees.

Practical shape suggested by the evidence: `jetbridge-change/v1 { change_id (opaque stable id, minted once, carried in a commit trailer), repo, target_branch, revisions: [ { n, base_snapshot_ref, change_record: repository-change/v1, sealed_at } ], threads: [ { id, anchor: {revision_n, path, line, side}, in_reply_to, unresolved } ] }` — identity scoped by (change_id, repo, branch) like Gerrit; revisions immutable and numbered; threads anchored to a revision and threaded independently of it; ported/derived positions computed on read and marked advisory.

TRANSFERABLE:
- Mint a JetBridge-owned opaque change id once and carry it as a commit-message trailer (Gerrit's Change-Id / Phabricator's 'Differential Revision:' / b4's change-id), so the identity of a logical change survives amend, rebase, cherry-pick and re-clone without any forge API.
- Scope change identity by the triple (change_id, repository, target_branch) rather than treating it as globally unique, so the same change id on a different branch is a legitimately different change (backports) rather than a collision.
- Make 'revision N of change X' a real, numbered, immutable object addressable by a stable ref (Gerrit's refs/changes/X/Y/Z, never force-pushed, never deleted), and make the numbering monotone so it doubles as the polling high-water mark.
- Store revisions as base-relative repository-change/v1 records against a single sealed base snapshot instead of one whole repository/v1 worktree per side, which collapses the measured 99.98% object overlap into O(patch) storage and needs no frozen-contract revision.
- Move base_sha from the change to the revision — every revision records its own base, as Gerrit patch sets do via their commit parent, b4 does via the base-commit: trailer, and ghstack does via a per-change gh/user/N/base ref — which dissolves the draft-vs-rebased-candidate contradiction outright.
- Split the event surface into two streams the way Gerrit splits patchset-created from comment-added: only sealing a new revision mints a Concourse version, while replies, votes and status writes go to an unversioned channel, so the platform's own writes structurally cannot re-trigger it.
- Key all automated results by (change, revision, check_name, attempt) with a required external id, following Gerrit's Checks API, so re-reporting overwrites rather than appends and retry becomes idempotent instead of depending on a frozen cursor.
- Publish agent output through a typed checks/results channel rather than as review comments, and if comments are still written, tag them with an autogenerated: prefix and post them from a service-user identity that is excluded from turn-taking, as Gerrit's Service Users group does.
- Filter inbound events on the performer's account identity (Zuul's username regex on the Gerrit account name) as a cheap second line of defence, never as the primary loop-prevention mechanism.
- Anchor every review comment durably to (revision_n, path, line, side) on an immutable revision, and treat any rebase-forwarded position as a derived, visibly-marked ghost — Phabricator's own docs concede exact porting is impossible in the general case, so the guess must never overwrite the anchor.
- Adopt Phabricator's pessimistic resolution default: when a commented line changes, assume the comment was NOT addressed until a human or an explicit agent claim says so, rather than silently dropping it as outdated.
- Drop the intermediate 'review' grouping object entirely — let comments belong to the change, be stamped with a revision, and thread via in_reply_to on three independent axes, which makes the cross-review-boundary reply bug unrepresentable.
- Expose an explicit attention-set-style 'whose turn is it' field on the change, updated by the same rules Gerrit uses (replying removes you, being replied to adds you, WIP and submit clear everyone), so the agent queries turn state instead of inferring it from event arrival order.
- Compute and surface a rebase-edit vs author-edit distinction when diffing revision N against N+1, as Gerrit does when the two patch sets have different parents, so an agent is not forced to re-reason about base-motion noise every cycle.
- Treat the GitHub PR as a disposable projection built from refs the platform force-pushes (ghstack's base/head/orig triple is the proven pattern), so deleting or recreating the PR is never data loss and no forge API call is on the critical path of the review loop.
- Record an explicit per-revision changelog entry ('v3: addressed comments 7 and 9', 'v4: rebase only'), as b4 auto-generates on reroll, so the agent's revision history is machine-checkable evidence rather than prose in a comment thread.
- Store the review metadata itself as an append-only chain of sealed records keyed by the revision commit id, mirroring Gerrit's NoteDb meta ref where the NoteMap key is the patch set SHA — JetBridge's sealed record store already is this, it just needs the change/revision schema on top.
- Provide 'delete the trailer to fork a new change' as an explicit author/agent affordance (Gerrit's cherry-pick rule), so identity continuation is always a deliberate decision rather than something inferred from content similarity.

## How agentic coding platforms actually run the code-review feedback loop: trigger mechanism, self-loop avoidance, server-side state, and whether the review conversation is modelled natively

## Headline: nobody in this field polls a forge for review *state*. The universal shape is "an explicit, human-authored imperative addressed to the agent, delivered by webhook, at submitted-review granularity." JetBridge's shape (poll a mirrored cursor, diff forge state, react to changes) has no analogue in any commercial platform surveyed.

---

### 1. TRIGGER: webhook + mention-gate, not poll + state-diff

| Platform | Transport | What actually starts a run | Documented? |
|---|---|---|---|
| **GitHub Copilot coding agent** | in-forge (no webhook needed) | `@copilot` mention **by a user with write access**; also "Fix with Copilot"/"Fix batch with Copilot" buttons | Yes |
| **Devin** | webhook | "PR comments are automatically sent to Devin by a webhook"; session auto-wakes; also `/devin review` | Yes |
| **OpenAI Codex cloud** | GitHub App (transport undocumented) | `@codex review` / `@codex fix it`; optional auto-review on PR open | Partly |
| **Google Jules** | GitHub App | human "starts a review"; optional **Reactive Mode** = only acts on comments mentioning `@Jules` | Yes |
| **Cursor cloud agents / Bugbot** | GitHub App | `@cursor` / `@cursor review` **as a top-level comment**; Bugbot auto-runs on new PRs and updates | Partly |
| **claude-code-action** | GH Actions events | `issue_comment`, `pull_request_review_comment`, `issues`, `pull_request_review` + `trigger_phrase` (default `@claude`) | Yes |
| **Qodo/PR-Agent** | FastAPI webhook endpoints per provider | PR open, `synchronize`, comment starting with `/` | Yes (source-level) |
| **OpenHands resolver** | GH Actions events | comment starting with `@openhands-agent` **authored by OWNER/COLLABORATOR/MEMBER** | Yes |
| **Aider** | none | no forge loop at all — human pastes review feedback into a local session | n/a |
| **agent-reviews (OSS toy)** | **polling**, `--interval 30` | `--unanswered` threads | Yes |

The only polling implementation found in the entire survey is a hobby CLI (github.com/pbakaus/agent-reviews), and it terminates on a **10-minute quiet period**, not a cursor.

**The structural point:** mention-gating converts an ambient state-diff problem into a discrete command problem. The trigger is an *imperative addressed to the agent*, not a *change in the world*. Self-triggering is impossible by construction, because the platform never `@`-mentions itself. Every commercial platform reached this independently.

### 2. BATCHING: the unit of work is the SUBMITTED REVIEW, not the comment

GitHub documents this explicitly and instructs humans to change behaviour to suit the agent:

> "Because Copilot starts looking at comments as soon as they are submitted, if you are likely to make multiple comments on a pull request it's best to batch them by clicking **Start a review**, rather than clicking **Add single comment**. You can then submit all of your comments at once, triggering Copilot to work on your entire review, rather than working on individual comments separately."
> — https://docs.github.com/en/copilot/tutorials/cloud-agent/get-the-best-results

Reinforced by the "Fix batch with Copilot" button (2026-05-19 changelog): "This helps you act on multiple comments more efficiently instead of handling each one individually."

JetBridge's self-triggering pathology (#1) is partly *self-inflicted by working at comment granularity*. GitHub's REST API is hostile to per-comment replies by design: `POST /pulls/comments/{id}/replies` "is only valid for standalone diff comments made using *Add single comment*, which are technically different from comments made as part of a review" (https://docs.github.com/en/rest/pulls/comments), and github/github-mcp-server#1322 exists precisely because there is no clean thread-reply primitive. The industry works around this by never operating below review granularity.

### 3. SELF-LOOP AVOIDANCE: five documented mechanisms, ranked by where they sit

**(a) Event-source suppression at the forge, keyed on the acting credential — the strongest, and only GitHub can do it.**
> "events triggered by the `GITHUB_TOKEN` will not create a new workflow run… this behavior prevents you from accidentally creating recursive workflow runs."
> — https://docs.github.com/en/actions/concepts/security/github_token

Note the shape: suppression is at the **emitter**, keyed on **which credential wrote**, not at the reader. The documented escape hatch is to write with a PAT/App token, i.e. deliberately re-enable the loop.

**(b) Bot-identity filtering at the reader — Devin's is the most complete design in public.**
- Default mode: **"Devin ignores all bot comments."**
- "Respond to all" carries an explicit warning: **"This mode may cause infinite loops with automated code review bots."**
- **Allowlist only, no denylist**; matched case-insensitively on usernames ending `[bot]`.
- Devin Review itself posts as `devin-ai-integration[bot]`, so **under the default, Devin does not act on its own review findings**. Self-loop closed by making its own identity subject to the same filter.
- One carve-out: "Lint failure comments from bots (containing 'lint check failed') are always processed regardless of this setting."
— https://docs.devin.ai/product-guides/bot-comment-settings

**(c) PR-Agent (readable source).** `should_process_pr_logic()` gate; GitHub path checks `sender_type == "Bot"` when `GITHUB_APP.IGNORE_BOT_PR` (default `ignore_bot_pr = true`); GitLab matches `sender_name` against `codium`/`bot_`; `ignore_pr_authors` for named accounts. Separately, `_duplicate_push_triggers` (a `DefaultDictWithTimeout`) collapses rapid `synchronize` events per PR URL. — https://deepwiki.com/qodo-ai/pr-agent/5.1-webhook-handlers-and-server-components

**(d) claude-code-action.** `checkHumanActor` in `src/github/validation/actor.ts` rejects **any** bot-authored trigger; `allowed_bots` is empty by default. Security doc: "By default, GitHub Apps and bots cannot trigger this action for security reasons," and warns "Allowed bots are not checked for repository permissions."

**(e) Text markers and iteration caps.**
- agent-reviews filters its own replies by their `> Re: comment …` prefix.
- **Sweep** caps self-review at **three iterations**, and on re-execution "incorporat[es] all files altered in the PR while omitting self-reviews" — an explicit loop bound plus source exclusion.

### 4. THE COST OF IDENTITY FILTERING — the most important finding for JetBridge

Identity filtering conflates *"don't loop"* with *"don't evaluate"*, and the failure is public and reproducible:

**anthropics/claude-code-action#1299** — "claude-review blocks itself when triggered by `claude[bot]`'s own commit — permanent red required check on PRs after @claude addresses review":
1. Human: `@claude address this` → 2. Claude commits & pushes as `claude[bot]` → 3. push fires `pull_request` → 4. `claude-review` workflow aborts with `Workflow initiated by non-human actor: claude (type: Bot)` → 5. **PR stuck with a failing required check and no code problem.**
> "the result is a **permanent red required check** on the PR, because the downstream `pull_request` event that fired on the bot's push gets blocked by the same workflow's actor policy."

The two proposed fixes are instructive: (1) *silent* exit-0 skip with a log line, vs (2) default-allow the action's own identity. The issue author judged (1) safer. Related: #900 (`checkHumanActor` 404s on bot actors *before* `allowed_bots` is consulted) and #1133 (`allowed_bots` bypasses the actor check but not the permission check).

Same class, different vendor: Cursor users report "**@cursor does nothing when mentioned on bot PR comment**" and "when a workflow posts a `@cursor` comment, it's authored by GitHub Actions, and it doesn't seem to be detected" — the identity filter makes the agent unreachable from automation.

**Conclusion:** author-identity filtering is the *default* answer in the field and is *known to be wrong at the edges*. The correct shape is what GitHub does — suppress at the write, keyed on "I caused this", not at the read, keyed on "who wrote this".

### 5. SERVER-SIDE STATE: essentially nobody keeps an "addressed" cursor

Three distinct positions, none of which is JetBridge's mirrored cursor:

- **CodeRabbit — the forge IS the database, deliberately.** "We had to design a system that stores all state within the pull request itself and not in our service for maximum privacy." The incremental-review state is a **summary-of-summaries saved and hidden inside a comment on the PR**, incrementally updated per commit. — https://www.coderabbit.ai/blog/coderabbit-deep-dive
- **Devin — the durable object is the SESSION, not the PR.** Sessions "sleep" rather than end; "when the PR receives comments or fails lint, Devin will automatically wake up to address it if it's sleeping." The PR is an *input channel into a long-lived conversation the platform owns*. Control Options live in Devin's own PR comment. — https://cognition.com/blog/sept-24-product-update
- **claude-code-action / PR-Agent — stateless re-read.** Claude "receives the full PR context, including any comments" on every run; the only durable artifact is a single sticky/tracking comment ("Claude is configured to update a single comment to avoid cluttering PR/issue discussions"). PR-Agent's only state is timeout-expiring in-flight dicts.

**The de-facto "have I handled this" bit in the whole ecosystem is GitHub's own per-thread resolved flag**, not a global cursor:
- `resolveReviewThread` GraphQL mutation is the standard write (agent-reviews `--resolve`; github/github-mcp-server#1768 requesting it).
- `--unresolved` / `is_resolved` are the standard read (agynio/gh-pr-review: "Keep only unresolved threads"; "Server-side filters for token efficiency").
- Devin Review: "When all threads in a bot-authored review are resolved, Devin automatically minimizes that review on GitHub."

A per-thread boolean is idempotent, self-healing, monotone, human-editable, and needs no pipeline rewrite. It is a *vastly* smaller state surface than a 45-column table projected into resource config.

### 6. RETRY vs CURSOR — these are separated everywhere except JetBridge

Webhooks are at-least-once by contract. The universal pattern is: **delivery layer retries; consumer dedupes on an idempotency key** (`X-GitHub-Delivery` GUID) persisted in a durable table **in the same transaction as the business update**. GitHub retries on 5xx and offers manual redelivery. Nobody uses "a frozen cursor" as the retry mechanism. JetBridge's coupling of cursor-advance to build success (finding #2) is unique in the survey and is the specific thing to factor apart: an event that a failed build consumed should be *redeliverable*, not *un-advanced*.

Charlie Labs states the requirement plainly: "A PR is a stream of changing states, not a document. New commits arrive, old comments are resolved, lines move… Avoiding this situation requires **idempotency keys, durable run state, reconciliation against the live PR**" and "Publishing safely requires **fresh anchors, prior-feedback awareness, run identity, and rules for cancellation and re-review**." — https://charlielabs.ai/blog/how-to-build-a-pr-review-agent/

### 7. DOES ANYONE MODEL REVIEW AS ITS OWN DURABLE OBJECT?

Among *agentic* platforms: only **Devin** (session), and only implicitly. Everyone else treats the forge PR as the object of record and themselves as stateless reactors.

The real precedents are outside agentics:
- **Gerrit.** A change is a first-class object with a stable `Change-Id` trailer, metadata, and **an ordered series of patch sets, each of which is one git commit**, plus comments and votes. Git holds `refs/changes/*`; the change is the object, the repo is the projection. Crucially: "The Gerrit review system is based on the assumption that each commit is reviewed separately, whereas at GitHub, a complete branch is reviewed." — https://gerrit-review.googlesource.com/Documentation/user-changeid.html and .../intro-gerrit-walkthrough-github.html
  **This dissolves JetBridge finding #4 directly.** The proof-of-stuckness rests on "one directory is one snapshot is one HEAD". Gerrit's answer is that a *change* is a store with revisions, each patch set naming its own base — the draft-on-PR-head and the rebased-candidate-on-base-tip are two patch sets of the same change, not two competing HEADs of one worktree.
- **Graphite.** Full bidirectional mirror: "continuously syncs every pull request, comment, and reaction… with full fidelity"; you can start a conversation in Graphite and reply from GitHub. This works, and it is a **$52M-funded, company-scale investment in a sync engine** — a cautionary datum on the cost of full mirroring.
- **HumanLayer / CodeLayer.** Human approval modelled as a first-class durable object the agent blocks on, with Slack/email/UI as projections — structurally identical to JetBridge's existing `await_snapshot` → `human-answer/v1`.
- **LangGraph `interrupt()` + checkpointer.** Node calls `interrupt()`, state is serialised to `PostgresSaver`, resume via `Command(resume=…)`. Same primitive JetBridge already has.

### 8. ACK MARKERS: the cheap, per-item, forge-visible cursor

Both Jules and Copilot converged on the same thing instead of a cursor:
- **Jules:** "When you start a review, Jules will add a 👀 emoji to **each comment** to let you know it's been read. Based on your feedback, Jules will then push a commit with the requested changes." — https://jules.google/docs/changelog/2025-09-23/
- **Copilot:** "an eyes emoji (👀) is added as a reaction to the comment, and a **'Copilot has started work' event is added to the pull request timeline**."

These are per-item, idempotent, human-visible, and — unlike a consumed Concourse version — they don't burn on failure.

### 9. OBSERVED FAILURE MODES (public)

- **Self-triggering, exactly JetBridge's #1:** openai/codex#11442 — "When replying with `@codex` to PR comments that Codex itself wrote, you trigger a new Codex task run unintentionally." The reporter asked for a *semantic* gate ("Codex should only start a task if the response asks for Codex to do something. It may be mentioned in passing or thanked for a comment without triggering a new task"). **Closed as not planned.** No public maintainer rationale.
- **Self-filtering causing a wedged PR:** claude-code-action#1299 (permanent red required check).
- **Agent unreachable from automation:** Cursor forum #153809, #148135.
- **"Agentic ghosting"** — GitHub's own term: agents "become unresponsive to review feedback or miss the point entirely across multiple rounds"; "larger pull requests with no structured plan correlate strongly with agent abandonment or misalignment." GitHub's mitigation is *not* a better loop — it's demanding a structured plan up front. Also: >1 in 5 code reviews on GitHub now involve an agent; a Jan-2026 study found agent-generated code carries more redundancy and tech debt per change. — https://github.blog/ai-and-ml/generative-ai/agent-pull-requests-are-everywhere-heres-how-to-review-them/
- **Unbounded-loop cost blowups (in-session, but the economics transfer):** github/copilot-cli#2881 (autopilot "continuously printing 'Continuing autonomously'… each iteration consumed a premium request"); community discussion #178998 (pre-commit timeout → agent assumes success → retries → "infinite loop that exhausts the Copilot session limits").
- **Whole-clone cost:** no public analogue found. Every platform surveyed operates on a **diff** plus a checked-out working copy it does not seal. Nobody stores two full repository images per observation — this appears to be a JetBridge-specific consequence of `repository/v1` being a worktree type rather than a store type.
- **Copilot's blast-radius control** is worth noting as a different lever: Actions workflows do **not** run automatically on Copilot's pushes; "Copilot PRs are treated like PRs coming from a fork" and require a human "Approve and run workflows" click (opt-out added 2026-03-13). GitHub chose *human gating of the downstream effect* over *filtering of the upstream event*.

### 10. WHAT IS CONSPICUOUSLY ABSENT FROM THE ENTIRE FIELD

- No one maintains a server-side mirror of forge review state and diffs it to derive work.
- No one projects forge state into CI configuration.
- No one treats the forge cursor as the retry mechanism.
- No one seals whole-repository images per review round.
- No one below submitted-review granularity.

Every one of those is a JetBridge-only property. That is the strongest available evidence that the current shape is the problem, not the tuning.

---

**Documented vs inferred:** trigger phrases, batching guidance, `ignore_bot_pr`/`allowed_bots`/Devin bot settings, `GITHUB_TOKEN` suppression, the 👀 markers, Sweep's 3-iteration cap, agent-reviews' polling and quiet-period, CodeRabbit's in-PR state, Gerrit's patch-set model, and all cited failure modes are **documented** (quoted above). Webhook-vs-poll for **Codex and Cursor** is **inferred** from GitHub App installation shape — neither vendor documents it. Devin's webhook is documented; its internal comment→session routing is not. No vendor publishes a postmortem on a review loop; the evidence base is issue trackers and support forums.

TRANSFERABLE:
- Gate every agent reaction on an explicit imperative addressed to the platform by a write-access human (the universal `@copilot`/`@codex`/`@cursor`/`@Jules`-reactive pattern), which kills the self-trigger class by construction because the platform never addresses itself.
- Move the unit of work from the individual comment to the submitted review, matching GitHub's own documented advice to reviewers to press "Start a review" rather than "Add single comment", so one human action yields exactly one run.
- Replace the opaque 45-column provider cursor with GitHub's per-thread resolved/unresolved bit (`resolveReviewThread` mutation, `is_resolved` read), which is idempotent, monotone, self-healing, human-editable, and requires no pipeline rewrite when it changes.
- Split retry from cursor: treat forge observations as at-least-once deliveries deduplicated on a durable idempotency key written in the same transaction as the business update, and let build retry be Concourse's problem rather than something the cursor emulates by refusing to advance.
- Suppress self-caused events at the write, not at the read: record every write-back in a platform-side publication ledger *before* issuing it, then classify any observed forge state that the ledger fully explains as a no-op — this is the shape of GitHub's own `GITHUB_TOKEN` suppression and avoids the documented `claude-code-action#1299` failure where author-identity filtering wedges a PR with a permanent red check.
- Never make author identity the sole loop guard, because the two public vendors that did (claude-code-action's `checkHumanActor`, Cursor's bot-comment filter) both produced user-visible pathologies where the agent became unreachable or a required check went permanently red.
- Adopt Gerrit's change model internally — a review is a durable change with a stable id and an ordered series of patch sets, each naming its own base — which dissolves the finding-#4 impossibility proof without amending the sealed-record gate, since base and revision stop being two competing HEADs of one worktree.
- Make the durable object the agent run/session that sleeps and wakes on input (Devin's model), with the forge as one input channel among several, rather than making the object a mirror of the forge's PR.
- Emit per-item forge-visible acknowledgements (👀 reaction per comment plus a timeline event, as both Jules and Copilot do) instead of projecting cursor state into resource config, since per-item ACKs are idempotent and do not burn on build failure.
- Give the review object an explicit termination rule as a first-class field — the only two documented loop terminators in the wild are Sweep's max-three-self-reviews counter and agent-reviews' ten-minute quiet period — rather than relying on humans noticing runaway spend.
- Default to ignoring all bot-authored feedback with an opt-in allowlist and no denylist, copying Devin's exact design including its explicit warning that respond-to-all "may cause infinite loops with automated code review bots".
- Do not build a full bidirectional forge mirror: Graphite raised $52M partly to fund that sync engine, and CodeRabbit deliberately went the opposite way by storing all its incremental-review state inside a hidden comment on the PR itself.
- Carry both sides of a review as one repository store plus two `repository-change/v1` records rather than two sealed worktree snapshots — no surveyed platform seals whole-repository images per round, they all operate on a diff plus an unsealed working copy, which is why none of them hit the 99.98%-overlap storage problem.
- Copy GitHub's blast-radius lever as well as its loop lever: it gates the *downstream effect* of agent pushes behind a human "Approve and run workflows" click instead of trying to filter the upstream event, which is a cheaper and more legible control than event suppression.
- Expect and design for "agentic ghosting" — GitHub's documented failure where agents go unresponsive or miss the point across multiple rounds, correlated with large unplanned PRs — by requiring a structured plan artifact before the revise loop opens, rather than by tuning the loop.


# DESIGNS

## Change Ledger: native change/revision/turn core, GitHub as a write-mostly projection [large]
The review object becomes a JetBridge-owned change — numbered sealed revisions over one shared base snapshot plus an append-only event ledger, reconciled level-triggered by the existing dispatcher — and GitHub becomes a disposable projection reached only through the existing directgit/publications path, which deletes the resource, the monitor, the cursor, and the double clone in one move.

THE OBJECT. Three small tables replace the 45-column `agent_pr_bindings`:
(1) `agent_changes` — id, team_id, repository, target_branch, change_uid, state (open/merged/abandoned), attention ('agent'|'human'|'nobody'), turn_generation, observed_generation, agent_turns_used, max_agent_turns, quiet_until. UNIQUE(team_id, repository, target_branch, change_uid) — identity scoped Gerrit-style, minted by JetBridge, never the forge's PR number.
(2) `agent_change_events` — append-only, PK (change_id, seq); kind IN (comment, thread_resolved, revision_sealed, submit, state_change); actor_kind IN (human, platform); anchor (revision_n, path, start_line, end_line, side); in_reply_to → seq; external_key UNIQUE (GitHub node id) for import idempotency; snapshot_id FK on revision_sealed. There is deliberately NO review-grouping row, so the cross-review-boundary reply bug (the one that bricked the observer live) becomes unrepresentable.
(3) `agent_change_projections` — (change_id, provider, external_id, url, etag, last_import_at). Renovate-cache shape: derived, resettable; TRUNCATE forces a slow re-import and changes nothing else.

STORAGE. One `repository/v1` base snapshot per (repository, target_branch), refreshed on base motion, whose refs map (landed in 22fec821be, `agent/snapshot/contracts/repository.go`) names the base tip AND every live change head — one clone carries all sides, killing the measured 99.98%-overlap double clone. Revision N of a change is a sealed `repository-change/v1` whose base_sha is a ref named in that snapshot: per-revision base dissolves the three-bases impossibility proof using machinery that already shipped. The exporter also pushes `refs/jetbridge/changes/<uid>/<n>` (append-only, never force) via `agent/publisher/directgit`, so GitHub's own interdiff works and objects are GC-anchored. Cost per observation drops from 789.8 MiB sealed to O(patch).

TRIGGER. No Concourse resource, no versions, no pipeline per change. turn_generation = sha256 over the human-authored event subset (actor_kind='human') + base tip. A ChangeReconciler added to the existing `agent/dispatch` loop (dispatcher.go Run/dispatchQueued) selects `attention='agent' AND turn_generation <> observed_generation AND no active run AND now() > quiet_until AND agent_turns_used < max_agent_turns`, then calls DispatchOne with run key (change_id, turn_generation); a unique index rejects duplicate dispatch. A failed run consumes nothing — the predicate is still true next sweep, so retry is re-derivation and the frozen-cursor-as-retry hack dies. observed_generation advances only when the run's revision seals.

SELF-TRIGGER SUPPRESSION, at the write not the read: every platform write is recorded in the existing `agent_publications`/`agent_publication_occurrences` ledger before the forge call; the importer marks any observed forge fact the ledger fully explains as actor_kind='platform'; the generation folds only human events — so the platform's own reply cannot change the state it watches, by construction. Dedicated bot identity filtering is the second line, never the first (claude-code-action#1299 lesson).

THE AGENT'S VIEW. At dispatch, a projector computes a turn packet from the ledger: OPEN threads only, anchored to revision N, rebase-forwarded anchors marked derived and pessimistically unresolved (Phabricator rule), plus per-revision changelog entries ('v3: addressed events 12,17'). Sealed as a new `review-turn/v1` record replacing `pull-request/v1` + `pull-request-response/v1` in `agent/snapshot/contracts/registry.go` — runs stay pure functions over snapshots, `AwaitSnapshotStep`/`human-answer/v1` approval is untouched, and the 200-thread history never re-enters the context: the packet is O(open threads).

THE BRIDGE, deliberately anemic. Export three things: push refs/branch (directgit), create the PR once via API, resolve threads the agent claims addressed. Import two things: submitted reviews and thread-resolution bits, via one shared per-repo poll loop using ETag/304, translated into change_events with external_key idempotency in a single transaction. Plus a low-frequency full resync that ignores generation. No bidirectional sync engine — that is Graphite's $52M problem and we refuse it.

WHAT 50-500 FORCES: per-change Concourse pipelines are dead (500 pipelines each rewritten on cursor motion is the real scaling wall — observation becomes one poller); comments must be DB rows, not sealed records (seal only the turn packet); termination must be first-class fields (max_agent_turns, quiet_until) because runaway spend is the top operational risk at that count; and the bridge must stay import-2/export-3 forever.

DELETES: cmd/forge-pr-resource and agent/pullrequest/resource/ (check.go, in.go, out.go, protocol.go, materialization.go) — the entire Concourse resource and its version-consumption semantics; agent/pullrequest/monitor.go (1,171 lines: MonitorCoordinator, ReserveAndLaunch, Acknowledge, reservation tokens), monitor_run_inspector.go, monitor_observation_inspector.go, atc/db/agent_pr_monitor_runs_factory.go and the agent_pr_monitor_runs table; agent/pullrequest/pipeline.go (647 lines) — the cursor-into-resource-config projection — and the PR-binding branch of agent/workflowrun/source_pipeline_lifecycle.go pipeline rewriting; atc/db/agent_pr_bindings_factory.go (1,871 lines) and the 45-column agent_pr_bindings table with all active_*/reservation/acknowledged_cursor machinery, replaced by agent_changes + agent_change_events + agent_change_projections; agent/pullrequest/triggers.go action-digest machinery (ActionFor, actionDigest, TriggerPolicy); agent/snapshot/contracts/pull_request.go (500 lines) and pull_request_response.go (217 lines); retire pull-request/v1 and pull-request-response/v1 from the registry in favor of review-turn/v1; the second whole-repository clone per observation and the rebased-candidate special-casing — the 4x sealed-storage path measured at 789.8 MiB per observation; the opaque provider cursor as a concept everywhere it appears (acknowledged_cursor, active_cursor, MonitorSourceVersion cursor validation)
RISKS: PR creation still requires one GitHub API call (GitHub is the outlier vs Gerrit/GitLab push-to-create); an API outage blocks projecting new changes — though not the review loop on existing ones.; turn_generation over the human subset inherits the controller-runtime GenerationChangedPredicate caveat: forge-side deletion of platform-written state is invisible to the trigger — the low-frequency full resync is load-bearing, not optional.; Human actions taken in the GitHub UI reach the reconciler only after the importer round-trip; at poll cadence there is a visible latency window on the agent's turn view (webhooks-as-cache-invalidation is the mitigation, later).; Retiring pull-request/v1 and pull-request-response/v1 is a frozen-contract event through record_schema_history — but finding #4 already proved a contract revision is mandatory; this spends that budget once, on the right object.; The refs-map base snapshot pins every live change head; refresh cadence and the 256-ref bound must be tuned per repo or storage regrows and seals start failing closed at high change counts.; GitHub 'Rebase and merge' produces a merge commit outside the revision-ref lineage; terminal state must be derived from base-branch observation, never from revision refs.; Migration ordering: agent_publication_occurrences and publication-authority rows FK RESTRICT into agent_pr_bindings, so in-flight bindings need a terminal-state backfill before the table drops.

## Ticket-native change series; the PR becomes a disposable projection [large]
A pull request is nothing but a mutable forge-side rendering of five things JetBridge already seals natively — base repository, change, review, approval, validation — so the review loop should run on the ticket's revision series inside JetBridge, with GitHub reduced to a one-way projection plus two explicit inbound commands, never an observed state machine.

DECOMPOSE THE PR AND CHECK EACH PART AGAINST THE INVENTORY. A PR is (1) a proposed change against a base, (2) a comment/finding conversation anchored to lines, (3) an approval, (4) CI status, (5) a merge affordance, (6) a durable identity for the whole exchange. JetBridge already has all six: (1) repository-change/v1 (agent/snapshot/contracts/repository_change.go) carries BaseSHA per revision against one repository/v1 store — commit 22fec821be just gave repository/v1 a refs map so ONE sealed store names base, head, and candidate simultaneously; (2) review/v1 (contracts/review.go) has Findings with typed Anchors (Subject+Locator: path/start/end), a conclusion enum, and a seal-time gate that changes-required requires a blocking finding; (3) the server-bound pr_approval/merge_approval await_snapshot producing human-answer/v1 (agent/workflow/typecheck.go:460-534); (4) validation/v1; (5) merge-delivery-v3 (base/candidate/target in, merge-preflight+merge-prepare, rebased repository-change/v1 out) landing through publisher.ModeBranch/ModeMerge over directgit with the provider-neutral refs/concourse/publications/<sha256> idempotence marker; (6) the Ticket (tickets.Store, Ticket.WorkflowRunID, agent/dispatch), which is already the durable unit that mints runs. So: do NOT invent a new review object — the codebase's documented failure mode is minting parallel machinery. Extend the Ticket with a revision series.

THE NATIVE OBJECT. Revision N of a ticket = the sealed triple (repository-change/v1, validation/v1, review/v1 self-review) produced by one workflow run, recorded as an ordered, append-only series on the ticket (a small revisions table keyed (ticket_id, revision_n) holding three snapshot IDs and the revision's own base_sha — snapshot IDs only, no mirrored forge fields; the sealed records stay the source of truth). Per-revision base is already how repository-change/v1 works, so the three-bases impossibility proof dissolves without touching any frozen contract: the draft (based on prior head) and the rebased candidate (based on target tip) are revisions N and N+1 with different BaseSHA over the same repository/v1 store. Storage per revision is O(patch), not a second 394 MiB clone; the 99.98% overlap disappears by construction.

THE LOOP. Harvest seals revision N and moves the ticket to needs_review (the harvest-v0 loop already lands this state). A human review is a FIRST-PARTY WRITE, not an observed forge diff: the web UI or fly files a review/v1 (findings + conclusion) or answers the standing pr_approval await with human-answer/v1. agent/dispatch gains one level-triggered predicate: 'ticket has a human-authored review/v1 with conclusion changes-required newer than its latest revision' is dispatchable work; it launches a new revise-v3 seed (replacing pr-monitor-v3) with inputs {base repository/v1, latest repository-change/v1, the review/v1, prior validation/v1} and run identity (ticket_id, revision_n+1), duplicate-rejected. No cursor, no per-PR pipeline, no consumed Concourse version: a failed run leaves the predicate true and the next dispatch re-derives identical work — retry falls out of level-triggering instead of a frozen cursor. Self-triggering is unrepresentable by type: the trigger is a human-authored review/v1 or human-answer/v1; the platform's outputs are repository-change/v1 and validation/v1; sealed records are immutable. This is the Kubernetes spec/status split enforced by the snapshot type system. Approval path unchanged: accept-conclusion review plus human-answer/v1 dispatches merge-delivery-v3, which lands via the existing marker-ref publisher.

THE GITHUB PROJECTION (small new adapter beside agent/publisher, reusing directgit). Outbound, per sealed revision: push branch refs/heads/jetbridge/<ticket>/change with append-only commits (never force-push, so GitHub's own 'changes since last review' interdiff stays correct), POST a commit status from validation/v1, upsert a PR body rendered from the sealed records and stamped with a machine marker. PR creation is the one steady-state REST call; deleting or recreating the PR is never data loss because every fact lives in sealed records. Inbound: exactly two commands, both explicit human imperatives — import a submitted GitHub review as a review/v1 authored by that human identity (idempotency key = forge review id, inserted in the same Postgres transaction as the ticket update) and import an approval as the human-answer/v1 answering the standing await. Import is a low-frequency level-triggered sweep over 'submitted reviews not yet sealed', skipping platform-marker artifacts; nothing is projected into pipeline config and there is no binding row per PR. For branch-protected repos where GitHub must own the merge, merge-delivery's final act calls GitHub's merge endpoint (the only other REST call) and confirms by git ls-remote of the target ref.

WHAT IS ACTUALLY LOST. GitHub's inline review UI and notifications for humans who live there — mitigated because the projection keeps a real PR they can review in, and their submitted review round-trips as review/v1. Required-checks integration — satisfied by one-way status writes. Anchor forwarding across revisions (GitHub 'outdated' handling) — handled natively with Phabricator's pessimistic default: an anchor on revision N whose line changed in N+1 is unresolved until a human or an explicit agent claim in the revise run's per-revision changelog says otherwise. Nothing else the PR provides exists anywhere but in the sealed records already.

DELETES: agent/pullrequest monitor machinery: pipeline.go per-PR pipeline rendering (one pipelines row + resource + job + checker per watched PR, ~35 consistent artifacts each), MonitorCheckState projected into atc.Source, updateProtectedMonitorPipelineConfig (~115 LOC private live-config mutator), monitor.go cursor/acknowledgement spine, the 7 exported interfaces with zero production implementations, and BindingStore's 16-method surface; RISKS: The native diff-review UI is the critical path: if the web UI cannot render an interdiff between revisions and file line-anchored review/v1 findings comfortably, humans will keep reviewing inside GitHub and the two-command import path silently becomes the real loop — i.e. the forge-observation problem reborn through the back door. ## repository-store/v1: seal the git object graph, name the revisions, derive the worktree [large]
A repository snapshot must be a content-addressed set of git objects plus a refs map naming many revisions — not a worktree at one HEAD — because git is already the Merkle store JetBridge is trying to build, and the tar-of-a-worktree wrapper is what destroys dedupe, forces the 4x clone cost, and creates the three-bases impossibility.

NEW TYPE: `repository-store/v1`, a materialized type (like `repository/v1`, deliberately NOT a record type — per the audit's own distinction it therefore needs no `recordSchemaHistories` event in `agent/snapshot/contracts/record_schema.go`). Its sealed bytes are a canonical OID-ordered object stream: for every git object in the closure, `(oid, type, size, content)` sorted by OID — a pure function of the object set, produced by a new `GitObjectCanonicalizer` beside the tar `Canonicalizer` in `agent/snapshot/archive.go`, which re-hashes every object against its OID while streaming (the seal gate becomes its own fsck). Two observations of an unchanged repo now produce byte-identical streams, so the whole-digest reuse in `sealer.go:401-405` fires for the first time ever, and Hangar needs zero changes: still one immutable `hangar/v1/snapshots/sha256/<digest>.tar.zst` per `hangar.Key`, still whole-digest `Store.Ensure/Open`, no chunk or delta API — layering lives above Hangar. Intrinsic metadata = today's `RepositoryMetadata` minus `head_sha`/`tree_sha` plus `refs` PROMOTED from advertisement (the 22fec821be duct tape) to the payload's meaning, plus optional `parents: []Digest`: a layer store contains only objects absent from its parents, and materialization unions layers — completeness is provable only with parents exposed, which is exactly the already-accepted `RevalidateSealed` base-binding pattern in `contracts/repository_change.go:163`, so self-containment stays honest (every layer's bytes prove themselves alone via OID hashing). Retention claims in `agent/snapshot/lifecycle.go` propagate along `parents` so GC cannot orphan a child. WORKTREES BECOME DERIVED: `cmd/function-runner` materializes `(store, ref)` into a pod mount by checkout from a node-local bare cache keyed by the existing `RepositoryID` (sha256 over object-format+root-commits, which carries over verbatim — it was always a store identity); the artifact daemon's cache holds one bare store per RepositoryID, derived and sweepable. Worktree safety gates (symlink escape, gitlink refusal, tree modes) move to per-named-revision root-tree validation at seal — `validateCommitTree` in `contracts/repository.go` already works per tree — and the entire `.git/config` allowlist attack surface disappears because the materializer writes its own config. THE ONE GOVERNED EVENT, taken deliberately as the payoff: `repository-change/v1` rev3 — new schema document file appended per the `record_schema.go:98` procedure — changes the base subject type to `repository-store/v1` and replaces the named rule `base-sha-must-equal-the-base-repository-head` with base-sha-must-be-a-revision-named-by-the-base-store (`document.BaseSHA` ∈ refs values, descent checks via `merge-base --is-ancestor` unchanged). That single rule change dissolves the (a)∧(b)∧(c) proof: `respond`'s draft binds base_sha = the PR-head ref and `repositorymerge/runner.go`'s rebased candidate binds base_sha = the base-tip ref, both against ONE sealed store carrying both refs. The forge-pr path collapses to what the audit already measured as optimal: one `git init` + one two-refspec fetch in `agent/pullrequest/resource/in.go`, sealing one store; `pull-request/v1` observations shrink from 394.9 MiB permanently pinned to record.json + a refs map; revision N of a review becomes one ref plus one O(delta) parent layer — Gerrit's refs/changes made out of parts JetBridge already owns. Beyond PRs: bisection, multi-branch validation, backports, and any workflow needing K revisions pays one store + K names instead of K clones, and re-observation of unchanged remotes is storage-free by construction. Rollout: `repository/v1` stops being minted but stays a permanent READ shape for the sealed corpus, the exact precedent `preRecordRepositoryChangeMetadata` in `contracts/repository_change.go:36` already sets.

DELETES: The dual-clone checkout loop and its claimed-directory-set assertions in agent/pullrequest/resource/in.go (source-repository + target-repository, in.go:112 and :309-313) — one store, two refs, one fetch; agent/functions/prmonitor/materialize.go's byte-for-byte WalkDir re-emission of two repository/v1 outputs (materialize.go:249-330, :445) — blobs B and C cease to exist as sealed objects; The two embedded full repositories inside every pull-request/v1 observation (the cp -a capture tree), i.e. the 394.9 MiB NULL-expiry system:resource-capture pin per observation; The repository/v1 SEAL path — worktree tars are never minted again; the type survives read-only for the existing corpus; The git-tree representation of repository-change/v1 and validateGitTreeChange (a full 10 GiB result-repository payload per change) — retired at rev3, git-bundle-against-store covers it in O(delta); The Refs advertisement bolt-on from commit 22fec821be, superseded by refs-as-payload with a real gate; The latent double-limit seal cliff (per-directory limits in in.go:155 vs combined-tree limits at seal) — the seal target is one object stream, not 2x worktrees; The .git/config allowlist parser and alternates/commondir containment checks in contracts/repository.go:282-640 as a sealed attack surface — no administrative git files are sealed at all; The temptation to build chunking/delta/CDC into Hangar — the Store interface stays exactly 6 methods
RISKS: repository-change/v1 rev3 is a governed descriptor-digest event and the project's own memory records such bumps as data-loss-class: the append procedure in record_schema.go must be followed exactly, rev2 records must revalidate forever, and the read gate must bind worktree bases (rev2) and store bases (rev3) during transition — the highest-ceremony piece of the whole design; Losing pack delta-compression may inflate the sealed full-store stream: 176 MiB of packed history could grow several-fold undeleted-and-undeltified before zstd; must be measured on this repo before commitment — mitigated because full-store seals happen once per repository and everything after is O(delta) parent layers, but a monorepo number is needed; ## Change Threads: native sealed review conversations with a write-only GitHub projection [large]
The review conversation becomes a JetBridge-owned append-only chain of three new sealed record types (change-open/v1, change-revision/v1, change-comment/v1) whose trigger is a level-triggered generation hash over the human-authored subset only, so the platform's own writes structurally cannot re-trigger it, each revision names its own base (dissolving the three-bases proof with zero edits to the frozen repository-change.v1.rev2 gate), and GitHub is demoted to a disposable write-only projection plus a narrow ledger-suppressed importer.

RECORD TYPES (new entries in agent/snapshot/contracts builtinTypeNames, new schema documents — no revision of any frozen document): (1) change-open/v1 mints identity once: {change_id ULID, repository_id, target_ref, originating agent_workflow_runs id}; identity is scoped (change_id, repository, target_ref) per Gerrit. (2) change-revision/v1: {change_id, revision_n monotone, kind: author_edit|rebase, changelog}, subjects = one repository-change/v1 (primary) plus its base repository/v1. Because EVERY revision names its own base, base_sha == base-snapshot HEAD holds per revision by construction — the draft (based on prior revision head) and the rebased candidate (based on target tip) are two revisions of one change_id, so the (a)∧(b)∧(c) impossibility in docs/superpowers/plans/2026-08-05-repository-snapshot-duplication-audit.md never arises and repository-change.v1.rev2.json is untouched. (3) change-comment/v1: {change_id, revision_n, optional anchor{path,line,side}, body, author{kind: human|agent, id, via: jetbridge|github+external_id}, in_reply_to digest, resolves digest} — comments belong to the change and thread by digest; there is NO review-grouping object, so the cross-review-boundary reply bug is unrepresentable. Reused unchanged: review/v1 for agent verdicts, validation/v1, human-answer/v1 + the await_snapshot step for approval, publish-impact/v1.

## Forge-fresh binding: version-as-generation, pipeline-as-binding [large]
GitHub already durably stores every bit the review loop needs; the only memory JetBridge requires is "which content-digests have already been built," and stock Concourse resource versioning IS that memory — so the binding collapses to a pure function (fresh read → platform-authored-content filtered out → sha256 → version) feeding one immutable instanced pipeline per PR, with zero JetBridge-owned forge state.

THE VERSION IS A GENERATION, NOT A POSITION. Rewrite `agent/pullrequest/resource/check.go` (currently a cursor-policy engine consuming `Source.Monitor.AcknowledgedCursor` and `pullrequest.ActionFor`'s TriggerPolicy) into a pure function: one fresh GraphQL read of the PR via `agent/pullrequest/github/observe.go` — state, base tip SHA, head SHA, review threads with `isResolved`, comments with author — then DELETE every node authored by the platform's GitHub App identity or carrying the platform's machine marker, canonically serialize the remainder with the existing `contracts/canonical_json.go`, and sha256 it. Check emits exactly one version `{generation, head_sha, base_sha}`. This is the Kubernetes spec/status split rebuilt for a forge that lacks one: platform writes are structurally outside the hash, so self-triggering is impossible by construction, not by bookkeeping. The self-trigger bug, the cross-review-boundary reply bug, and the review-batch delta contract (`Observation.ReviewBatches` as "strict delta vs Cursor") all evaporate because there is no delta — every check re-derives whole state.

WHERE THE MINIMUM DURABLE STATE LIVES (three places, none new):
1. GitHub — the PR, threads, resolved bits, and PR-body trailers (`JetBridge-Change-Id`, `Agent-Ticket`, originating workflow-run id) written once at PR-open by `agent/publisher/pr_service.go`. Provenance is read back fresh from the PR body; the `originating_workflow_run_id` / `monitor_workflow_definition_id` columns become text in the object they described.
2. Stock Concourse tables — `resource_config_versions` remembers which generations have been seen (this is the ONLY "have we handled it" memory, and it is not JetBridge schema; wiping it costs one redundant no-op run, the Renovate-resettable property); `builds` + build inputs record which generation each run consumed — the acknowledgement ledger for free.
3. The sealed record store — `pull-request/v1` observations sealed at get-time and publication records: append-only EVIDENCE, never consulted for coordination; deleting it loses audit, not liveness.

PIPELINE-AS-BINDING. One instanced pipeline per PR: `atc.PipelineRef{Name: "pr-review", InstanceVars: {repo, pr_number}}`, config a pure function of (workflow definition, repo, PR number) — no Monitor block in Source, therefore set once at PR-open by the publisher path that already exists in `agent/pullrequest/initial_coordinator.go` (shrunk to: push branch via `agent/publisher/directgit`, open PR, set instanced pipeline) and NEVER rewritten. Concourse features replace binding-table columns one-for-one: `serial: true` replaces the `active_reservation_token`/`active_workflow_run_id` reservation block; pipeline pause replaces `paused`; pipeline archive replaces `lifecycle_state`/`operator_terminated`/`terminal_*`; the pipeline dashboard replaces the binding list view. The job's terminal step archives the instance when a run observes state=merged/closed. The 45-column table was a reimplementation of the Concourse pipeline object.

RETRY DECOUPLED FROM TRIGGER. Because the version is a content digest and not a log position, nothing burns: a failed build reruns via stock `fly rerun-build`/web or `attempts:`, and the `get` re-reads the forge fresh at materialization (the stale-version gate in `resource/in.go` is already deleted — task 1 of the current track). The frozen-cursor re-emission hack, `ErrStaleMonitorSourceVersion`, and `MonitorSourceVersion`'s eight-field identity all die.

MATERIALIZATION. `resource/in.go`/`materialization.go` stop sealing two whole `repository/v1` worktrees; they seal one base store plus the head as a `repository-change/v1` (the contract already registered in `contracts/record_prototypes.go:21`, produced via `agent/repodiff`) whose body names its own base_sha — which also dissolves the three-bases impossibility, since a change names its base while a worktree only has a HEAD.

WEBHOOKS ARE A NUDGE, NOT DATA. Day 1: `check_every: 2m`, nothing else. Accelerator: point the GitHub App webhook at a ~150-line stateless relay that maps (repo, PR#) to `POST /api/v1/teams/:team/pipelines/pr-review/resources/forge-pr/check/webhook?webhook_token=...&vars.pr=N` — the endpoint already exists at `atc/routes.go:284`. No delivery-id table: a webhook is a cache-invalidation hint against an idempotent check, so replay and loss are both harmless; polling is the correctness backstop (bors-ng rule).

DEFENSE IN DEPTH FOR THE IDENTITY FILTER (the one thing that can rot): the job's first step is a cheap pre-LLM `compute-work` node over the sealed observation — "unresolved threads whose latest comment is not platform-authored"; empty means succeed as no-op. # SYNTHESIS

# Synthesis: the review object is the ticket's revision series

## 1. The recommendation, as a shape

**A review is a ticket whose latest revision is a sealed `repository-change/v1`. A human review is a sealed `review/v1` written *into* JetBridge whose primary subject is that change. The loop is the ticket's own revision counter: review seals → ticket revision bumps → the dispatcher that is already running re-dispatches → a new change revision seals → back to `needs_review`. GitHub is a set of refs JetBridge pushes and one PR it creates. Nothing in the loop ever reads the forge to decide what to do next.**

Two structural claims drive this, both verified in the tree:

**(a) The mirror exists to answer "what changed since I last looked," and that question only exists because the answer lives somewhere else.** The cursor, the 45-column table, the pipeline-per-PR, version-as-log-position, the action digest, the reservation token — none of these are bugs to fix. They are all consequences of one decision: putting the review conversation in a system JetBridge does not own. Move the conversation inside and these artifacts do not get repaired, they *lose their referent*. Finding #2's discovery that the cursor is secretly also the retry mechanism is the tell: two unrelated concerns collapsed into one field because there was only one place to put durable state about someone else's object.

**(b) The native review object already exists, is registered, and has a UI.** `/Users/tdmtrader/concourse/concourse/.claude/worktrees/modest-noether-2975f7/agent/snapshot/contracts/schemas/review.v1.rev2.json` declares `"subject_type": null` — **any** type may be the primary subject. `review/v1` already carries `Findings` with typed `Anchor{Subject, Locator{Path, Start, End}}`, a blocking/conclusion consistency gate, a per-finding human verdict channel (`agent_feedback`, keyed `(review_snapshot_id, finding_id, reviewer)`, upsert-idempotent), a read API at `agent/api/reviews/`, and Elm surfaces at `web/elm/src/AgentReviews/` and `web/elm/src/Build/AgentReview.elm`. **A human review of an agent's change is a `review/v1` whose primary subject is a `repository-change/v1`, and that is legal today with zero contract changes.**

And the identity/trigger machinery is already built and *running live*: `agent_tickets` has a monotone `revision` with immutable revision capture, a deterministic dispatch key `ticket-dispatch/v1/ticket/%d/attempt/%d/revision/%d` (`atc/db/agent_tickets_factory.go:327`), reject-duplicate semantics, a legal `needs_review → queued` edge (`agent/api/tickets/types.go:61`), and a polling dispatcher with explicit no-notify-only discipline (`agent/dispatch/dispatcher.go`). That *is* the (object, generation) level-triggered reconcile that three of the five designs propose to construct.

**The decisive fact nobody's risk section got right: none of the PR stack can execute.** `atc/atccmd/agent_publisher.go` appends `incompletePRAuthoritySpineError` unconditionally when `PullRequestsEnabled` — both in `validateAgentPublisher` (web refuses to boot) and in the executor constructor (`return nil, errors.New(...)`). `NewAgentPRBindingsFactory` lives inside that dead branch; `NewAgentPRMonitorRunsFactory` has zero call sites including tests. **There are no live bindings, no in-flight PRs, no drain, no cutover, no migration hazard.** Every "live cutover" and "in-flight PR" risk across the five writeups is wrong. This is ~20.5k src / ~17k test lines that has never run in production.

## 2. What it draws from, what it discards

**Draws from Design 4 (Ticket-native change series)** — the spine, essentially intact: ticket as change identity, revision as sealed triple, human review as a first-party write, forge as one-way projection, import narrowed to explicit commands.

**Draws exactly one line from Design 3 (repository-store/v1)** — the gate relaxation, nothing else. `agent/snapshot/contracts/repository_change.go:218` enforces `document.BaseSHA != baseMetadata.HeadSHA`; the frozen rule is named `base-sha-must-equal-the-base-repository-head`. `repository/v1` now carries `Refs map[string]string` (commit `22fec821be`, `contracts/repository.go:40`). **rev3 changes that one rule to *base_sha must be a revision named by the base repository* — HEAD or any ref.** It is a strict widening: every rev2 record still validates, one validator serves all revisions (`registry.go:147`), and read-time acceptance is `anyAcceptedSchemaDigest`. The append procedure is documented at `contracts/record_schema.go:37-56` and has been exercised four times already (`validation/v1` rev3, `publish-impact/v1` rev3, `pull-request/v1` rev3, `pull-request-response/v1` rev4). This one rule simultaneously dissolves the (a)∧(b)∧(c) impossibility, collapses the 99.98%-overlap double clone into one store with two refs, and makes "revision N, based on X" expressible.

**Draws the discipline, not the tables, from Designs 1 and 5** — level-triggered predicate, suppression at the write ledger rather than by author identity, `agent_publications`/`agent_publication_occurrences` as the ledger. All implemented on machinery that exists.

**Discards Design 2 (Forge-fresh binding) wholesale.** It keeps GitHub as the source of truth and makes content-based identity filtering the single load-bearing loop guard. Both public precedents that leaned on that (claude-code-action#1299, Cursor's bot filter) produced user-visible pathologies, and this codebase *already proved live* that a platform reply mints a new review. It also keeps a Concourse pipeline per PR, which is the real scaling wall at 50-500 changes.

**Discards the new record types** (`change-open/v1`, `change-revision/v1`, `change-comment/v1` from Design 1; `review-turn/v1` from Design 5). `review/v1` + `repository-change/v1` + `validation/v1` + `human-answer/v1` already span the space. Minting parallel machinery beside working machinery is this platform's documented failure mode; do not repeat it on the one object that already works.

**Discards the `agent_change_events` ledger (Design 5).** Threads are not needed for v1: a `review/v1` with anchored findings *is* the comment set for one round, and `agent_feedback` already carries per-finding human verdicts. Add threading when someone hits the wall, not before.

**Discards the canonical git-object stream (Design 3).** Unmeasured compression risk against 176 MiB of already-delta-compressed packed history, a new parent-layer GC surface in a codebase with a documented NULL-expiry pin-leak history, and it buys the same unlock the one-line gate change buys.

## 4. What would have to be true for this to be wrong

**1. Humans will not review inside JetBridge.** This is the whole bet. If reviewers keep reviewing in GitHub, the narrow importer silently becomes the primary loop and the forge-observation problem returns through the back door with *less* machinery to handle it than exists today. Note the honest asymmetry: the live loop today is agent-reviews-human (`code-review-v3` → `agent_feedback`), and it works this way. The inverse — human reviews agent's change, on JetBridge's surface — is unproven. If it fails, Design 2's shape is right and this recommendation is wrong.

**2. Branch protection makes the forge authoritative on the exit path.** If the target repos require GitHub-side approving reviews before merge, a JetBridge-native approval is not sufficient; the imported human review must *also* exist as a GitHub approval, which means a human must act in GitHub anyway — which collapses (1). Check the actual protection rules on the repos JetBridge will land into before committing to the native surface.

**3. `review/v1` cannot carry a real code review.** It has conclusion / summary / anchored findings, but no threading, no reply-to, no per-finding resolution state, and its seal gate forces `changes-required` to carry a blocking finding. My claim is that one sealed review per round plus `agent_feedback` for per-finding verdicts is enough for the first ten changes and threads should be added only when someone hits the wall. That is a bet, not a proof. If real review needs threads on day one, Design 5's event ledger is right.

Secondary and real but not disqualifying: the merge oracle (squash/rebase rewrite SHAs, so "absorbed into target" must be patch-id/tree containment, and it needs an explicit human close as backstop); `maxRepositoryRefs = 256` (`contracts/repository.go:197`) if one base snapshot names every live change head; and anchor staleness across revisions, which is unsolvable in general — take Phabricator's pessimistic default (a changed line leaves its finding *unresolved*) and explicitly decline to build a clever porter.

## 5. The smallest valuable increment

**Let a human file a `review/v1` against a ticket's sealed `repository-change/v1`, and let the existing dispatcher re-dispatch that ticket with the review as an input.** No forge. No projection. No new tables. No contract revision.

1. `POST /api/v1/teams/:team/agent/reviews` accepting a human-authored `review/v1` whose primary subject is a `repository-change/v1`.
