# Native agentic-first review: designs, critiques, and the MVP

Generated 2026-08-07 by two codebase-grounding agents, six independent Fable
design agents working from distinct creative frames, six adversarial critiques,
and one synthesis (15 agents, ~2.1M tokens).

Brief: reinvent the pull request natively, agentic concerns first -- a sealed
review structure driven by agent or human, carrying content a forge PR cannot
express (agent findings the human adjudicates, evidence proving the fix, and an
agent-authored reading order). Forge integration deferred entirely. Wanted: an
MVP that validates the approach, not a total solution.

The six frames were: guided walkthrough, proof-carrying claims, agent-interviews-
human, intent-over-code, attention budget, and one unconstrained.

Two claims in the synthesis were independently verified against the tree before
this was committed, and both hold: (1) no run-side path advances a ticket's
repository_snapshot_id, so re-queue after needs_review re-runs from the original
base; (2) small-fix-v3 emits no review/v1 at all.

# NATIVE REVIEW, MVP — THE RECOMMENDATION

## 1. THE SHAPE

Build **The Round**: a review revision is the ordered pair of two sealed snapshots over one immutable candidate — an agent-authored **`review/v1`** (reused unchanged, no schema revision) whose findings carry stable zero-padded ids, and a human-authored **`review-response/v1`** (one new *document* type, server-materialized, never uploaded) that assigns a typed disposition to each finding, carries free-text directives, and records what the human never looked at. The response is not a comment thread and not a payload on a state transition: it is a **snapshot bound as an optional third input port on the next dispatch**, alongside a fourth optional port carrying attempt N's `repository-change/v1` so attempt N+1 edits the code it was reviewed on instead of restarting from base. Identity of a round is the pair `(review digest, response digest)` over a fixed candidate digest — content addressing gives us a revision noun for free, so we mint no revision object. `needs_review` becomes the review screen: findings on the left with four disposition buttons, the changed-file list on the right with examine checkboxes, and three exits — Accept & close, Send back (carries the response forward), Re-queue clean (discards it). **No new record type. One new document type. Two new nullable columns. One clause in `resolveTicketPorts`.**

## 2. WHY THIS SHAPE

**(a) The loop is broken below the review layer, and every design on the table built on the break.** I verified it: `repository_snapshot_id` is written only by ticket create (`atc/db/agent_tickets_factory.go:66`) and `Update` (:237-256), and `Update` refuses to move it while a reservation exists. Nothing run-side ever advances it. `needs_review → queued` clears `work_item_snapshot_id`, `dispatch_reservation_key`, `pipeline_run_id` (:487-499) and leaves the repository pointing at the original base; dispatch then binds `*current.RepositorySnapshotID` verbatim (`agent/dispatch/dispatch.go:236`). **Attempt 2 today never sees attempt 1's code.** Two independent critiques (Five Questions #1, Attention Docket #1) found this. Any feedback channel built on top of it is a hint channel: you send back "the retry loop swallows `ErrStaleTransition`" and the agent rewrites the fix from scratch. Carry-forward is item zero, and it is smaller than any of the six review objects proposed.

**(b) `review/v1` already is the review object, and this project's documented failure mode is minting parallel machinery beside working machinery.** Its `subject_shape` (`schemas/review.v1.rev2.json:8-19`) has `subject_type: null`, `primary: exactly 1`, `evidence: 0..unbounded`, `reference: 0..unbounded` — so a review can name a `repository-change/v1` as primary, a `validation/v1` as evidence, and a prior response as `reference`, **today, with no schema change**. Findings are an entity-set with stable ids, severity, blocking, category (an *open* identifier set), markdown description, evidence anchors, and recommendation. That is Docent's stops, Claim Ledger's claims, and Attention Docket's items, minus fields nobody has yet earned. Every design that minted a new record type paid ~7 production edits, 6-7 test tables, a permanent registry slot and a frozen descriptor — the one genuinely irreversible move in this codebase — to test a *behavioral* hypothesis. Wrong order.

**(c) The human's half cannot be a record, so it must be a document, and documents are cheap.** `agent/snapshot/sealer.go:285` builds `NewValidationContext(nil, nil)` for uploads and every record needs ≥1 subject rebound to a declared exposed input (`record.go:157-174`) — **a human-authored review record is structurally impossible to upload.** The escape is the one the platform already uses: capture-not-upload, server-materialized (`agent/workflowwait/materializer.go:31-115`, `agent/workitem/capture.go:221-232`). Document types need no schema document, no `recordSchemaHistories` entry, no record prototype, no parity fixtures — verified: `agent/snapshot/contracts/schemas/` contains zero files for `work-item`, `question`, `human-answer`, `opaque`, `log-bundle`. Cost is a Go struct, one `builtinValidator` case, one `builtinTypeNames` line, and the count test 20→21.

**Draws from:** Case Law (the disjoint direct-the-work vocabulary; capture-at-dispatch as the channel; folding-as-presentation), Five Questions (the optional zero-or-one typed port — verified safe: `resolveTicketPorts`' switch at `dispatch.go:387-402` counts only `work-item/v1` and `repository/v1`, unknown types fall through, so no existing workflow breaks), Attention Docket (the attention receipt; budget refusal, deferred), Claim Ledger (the send-back compiler, made atomic).

**Discards:** `walk/v1`, `claim-ledger/v1`, `intent/v1`, `interview/v1`, `review-docket/v1` — five parallel record types for one hypothesis. `KindRecordRef` in any form (`schema_core_validator.go:204-210` returns a hard error; it also breaks the parity fixture gates). The zero-padded-id-as-reading-order trick as *ordering* (Docent's critique #1 is right: an id cannot simultaneously be stable identity and mutable sequence) — I keep the padded ids for stable identity and deterministic sort only. Agent-declared `touches`/coverage residue (unverified producer claim, monotonically gameable). Pre-implementation intent approval (adds a 72h blocking gate with no reject affordance — `questionAcceptsAnswer` only accepts a declared option, and the option list is `[approve]`).

## 3. THE OBJECT, SPECIFIED

**Reused unchanged — no schema revision anywhere.**

- `review/v1` — the agent half. Subjects: primary = the `repository-change/v1` candidate; evidence = `validation/v1`; context = `work-item/v1`; **reference = the prior round's `review-response/v1`** (legal today, `reference: 0..unbounded`, and `AdmitForSeal` binds it to the step's declared input digest, so "this judgment was rendered under exactly that response" is machine-checked). Findings use ids `f-0010`, `f-0020`, … — stable across attempts, reused verbatim when a finding persists. **The `category` identifier set is open** (`review.go:80` runs `ValidateIdentifier` only), so any vocabulary we are not yet sure about — `resolves:f-0020`, `tier-must` — rides there in the MVP. Deliberately ugly, deliberately unfrozen, deliberately reversible.
- `repository-change/v1`, `validation/v1`, `work-item/v1` — unchanged.

**Newly minted — exactly one type.**

`review-response/v1`, a **document** (`review-response.json`):

```
{ schema_version: "1.0.0",
  review_digest, candidate_digest,          // what was reviewed
  responded_by, responded_at,               // server-derived from the principal, never the body
  verdict: "accept" | "send-back",
  dispositions: [ { finding_id, disposition: "must-fix" | "waived" | "not-a-defect" | "acknowledged",
                    note? } ],              // sorted by finding_id
  directives:  [ { id, body } ],            // things no finding covered
  examined:    { files: [path], findings: [finding_id] },
  unexamined:  { file_count, files: [path] } }   // computed, not claimed
}
```

**Justification against the parallel-machinery failure mode:** this type has no overlap with `review/v1` — it is the *other party's* value, it cannot be a record (records are unuploadable), and there is no existing human-authored type that can carry a per-finding verdict (`human-answer/v1` is one string; `agent_feedback`'s six verdicts — `accurate | false_positive | noisy | overly_strict | partially_correct | missed_context` — grade the *reviewer*, are read by nothing but a `COUNT(DISTINCT finding_id)`, and are the wrong verbs). It replaces nothing that works; it fills a hole that is empty.

**Control plane:** two nullable columns on `agent_tickets` — `review_response_snapshot_id`, `prior_change_snapshot_id` — plus their clearing rule. Not `repository_snapshot_id`: that stays the immutable *base*, and the prior candidate is a separate input, which is coherent because `repository-change/v1` self-verifies against its base.

## 4. THE HUMAN'S FIRST FIVE MINUTES

Ticket #41, state `needs_review`. Today: two buttons (`AgentTicket.elm:1019-1032`).

**0:00** — The page now leads with a review panel. Header: *"attempt 2 — 6 findings (2 blocking) · 14 files changed · 3 findings carried over from attempt 1."* Carried-over findings are marked because their ids match the prior round.

**0:10** — Left column, findings, sorted by id, cards lifted verbatim from `Build/AgentReview.elm` (severity badge, clamped description with show-more, monospace `file:line` from the first `file-lines` anchor, deep-link anchor per finding). Two blocking findings are open by default; the four observations are folded behind a count.

**0:30** — `f-0010`, blocking: *"`ReserveDispatch` retry swallows `ErrStaleTransition`."* Four buttons under it: **Must fix · Waived · Not a defect · Acknowledged**, plus a note box. He clicks the file link; the right column scrolls to `agent_tickets_factory.go` and expands its per-file patch — **already available**, `repodiff.ChangedFile.Patch` (`agent/repodiff/diff.go:38-48`, sliced at :294-301) lives in the `files` JSONB today; no new diff pipeline. Clicking a file marks it examined.

**1:40** — He hits **Must fix** on `f-0010` and types "surface it as 409, don't retry." **Waived** on `f-0030` ("test padding is fine here"). **Not a defect** on `f-0050` with a one-line reason. The three carried-over findings from attempt 1 show their prior dispositions inline: two he already waived — one click each to re-affirm.

**3:30** — Right column, changed files. Five are checked (he opened them). The footer reads, always visible: **"Examined 5 of 14 changed files. 9 never opened."**

**4:00** — He adds one directive that no finding covered: *"while you're in there, the error string should name the ticket id."*

**4:30** — Three exits, and the confirm dialog restates the receipt verbatim.
- **Accept & close** → writes an `accepted` disposition on the change output via the existing `agent_workflow_outcomes` PUT, materializes the response with `verdict: accept` (the receipt is preserved — "closed with 9 files unexamined" is now a recorded fact, not an ambient one), transitions to `closed`.
- **Send back** → one atomic route (below). Ten seconds later the dispatcher's poll starts attempt 3.
- **Re-queue clean** → today's behavior: discard the response, clear both new columns, start over from base. This button exists so "start over" and "revise this" are two different, honest verbs.

If the run failed and produced no `review/v1`, the panel degrades to the current two buttons plus the directive box and the file list — the response can still be sent back with directives only. **The critique step's output must be declared `optional`** or a malformed finding fails the whole run (`agent_workflow_runs_factory.go:2833-2838`).

## 5. THE LOOP

**Propose.** Human dispatches (`POST /agent/tickets/:id/dispatch` — MemberRole, `agent/dispatch/handler.go:13-19` deliberately has no principal tier: *"an agent must not be able to spend the cluster's budget"*). Dispatch binds base `repository/v1` + `work-item/v1`, plus — if present — `prior_change_snapshot_id` and `review_response_snapshot_id`. Plan: implement → correct → validate → **critique** (new; emits `review/v1`). Run completes. The reconciler writes `running → needs_review`, the only completion edge, however the run ended.

**Review.** Human dispositions findings at rest. **No `await_snapshot`, no 72h timer.** (Correction to two designs: killing the gate frees a *build slot* and unpins the ticket — `await_snapshot` is a web-node step, `atc/exec/await_snapshot_step.go`, not a pod.)

**Revise.** **One route**, `POST /agent/tickets/:id/review-response`, in this order: (1) materialize `review-response/v1` server-side, idempotency-keyed `review-response:<ticket>:<revision>` (Upload auto-pins, `sealer.go:323`, so retention is solved); (2) one transaction — set `review_response_snapshot_id` and `prior_change_snapshot_id`, then `Transition(needs_review → queued)` guarded by the expected `from`, returning `ErrStaleTransition` → 409. Materialize-then-transition, never two PUTs: a 409 leaves an orphaned pinned snapshot (harmless) rather than a ticket carrying feedback for a run that never happens.

**Land.** Accept & close. Disposition stays in `agent_workflow_outcomes`; the ticket stays a queue shell and never re-learns disposition (migration 1773106133's rule).

**Why the agent cannot trigger itself.** Four independent locks. Dispatch is human-tier by construction. Ticket state has exactly one writer (`Store.Transition`) under optimistic concurrency. The response route derives `responded_by` from the authenticated principal, never the body (`agent/api/feedback/handler.go:126-133` pattern), and carries no principal tier. And the pod holds only a broker MCP token — no member credential exists inside a run. A sealed response is inert data; nothing executes it. **Every iteration requires one human click, so the loop terminates by human inaction.**

One correction to carry into the code: `needs_review → queued` bumps `revision` but **does not** increment `attempt_count` (`agent_tickets_factory.go:490-493` increments only when `from == running`). The reservation key `ticket-dispatch/v1/ticket/<id>/attempt/<n>/revision/<r>` is still fresh via `revision`, so a genuinely new run is minted — but do not label rounds by attempt number.

## 6. THE MVP

Ordered. One person plus agents, ~6 focused days.

Mirror `dispatch.go:222-236`'s post-capture assertion so a retried reservation cannot rebind different inputs. | **1 day** |

| 5 | **Prompts.** `critique.md`: stable zero-padded finding ids; reuse an id verbatim when a finding persists; put `resolves:f-XXXX` in `category` for a prior finding you fixed; never re-raise a `waived` or `not-a-defect` finding — restate it as an `observation` with `category: waived` so it stays visible and folds. `implement.md`: `must-fix` dispositions plus `directives` are the mandatory work list; apply the prior candidate's payload before editing. | **0.5 day** |
| 6 | **Elm.** Findings column (reuse `Build/AgentReview.elm` cards + the four-button control), changed-file column with per-file patches from the `files` JSONB and examine checkboxes, the receipt footer, three exits. ~700 lines + the ~15-file wiring tax (`Routes`, `SubPage`, `Message/Effects/Callback`, `Api/Endpoints`). | **2-3 days** |

**Genuinely new content a GitHub PR cannot express:** the **attention receipt** — `examined` / `unexamined`, computed from what the human actually opened, sealed into the response, carried into the next run. GitHub's "viewed" checkbox is ephemeral per-user UI state; a reviewer's silence about a file is indistinguishable from scrutiny of it; approval is a total verdict over a moving head SHA. Here "closed with 9 of 14 files never opened" is permanent data, and the next agent is told explicitly that *unexamined is not approved*. Second: a **typed per-finding disposition that is a machine input to the next attempt**, not prose in a thread.

**Deferred, and why each is safe.**

- **Any new record type.** Safe because `review/v1`'s open `category` set plus markdown carry every vocabulary we might want, reversibly. Minting a registry slot is the one irreversible move; buy it after the behavior proves out, and buy it knowing the vocabulary the corpus actually produced.
- **`review/v1` rev3.** Safe because `RevalidateSealed` runs today's validator over yesterday's bytes — a tightening is a corpus migration, not a revision (`record_schema.go:98-99`). We do not yet know what to freeze.
- **Screenshot / media evidence.** No browser in `deploy/agent-runner/Dockerfile`, no per-entry content endpoint, and an unmade XSS/origin decision about serving agent-authored bytes from the ATC origin. Three separate projects, none of which tests the bet.
- **Agent-declared coverage / residue.** Unverified producer claim, monotonically gameable by listing more paths. The human-side receipt gives the same reader value with nothing to fake.
- **Standing precedent (Case Law).** Its curve needs dozens of tickets over weeks; the MVP window cannot measure it. Also note the trap: `review.go:58-77` forces high/critical findings blocking and forbids `accept` alongside any blocking finding, and `agent/publisher/review_evidence.go:93` gates publication on `conclusion == accept`, so a standing waiver of a high finding would permanently block the publish path.
- **Wiring the new `review/v1` into the publisher's approval evidence.** Explicitly do not. It would couple the review loop to the merge gate before the review loop is trusted.
- **Batch-atomic disposition writes, multi-reviewer conflict, reviewer assignment, forge projection.** n=1 does not race itself.

## 7. THE EXPERIMENT

Run it on ~12 real tickets, ~2-3 weeks. Three numbers, all derivable from sealed records plus two click instrumentations.

**The tell — targeted convergence.** For every `send-back`, does attempt N+1's `review/v1` carry `resolves:<id>` for each `must-fix` id, *and* does its changed-file set overlap attempt N's by more than half? Both are computable: the first from the finding `category` set, the second by diffing `agent_repository_change_projections.files` across the two runs. **Target: ≥70% of `must-fix` dispositions resolved on the next attempt, with ≥50% file-set overlap.** Overlap is the carry-forward check — if attempt N+1 rewrites everything, the port is bound but the prompt is not honoring it, and every richer design would fail the same way.

**The second tell — attention.** Track `examined.files / changed_files` per round and the send-back rate per ticket. The win looks like: examined fraction *falls* while send-back rate holds flat and nothing defective reaches `main`. That is findings doing the reading.

**What falsifies it.**
1. **The owner opens the raw diff before dispositioning any finding.** Instrument one thing: whether the first interaction on the page is a file expand or a disposition click. If it is consistently the diff, the findings are not carrying the review and the whole agentic-review premise for this size of change is wrong.
2. **`must-fix` resolution below ~50%, or file-set overlap below ~30%.** The channel exists and does not work. Fix the prompt once; if it still fails, the directive channel is weaker than editing the ticket body and the object is overhead.
3. **Waiver rate above ~60%.** The critique step is generating noise, and the loop is carrying garbage forward at full token cost.
4. **Examined fraction falls *and* defects reach `main`.** The receipt is legitimizing rubber-stamping rather than exposing it. This is the one failure the MVP is specifically instrumented to catch, and it is the reason the receipt is in the MVP rather than deferred.

Any of 1-4 → **do not mint a record type.** The cost of being wrong is one document type, two columns, one dispatch clause, and an Elm page — all of which the carry-forward fix and the record-read endpoint justify on their own.

## 8. THE BEST IDEAS NOT IN THE MVP

1. **Candidate → `repository/v1` materialization function.** Unblocks a shadow-review control arm (`code-review-v3` takes two `repository/v1`s and nothing in-tree materializes one from a change) and a "what changed since I last looked" round-to-round diff. *Trigger:* the first time the owner wants to re-review only the delta, or wants an independent second opinion on a change the loop green-lit.
2. **Explicit reading order.** Not the id-sort trick — a real `order` int or top-level `sequence[]`, because id must stay stable identity. *Trigger:* reviews routinely exceed ~10 findings.
3. **Budget refusal — `unreviewable: split it` as sealed data** (from Attention Docket). The one claim the producing agent is uniquely positioned to make and no forge can represent. *Trigger:* the first change the owner cannot review in one sitting.
4. **Attested citation:** `json-pointer` anchors from findings into sealed `validation/v1` bodies, plus a validation read route. Turns "the tests pass" from agent prose into a link to an attested attempt (`validation/v1` rev3 pins candidate digest, profile digest, capability image digest, toolchain — and seal admission byte-matches them against server-declared authority). *Trigger:* the owner asks "did it actually run the tests?" twice.
5. **Verified coverage.** An agent-declared vouching set validated *at seal* against the change's real file list — precedented, because `repository_change.go:91-296` already materializes the base and verifies the change. This is the honest version of residue. *Trigger:* examined fraction stops falling.
6. **Standing rulings (Case Law).** Waive once, waived everywhere, captured at dispatch like `work-item/v1`. The strongest long-horizon idea on the table — review cost per attempt genuinely declining — but its period is longer than the MVP's window, and it must first answer the `conclusion`/blocking/publication interaction above. *Trigger:* the same waived class appears in three tickets.
7. **`review-response/v1` promoted from document to record**, with subjects binding it to exact digests. *Trigger:* a second human reviewer, at which point provenance stops being decorative.
8. **Seal-before-implement as an ordering witness** (from Warrant & Drift). Lineage proving X was decided before Y — a real, general, forge-impossible platform primitive, worth adopting well outside review. *Trigger:* the first dispute about whether a plan preceded the code.
9. **The meta-verdict** (from Docent): let a human reject an agent's *framing* without rejecting the work. Generalizes to plans, summaries, question phrasing. *Trigger:* the owner finds himself waiving every finding because the critique attacked the wrong layer.
10. **Media evidence + browser sidecar.** The image side is already solved — `opaque/v1` accepts any tree, canonicalization is byte-exact, the ceiling is 10 GiB — but *capture* needs a pinned sidecar image and *display* needs a per-entry content endpoint with a media-type allowlist and origin isolation. *Trigger:* a UI bug the loop cannot prove fixed.
