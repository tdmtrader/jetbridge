Internal platform guide

JetBridge / orientation & architecture

A Kubernetes-native backend and an agentic workflow platform, both grafted onto stock Concourse. This assumes you already know Concourse well — it covers what's different, why it's shaped this way, and what to know before you operate, deploy, or extend it.

lives on jetbridge grounded in a direct code audit, not the existing docs

JetBridge started from a simple itch: Concourse tasks already look like functions — inputs in, outputs out — so a Kubernetes-native backend seemed like a natural rewrite, and that same function shape looked like a good fit for agentic CI. Everything in the fork is agentically coded: the author specified outcomes, not implementations, and treated it as an open question how far that could go.

The fork adds two things to stock Concourse: a Kubernetes-native execution backend, and an agentic workflow platform on top of it — durable GCS-backed snapshot storage ("Hangar"), a sandboxed agent execution broker for synchronous sub-agent calls, a crash-recovery/checkpoint layer, and outbound publication (direct-Git today, a gated provider-native pull-request lane alongside it) driven by credentials mounted directly into ATC. Some of these subsystems are fully implemented, wired, and covered by tests, but self-declared not safe for production by their own first-party docs — this guide is direct about which is which. Orientation

What JetBridge is

Two additions sit on top of stock Concourse, built in sequence and now deeply intertwined.

Phase 1 replaces the worker/Garden/TSA/BaggageClaim stack with direct execution against the Kubernetes API: the web node talks to the cluster itself, and every step — task, check, get, put — becomes a pod. There is no concourse worker binary anymore.

Phase 2 builds an agentic workflow platform on top of that runtime: AI coding agents (and a few deterministic compute functions) run as typed, versioned workflow definitions — informally "workflow functions," since each has a typed input/output signature like a function call — over immutable, content-addressed inputs and outputs called snapshots. A ticket queue feeds work in; a durable run engine tracks execution independent of the disposable Concourse machinery that carries it out. One thing worth internalizing up front: an agent: node's output is stochastic — the same inputs can produce a different diff, review, or answer on a different run. Nothing downstream treats an agent's output as trustworthy just because the step exited zero; that's why validation, review, and human approval are load-bearing rather than decorative, and it's why an entire experiments subsystem exists — you can't unit-test a stochastic step the way you'd unit-test a deterministic one, only measure it statistically across repeated trials.

If a Concourse task is already a pure function — inputs in, outputs out — phase 2 just makes that literal for agents: a typed signature, a pinned version, immutable values on both sides.

That last divergence is also the deepest one, and it's worth naming directly rather than leaving implicit. Stock Concourse is fundamentally convergent: a fixed set of inputs, checked and re-checked, reduces deterministically to the same container image or deployment every time you run it. The agentic side is fundamentally generative: a snapshot of some state gets rendered, stochastically, into a candidate diff, review, or PR that has to earn its way to being trusted rather than being trusted by construction. That inversion is the reason the platform has machinery a plain deterministic pipeline wouldn't need — independent re-verification before promotion (a run isn't "done" just because the build exited zero, see Durable workflow runs), a human-approval gate a workflow author structurally cannot forge (Human approval & publishing), and a whole experiments subsystem for statistically comparing stochastic output across repeated trials (Experiments). None of it is ceremony for its own sake — it's what a generative step needs that a deterministic one doesn't.

The two phases share one execution backend. An agent: step and a plain task: step both come down to a pod scheduled by the same K8s-native runtime — the "agentic platform" is a control-plane layer (definitions, snapshots, runs, dispatch, approval, publication) sitting on top of ordinary pod-per-step execution, not a second runtime.

Phase 1

The Kubernetes-native runtime

Pod-per-step execution, a mandatory node-local artifact cache with an optional durable backing store, and everything a `kubectl` reflex needs to keep working.

Pod-per-step, no workers

The web node registers itself as a synthetic worker named k8s-<namespace>, written directly into the database rather than negotiated over an SSH/TSA tunnel, and heartbeats it every 15 seconds against a 30-second TTL. Every step — task, check, get, put — becomes one pod, named deterministically from pipeline metadata and labelled with concourse.ci/pipeline, concourse.ci/job, concourse.ci/build, and concourse.ci/step for easy kubectl filtering. Pods idle on a pause loop so the web node can exec the real command via the Kubernetes exec API — this is what gives full stdin/stdout/stderr separation and makes fly intercept work: it execs a new shell into the same still-running pause pod. Container lookup (the path both fly intercept and fly hijack go through) resolves the pod through the same GeneratePodName function the step used to create it, keyed off the DB row's real metadata, so it locates the actual pod rather than a metadata-less fallback name; a looked-up container is marked so it can only attach to a pod a step already created, never fabricate or replace one — replacing a pod that has already exited would destroy the exit-status annotation described in Garbage collection below.

A small in-pod shell supervisor wraps every task/agent command specifically so a build survives a web restart: if the web pod dies mid-step, the exec session's pty closes and the child gets SIGHUP, but the supervisor keeps the real process running and a freshly-reconnecting web replays the log from the start and waits for the exit file, rather than restarting the command from scratch. This is real, load-bearing crash safety that predates and is independent of the newer checkpoint/recovery feature described in Checkpoint & crash recovery — though that section also covers a real gotcha where checkpoint-enabled steps opt out of it.

The artifact daemon Live · mandatory

A DaemonSet — one pod per node — runs a small HTTP server over node-local storage and acts as the artifact cache for the whole cluster. It is not optional; the web node refuses to start the Kubernetes runtime at all without it configured (--kubernetes-artifact-daemon-host-path).

For ordinary pipeline artifacts (task/check/get/put outputs), the daemon holds content independently of any producing pod, so a downstream step's input fetch never depends on an upstream pod still existing, and content is peer-mirrored to a configurable number of nodes after every write — no cluster-wide read-write-many storage class is required.

For agentic snapshots and checkpoint archives, the daemon's local disk is a node-local, on-use cache, not the durable authority. The daemon reserves a separate snapshots/ key namespace with its own handlers — snapshot PUT/GET/DELETE never triggers the ordinary peer-mirror path at all — and, if configured, backs that namespace with Hangar, a durable, provider-neutral (GCS-backed today) object store.

Hangar: what it actually solves

Hangar exists because node-local-plus-peer-mirror is not durable enough for content you can never afford to lose — a sealed snapshot, or a checkpoint archive that's the only copy of an interrupted agent's workspace. Object identity is the SHA-256 of the uncompressed canonical content, stored zstd-compressed under a deterministic key (hangar/v1/<kind>/sha256/<digest>.tar.zst). Writes are create-only (a GCS conditional write that only succeeds if nothing exists at that key yet); a write that loses the race re-verifies the winning object is bit-identical rather than erroring, so retrying the same content is always safe. Every read and delete is generation-pinned — scoped to one exact GCS object version, with a second read-back check to catch a concurrent mutation mid-verification — so an "immutable" object can't be silently swapped out from under a reader. The daemon verifies restored bytes against the requested digest a second time on its own side before trusting Hangar's response. An omitted zstd compression level defaults to the encoder's standard level rather than failing the daemon's startup probe.

The non-production GCS emulator has two failure modes worth knowing before relying on it

--hangar-gcs-endpoint (daemon) exists for a non-production integration environment — pointing it at fake-gcs-server or similar — but docs/operations/hangar.md documents two ways that emulator silently loses data that a real GCS bucket does not. It holds an object entirely in memory while writing it, so a snapshot larger than the container's memory limit OOMKills the emulator mid-upload; the write then fails with no replica acknowledgements, which reads as a daemon problem rather than an undersized emulator, and small captures are unaffected, which is why it looks size-dependent rather than broken. Its filesystem backend also persists object content but keeps custom metadata in memory only, so every emulator restart returns intact bytes with empty metadata, and every read then fails validateStoredMetadata's exact three-key vocabulary check. The agent_snapshot_repair component heals that automatically once the content proves itself against its own digest; hack/hangar-repair-metadata.py is a dry-run-by-default manual fallback for a build that predates the automatic repair, or to recover without waiting for a tick.

Enabling it is a chart-enforced pairing — agentSnapshots.enabled: true requires artifactDaemon.hangar.bucket, or the Helm render fails outright:

agentSnapshots: enabled: true artifactDaemon: serviceAccount: annotations: iam.gke.io/gcp-service-account: concourse-hangar@project.iam.gserviceaccount.com # workload identity — never mount a static key hangar: bucket: concourse-agent-snapshots networkPolicy: enabled: true hangarEgressTo: - ipBlock: {cidr: 198.51.100.32/32} # operator-specific GCS Private Service Connect address

Orphan reclamation exists: the agent_snapshot_orphan_sweep component runs Lifecycle.SweepOrphans (agent/snapshot/orphan_sweep.go), which lists Hangar's bucket directly via the store's list call — the only authority that can see an object no database row references — and reclaims (or, in report mode, only logs) any digest with no snapshot row, no staged upload, and no location row referencing it anywhere, gated by a minimum age (--agent-snapshot-orphan-sweep-age, default 24h, floor 1h) and a generation-pinned delete so a concurrent re-upload of the same digest can't be destroyed. It ships Gated: --agent-snapshot-orphan-sweep-mode defaults to off, so an operator opts in twice — once to run the pass at all, in report mode, to see a real inventory before authorizing deletion, and again to let it actually reclaim. This is the backstop for content a failed upload, a crashed sealer, or any other path leaves durable but unreferenced: every delete request to the daemon specifies durable-vs-cache-only scope explicitly rather than having it inferred, so a digest whose staged row is dropped after a failed upload stays reachable through the sweep instead of becoming permanently unreachable. hangarEgressTo remains a genuine gap: it is only enforced when the operator also turns on artifactDaemon.networkPolicy.enabled, so leaving that off (the default) means Hangar egress is unrestricted by design, with no "hardened profile" that forces it.

Garbage collection

A reaper component runs on the default 10-second component-polling interval (it has no dedicated flag of its own) and deletes pods the database has marked for destruction. It also proactively deletes any pod carrying the concourse.ci/exit-status annotation, ahead of the full DB GC cycle — but only once the pod's owning build, read from its concourse.ci/build-id label, is no longer running; pods with no build-id label (in-memory check builds and the resource-type get/put steps they spawn) have no build to resume and always take the fast unconditional path. That distinction is load-bearing: the annotation is the only record of a step's result that survives a web restart — engineBuild.Run deliberately leaves job builds "started" on drain so the next web re-attaches, and Container.Attach reads the annotation to skip a step the resumed plan would otherwise re-execute. When the running-build set can't be read, the split fails closed and retains the pod rather than risk a lingering annotation. Artifact cleanup is an HTTP delete against the owning node's daemon rather than an exec-based rm inside a live pod. A single artifactLocator() accessor supplies the same ArtifactLocator instance to both the worker pool and the Reaper, so the writes a step's containers record and the reads GC performs operate on one shared map instead of two independent ones. LocateStep finds a step's entries through the recorded HostDir (<container handle>/<output name>) rather than a bare-handle lookup, since entries are keyed by volume handle (<container handle>-output-result, …) while GC hands the Reaper bare container handles.

Security posture & RBAC

The web pod's namespaced role covers the obvious pod lifecycle permissions (get/list/watch/create/update/patch/delete on pods, pod exec, and pod logs), plus several things worth knowing about explicitly: it can create and delete secrets (used for per-run agent credentials, described in Execution, budget & credentials), read EndpointSlices (used to resolve other artifact-daemon pods for cross-node artifact routing), and patch both Deployments (its own, for the worker-registrar heartbeat) and DaemonSets (so a self-upgrade rollout check on the artifact-daemon doesn't hang). A separate cluster-scoped role grants read-only access to secrets and nodes, used for cross-namespace credential resolution and artifact-daemon peer IP lookup. The chart disables ambient service-account token automount on the web pod and instead projects a bounded, roughly one-hour API token, CA, and namespace directly into the web container — init containers never receive that credential at all.

Phase 2

How a change gets made

Every agentic execution — a ticket, a manual run, a retry, an experiment cell — moves through the same six-stage shape. The sections that follow work through these same stages in roughly the same order, though a few — Bind & admit spans Durable workflow runs and Tickets & dispatch; Render & execute spans Workflow definitions and Execution — each cover more than one stage, so don't expect a section titled exactly after a stage name.

Six stages sounds like a lot, but in practice a human only ever touches two of them directly: you capture whatever inputs the change needs (or a ticket, or a declared resource source, does it for you), and — if the workflow declares one — you resolve a publish approval at the end. Bind, render, seal, and promote all happen automatically once a run is admitted. Mapped onto the get/task/put comparison above: capturing a repo's current commit as a snapshot is the get; the workflow's nodes running end to end and sealing their outputs is the task (repeated, chained, however many nodes the definition declares); and — only if the workflow author bothered to declare it, and only through a lane that isn't gated closed — an approved, published change is the put.

  1. 1
    Capture

    Live or mutable state — a pipeline resource version, a ticket's current text — is sealed into an immutable, typed snapshot. This is the only door from the outside world into the agentic platform; nothing downstream ever reads a live system directly.

  2. 2
    Bind & admit

    A durable workflow run is created, binding exact snapshot IDs to a pinned, promoted workflow definition version via an opaque, tamper-evident launch envelope. One admission engine handles every origin — manual, ticket dispatch, retry, experiment cell, automatic resource-source trigger — so they all get the same guarantees.

  3. 3
    Render & execute

    The definition renders into an ordinary one-shot Concourse pipeline. Every declared node — a deterministic task: or an LLM agent: — runs as its own pod, using the same K8s-native execution described above.

  4. 4
    Seal

    Each node's output is captured, content-addressed, validated against its type, and sealed as a new snapshot the moment its producing node finishes — not when the whole run finishes, and not only for outputs the definition declares publicly.

  5. 5
    Promote

    Only once the entire run succeeds — re-verified against durable evidence, not just trusted from the build's exit code — do its declared outputs become the run's public, durable result set. A failed or partial run leaves its intermediates invisible forever, even though the bytes still exist.

  6. 6
    Publish (optional)

    A workflow that declares a publish_snapshot node — gated by a durable human-approval wait — hands its result off for delivery to a real git host. Most workflows stop at step 5.

A quick-reference glossary before the deep dive:

Snapshot
An immutable, typed, content-addressed value. The only unit of data that crosses a workflow's typed boundaries.
Workflow definition
A versioned, typed function signature plus a Concourse DAG that implements it. Imported, then promoted to "live."
Reusable node
A separately versioned, single-step function a workflow can compose in by reference — a shared library of typed functions.
Durable workflow run
The crash-survivable execution identity for one invocation — outlives the disposable build that carries it out.
Ticket
A mutable work-item queue entry. Not an execution identity — it dispatches into a durable run and stays a thin projection shell.
Dispatch
The act of turning a queued ticket into a bound, admitted workflow run. Manual always works; auto-dispatch is a runtime toggle.
Publish
The one side-effecting primitive. Direct-Git works today; the newer provider-native PR lane is implemented but gated off.
Experiment
A/B comparison of workflow (or single-node) variants against pinned fixtures, using the exact same run engine with an extra admission gate.

"Admission" does double duty below — at promotion time it means passing the compiler's type-checking proof (a workflow definition is "admitted" into the live/promoted state); at run time it means passing the durable-run engine's binding and budget checks (an invocation is "admitted" into a run). Same word, two different gates on two different objects at two different times.

Phase 2

Snapshots

The immutable, typed value that everything else in the agentic platform is built around — think of it as an extension of the resource-version idea you already know, not a new concept from scratch.

If you already know Concourse resources, start from what's the same: like a resource version, a snapshot is a specific, immutable, pinned "version" of some content that a step declares as an input or output, and that you can reference by an exact ID later. A workflow's repository input and an ordinary pipeline's source resource are conceptually the same kind of thing — a versioned view of a git repo at some commit. Now the differences, which matter more than the similarity: a resource version is usually a lightweight pointer at external state, fetched by a check loop the pipeline itself runs. A snapshot is the opposite — the platform actually stores the content, content-addressed by its own digest, and it's sealed once by an explicit act (see "Resource capture" below) rather than continuously re-checked. Once sealed, a snapshot never changes and is never re-fetched.

A snapshot is a typed, content-addressed blob — its identity is really a (type, digest) pair, where the digest is a hash of the canonicalized content rather than the raw upload, so semantically identical output converges on one digest no matter how the producer happened to write it. Sealing a duplicate is cheap: if a verified copy of that exact digest already exists, it's reused and nothing is re-uploaded. Concurrent producers of the same content are serialized so two racing steps can't corrupt shared storage.

Storage rides the node-local artifact-daemon fleet described in the runtime section, under its own reserved key namespace and mandatory TLS — snapshot bytes never cross the cluster network unauthenticated — with an opt-in durable Hangar/GCS backing store behind it. Because a snapshot commit only answers after the archive is read, digest-verified, linked into the daemon's immutable namespace, and durably committed, the upload transport carries no response-header deadline; it is instead bounded by an accept check (the daemon must answer 100 Continue) and an in-flight stall guard that requires bytes to keep leaving the client (atc/worker/jetbridge/snapshot_upload_guard.go). The snapshot read path keeps its own real handshake bound, since a read answers before doing its work.

The non-production GCS emulator loses metadata on restart; repair recomputes it

When Hangar's bucket is backed by fake-gcs-server — the GCS-compatible emulator --hangar-gcs-endpoint selects for a non-production integration environment, see the runtime section — its filesystem backend persists object bytes to disk but keeps custom metadata in memory only, so a pod restart empties every object's metadata and any read against it fails closed. Real production GCS persists metadata durably and isn't exposed to this. agent/hangar/gcs.go can re-derive and rewrite an object's metadata, but only after independently recomputing its SHA-256 from the decompressed bytes and confirming it matches the digest already embedded in the object's key — repair asserts nothing the content hasn't already proven, and an object that fails the check is reported and left untouched. The exact vocabulary repair may restore is three keys: representation, uncompressed SHA-256, and uncompressed byte count. docs/operations/hangar.md also documents a standalone hack/hangar-repair-metadata.py script as a manual alternative.

The type registry is fixed, not configurable — 20 types today

Every snapshot type is a compiled-in Go validator, built identically into both the web binary and the standalone function-runner binary. There is no runtime or configuration path that registers a new type; adding one is still a code change and a coordinated redeploy of both binaries. The current, exact, full list of 20:

opaque/v1 repository/v1 repository-change/v1 review/v1 work-item/v1 log-bundle/v1 measurements/v1 validation/v1 upgrade-request/v1 upgrade-report/v1 database-snapshot/v1 deployment-snapshot/v1 audit-findings/v1 diagnosis/v1 consultation/v1 question/v1 human-answer/v1 pull-request/v1 pull-request-response/v1 publish-impact/v1

consultation/v1, pull-request/v1, pull-request-response/v1, and publish-impact/v1 exist for the agent-broker and PR-publishing work below. There is no selection/v1 type: its one load-bearing role, the candidate subject, lives directly on measurements/v1.

Sealed records: one validation core for nine types Live

Nine of the twenty types — review/v1, diagnosis/v1, validation/v1, repository-change/v1, measurements/v1, consultation/v1, pull-request/v1, pull-request-response/v1, and publish-impact/v1 — share a common envelope (a record version, type, schema reference, subject list, and body) and a two-layer validator: a generic, JSON-schema-driven core checks structural shape before a much smaller hand-written Go layer checks type-specific business rules. This is the validation engine for these nine record-shaped types — it doesn't touch the registration model above.

Evolving one of these types' shape appends a new schema-digest revision rather than editing in place: the previous revision is retained as superseded; reads accept either digest; a fresh seal only accepts the current one. This two-gate split exists because a single exact digest checked everywhere — including on read — would turn a schema bump into a silent data-loss event, failing every already-sealed record's re-validation instead of treating it as "an older but still valid version."

validation/v1 is on revision 3

Revision 3 requires a body.attestation block — the candidate digest, base inputs, the validation profile's digest, the pinned capability image and its digest, the workflow definition ID/version, and the toolchain string. This attestation is compiled by the server, not asserted by the agent: it's derived from a workflow's pinned dev_validation profile at admission time and hashed into a provenance value; a sealed rev3 record's attestation fields must match that server-held authority byte-for-byte, or the seal is refused. Revision 3 also requires every per-check log to be independently reopened and re-hashed against its declared digest and size at seal time. Rev2 records stay readable — they're simply never asked to produce an attestation or logs they never had; a rev3 record must have both.

Validation failures disclose a closed reason, not just pass/fail

Every rejection from the archive canonicalizer and from the shared record/tree contract core carries one of a closed, compile-time set of reasons — ValidationFailureReason in agent/snapshot/validator.go — instead of an opaque, undifferentiated failure. Eleven reasons cover archive-level rejections (a non-canonical or too-long path, a duplicate entry, an unsupported entry type or metadata, a symlink escaping the archive root, an unreadable tar stream, and so on); nineteen cover the record/tree contract core shared by the nine record-shaped types (a missing or malformed document, an invalid envelope, a field outside its declared shape or its allowed values, a duplicate or unsorted entity id, an anchor that doesn't resolve, an inconsistent conclusion or blocking flag, missing evidence, non-contiguous ranks). Only the fixed reason string reaches the caller, plus — for archive rejections only — the sanitized, 256-byte-bounded name of the offending entry (PublicValidationFailure.Entry()); the full underlying cause is retained exclusively for structured server logging, never republished.

Record uploads over HTTP cannot seal today Gap

BatchSealer.Upload (agent/snapshot/sealer.go) builds its ValidationContext as NewValidationContext(nil, nil) for every uploaded type — no declared inputs, no input opener. Every one of the nine record types requires at least one subject, and Record.RebindSubjectsToExposedInputs (agent/snapshot/contracts/record.go) rejects any subject whose named input isn't present in that context before the type-specific body is ever examined. The practical effect: uploading a review/v1 — or any of the other eight record types — through the HTTP upload endpoint always fails at subject rebinding with reason record_subjects_invalid, regardless of what the uploaded document actually contains; the disclosed reason above makes the failure legible, but doesn't make it succeed. Non-record types (opaque/v1, repository/v1, and the rest that don't compose the record contract) are unaffected, since they never call into subject rebinding. The upload path has no mechanism today for supplying the declared inputs a record upload's subjects would need to rebind against.

Resource capture: the only door for live data

Because typed workflow nodes reject get, put, load_var, and top-level resources outright, there has to be some sanctioned way to pull an existing pipeline resource version into the typed world. That's resource capture: given an exact, already-known (team, pipeline, resource, version), the web node runs a small one-shot pipeline that fetches it and seals the result as a typed snapshot — reusing the same sealing path any workflow output goes through, so captured content gets identical validation and dedup. It's idempotent by a content-addressed operation key, so repeating the same capture call is safe.

A server-minted authority scopes the capture task's input waiver

A capture task's shape — one ordinary source input, zero typed inputs, one typed output — needs an exception from the exact-artifact-coverage check atc/exec/task_step.go's validateSnapshotDeclarations runs on every task with a typed port. That exception is atc.ResourceCaptureAuthority (atc/resource_capture.go): a server-minted waiver honored only when it is bound to the authenticated capture template that owns the build's pipeline run (via agent_workflow_run_templates, checked in TaskStep.authorizeResourceCapture) — not to the task's own FunctionID, which is ordinary source-authorable configuration and is not a trust anchor. The waiver covers exactly the capture task's one untyped input; output coverage, the typed-snapshot smuggling guard on ordinary inputs, and agent-step tasks are all unaffected. Pipeline-run instances materialized from a registered capture template are treated as server-owned for ordinary config writes and public manual/rerun execution, so a team config writer cannot resubmit a capture authority against substituted inputs.

The one-shot pipeline's own name is agent-resource-capture-<24-hex-op-key-prefix>-<12-hex-config-hash> (atc.ResourceCaptureTemplatePrefix, built in agent/resourcecapture/capture.go's newTemplateSpec), where the hash segment is workflow.TargetConfigHash of the rendered capture task config. Because that hash is part of the template's identity, any change to the capture task's own shape mints a new template name rather than reusing the old one.

A declared resource_sources: input on a workflow definition (see Durable workflow runs & resource-source admission) reuses this exact same capture machinery under the hood, just triggered automatically by a standing pipeline instead of a manual CLI call.

Authoring/derivation packages worth knowing about

Two packages are infrastructure for how outputs actually get produced and reasoned about, not optional add-ons:

  • The managed output builder

    A fixed, non-authoritative authoring surface an agent pod uses to stage and preflight a typed output before the step ends — it reopens and re-hashes its own inputs against server-declared digests, stages writes atomically with rollback on any failure, and structurally cannot seal anything itself. The real seal always happens later, independently, when ATC reopens and re-validates the produced tree after the pod has exited. This is a hard trust-boundary split: the in-pod tool gives an agent fast local feedback on its own mistakes; only ATC's own independent re-validation can actually mint a snapshot.

  • Deterministic offline repository diffing

    Derives repository-change projections (the file list, +added/-removed counts, the unified diff the web UI renders) from already-local immutable Git objects only — it never resolves a remote and never fetches. This is what actually powers the in-app diff viewer described in The operator surface today.

Phase 2

Workflow definitions

A versioned function signature, compiled from a directory of prompt/skill/config files into an ordinary Concourse DAG — plus a type-checker that treats admission as a proof obligation, not a lint pass.

Source, import, and promotion

A workflow's source is a directory: a workflow.yaml plus whatever prompt, system-prompt, context, and skill files it references. workflow.yaml is the preferred filename; the legacy workflow.yml still works, but if a directory somehow has both, .yaml wins outright and the .yml content is never even consulted. Every seed workflow in the repo uses .yaml. fly agent workflows import packages that directory and compiles it — resolving file references into literal content, expanding any declared capabilities and broker profiles into sidecars (below), and marking every node hermetic. Import is deliberately permissive: it only has to compile and type-check, so an author can inspect a draft that couldn't actually run yet. Promotion is strict: --set-live additionally fully renders the definition, re-validates every runtime dependency is immutable (no file-backed task configs, no unresolved variables), and only then can a version become live — the promotion transaction itself refuses any target whose schema version isn't exactly 3, so a pre-v3 definition can never become live.

Here's what's actually inside that directory — trimmed from the real version-upgrade-v3 seed (its full plan has four more nodes; see the worked example for the whole thing):

# agent/workflow/seeds/version-upgrade-v3/workflow.yaml schema_version: 3 name: version-upgrade signature_version: 1 disposition_output: change inputs: - {name: repository, type: repository/v1} - {name: request, type: upgrade-request/v1} outputs: - {name: change, type: repository-change/v1, from: candidate} # must match an output name below - {name: report, type: upgrade-report/v1, from: report} plan: - agent: upgrade function_id: upgrade # stable identity — addressable for extraction / experiments prompt_file: prompts/upgrade.md inputs: [repository, request] outputs: [draft, report] input_types: {repository: {type: repository/v1}, request: {type: upgrade-request/v1}} output_types: {draft: repository-change/v1, report: upgrade-report/v1} # ...review, validate, prepare-question, await_snapshot follow
fly -t TARGET agent workflows import agent/workflow/seeds/version-upgrade-v3 --set-live

Two things to notice against the get/task/put comparison in the overview: inputs/outputs at the top are the workflow's own typed signature (what a caller binds snapshot IDs to, and what gets promoted on success) — everything under plan is the actual Concourse-shaped DAG that computes them, node by node, exactly like a pipeline's plan:. function_id is what makes a node individually addressable later (see Experiments) — it has to be stable and unique within the definition, but otherwise means nothing to the compiler.

Typed nodes are the whole admission model

Every task: or agent: step in a workflow is a "typed node": it declares a stable, unique function_id and must have exact type coverage between its artifacts and its declared input/output types. The compiler's type-checker walks the entire DAG — through do, in_parallel, try, retries, timeouts, hooks, everything — proving that snapshot data actually flows the way the signature claims, and it rejects, structurally, anything that would break that proof: top-level resources or variable sources, get, load_var, put, set_pipeline, and across (rejected specifically because it mints new runtime plan IDs after admission, which would break exact frozen provenance). A prototype run: step gets its own explicit, purpose-built rejection message rather than falling through to a generic error, for the same underlying reason — Concourse plans a prototype run without a resolvable source identity, which can't meet the frozen-provenance bar either. There's no untyped island possible in an admitted v3 workflow — it's proven, not just conventionally true.

Under the hood this reuses Concourse's own machinery rather than inventing a parallel runtime: promotion compiles a definition into a content-hash-named, one-shot Concourse pipeline template — identical content always reuses the identical template rather than minting a new one every single admission. "Workflow" is a control-plane concept layered on ordinary pipelines, not a separate execution engine.

Capability sidecars & hermetic execution

A workflow grants an agent tool access by declaring a named capability — an exact-digest-pinned container image plus one TCP port. The compiler expands each declared capability into a real sidecar and a generated <NAME>_MCP_URL environment variable; an author cannot author their own MCP endpoint, inject a sidecar directly, or reuse a reserved name (dev, platform, gateway — retired privileged runtime roles) to smuggle in undeclared access. Every task and agent node is unconditionally hermetic — deny-egress network policy applied at compile time, not something an author can opt out of.

That raises an obvious question: if egress is denied, how does an agent: node ever reach Anthropic's API? Two exceptions exist, and only one of them is automatic. The platform itself carves out the same-node path to the local artifact daemon, which is what lets a hermetic pod fetch its own inputs — that one requires no configuration. Reaching any external HTTPS endpoint, including the model provider, is not automatic: the chart's hermetic-egress policy is emitted with a hard-deny (egress: []) unless an operator explicitly sets networkPolicy.hermeticEgressTo. The documented pattern is to point that at a single in-cluster egress proxy rather than opening a raw internet-wide allow-list from every hermetic pod. Whether this is enforced in practice depends on the cluster's CNI actually implementing NetworkPolicy; on a CNI that doesn't, the object is created but has no effect. Skipping this configuration on a policy-enforcing CNI doesn't break something subtly — it means no agent step can call the model at all.

A second, independent tool-access mechanism: broker profiles

An agent node has a second way to get extra capability: declaring a broker_profiles: entry, which lets it synchronously call out to a completely separate, sandboxed child agent for a static review or a bounded consult. This is a materially different mechanism from a capability sidecar, not a variant of it:

plan: - agent: implement function_id: implement prompt: implement broker_profiles: - {tool: consult_agent, tier: balanced, effort: high} - agent: review function_id: review prompt: review broker_profiles: - {tool: request_review, tier: frontier, effort: medium}

An author supplies only a neutral {tool, tier, effort} selector — never an image, model, or provider. Those get resolved server-side, at compile time, against an operator-only deployment catalog; if no catalog is configured, compiling a definition with any broker_profiles fails outright with an error naming the missing catalog (workflow: broker catalog is required to compile "<name>"). The resolved profile (model, provider, harness, worker image, credential slot) is frozen by content hash into the compiled definition, so a later catalog edit can never silently change what an already-promoted workflow does. See Agent execution broker for the full mechanism, including a real, self-declared reason not to turn this on in production yet. There are no seed workflows using broker_profiles in the repo today — it's fully implemented and compiler-tested, but with zero first-party worked examples.

Worth knowing
  • A single top-level task or agent node can be extracted out of its parent workflow into its own standalone, independently renderable target, addressed as workflow@version#function_id. This isn't a curiosity — it's exactly how you iterate on one step of a chain without re-running everything upstream of it: pin an earlier node's output snapshot as an experiment fixture, then compare two extracted versions of a downstream node against that same fixture. See Experiments. This is a genuinely different mechanism from reusable nodes below — extraction pulls a leaf back out of an already-compiled workflow with no prior declaration required; a reusable node is composed into one or more workflows and has its own independent, versioned identity. Both are real and coexist.
  • Two step-level keys from the pre-v3 grammar, gate_policy and judge, still fail to compile if an author writes them on a step — but there's no bespoke shape-checker for either; it's the same generic strict-unknown-field rejection every other unrecognized key gets.
  • A disposition_output field is compiled and validated, and five of the eight seed workflows author it, but nothing in the live dispatch or ticket code reads it yet.
Phase 2

Reusable nodes Live

An immutable, independently versioned single-step function that workflows can compose by exact reference.

A reusable node packages one typed task, agent, or publish_snapshot leaf with its prompts and assets. Create or capture exact typed input snapshots, import the package and retain the exact returned version, then run that unreleased version through the ordinary durable admission engine. Inspect show-run, follow its exact fly watch -b build hint, download and inspect the sealed typed output, and only then release the tested version.

Released nodes compose into workflows as uses: NAME@EXACT-INTEGER; there is no latest channel. Consumer discovery and explicit upgrades create new unpromoted workflow revisions without rewriting existing definitions or historical runs. See the reusable-node operations guide for the runnable lifecycle, portability and budget rules, release compatibility, and upgrade procedure.

show-run has no node-scoped metrics or transcript route

A node run shares the same durable run table and ID space as a workflow run, but the observability API does not follow it there. /api/v1/agent/workflows/:workflow_name/runs/:workflow_run_id/metrics and its /transcripts sibling (ListAgentWorkflowRunMetrics, ListAgentWorkflowRunTranscripts in atc/routes.go) are registered only under /agent/workflows/; there is no analogous route under /agent/nodes/. fly agent nodes show-run reuses the same workflowrunsapi.RunDetail struct (agent/api/workflowruns/types.go) a workflow run gets — it carries a planned_build_id but no agent-metrics event count or flight-artifact handle. The only working path to a node run's agent metrics is to read planned_build_id off show-run and call the generic, build-scoped /api/v1/builds/:build_id/agent-metrics route (ListBuildAgentRunMetrics) by hand; there is no equivalent workaround for transcripts.

Phase 2

Durable workflow runs & resource-source admission

A crash-survivable execution identity, deliberately separate from the disposable Concourse build that actually carries it out — plus a genuinely new way for a workflow to auto-trigger off its own declared resource inputs.

Deleting the build, pipeline-run, or instance-pipeline behind a workflow run doesn't delete the run — those links are nullable, and the run keeps its own captured copy of the plan and config it executed. This is what makes the run ID a stable thing to link to, cite in an audit log, or retry against, independent of whatever GC has done to the disposable execution plumbing underneath. The same durability extends one level up: a workflow definition version can only ever be deprecated, never deleted — there is no exposed delete operation for one at all — and the database enforces this structurally (a run's foreign key to its definition version is ON DELETE RESTRICT). A run you dispatched against a since-deprecated or since-superseded workflow version stays exactly as viewable as one from five minutes ago.

One admission engine — a restartable, crash-resumable state machine — serves every invocation origin: a manual run, a ticket dispatch, a retry, an experiment cell, or an automatic resource-source trigger (below). That's a deliberate design choice: every origin gets identical guarantees around idempotency, budget admission, and secret preparation.

The launch envelope: binding trusted config to a caller's params

Launching a run requires an opaque ExecutionEnvelope minted only from a trusted, already-rendered definition — its canonical config bytes and content hash are private fields no outside package can read or forge. This closes two distinct threats: a caller can't pair the params from one render with the persisted config of a different definition (a zero-value or mismatched envelope is rejected outright, proven by a direct regression test), and a caller can't substitute their own value for a parameter a trusted resource-source binding already fixed — the binder unconditionally overlays server-selected values and errors if the caller's own value disagrees. This is a different, complementary mechanism to the one that protects which Kubernetes secret gets mounted for a live agent step (see Execution, budget & credentials) — one protects admission-time launch integrity, the other protects runtime credential identity.

Public output promotion isn't just "the build passed"

Every output snapshot gets bound to the run the moment its producing node finishes, but it stays invisible — an intermediate candidate — until the entire run succeeds. At that point the platform independently re-verifies the declared outputs against durable evidence (does a real, unambiguous producer exist for each one, is the content actually available, is retention correctly claimed) before flipping them public. A run whose build technically exited zero can still terminate as failed or errored if that re-verification doesn't check out.

A failed or partial run's outputs simply never get promoted. The bytes aren't deleted — they remain visible through snapshot history — but nothing treats them as the run's result.

The reconciler Live

A background component polls for runs stuck mid-admission, drains pending human-wait resolutions, and finalizes cancellation — closing the crash windows an in-memory-only state machine would otherwise leave open. It's the reason a resolved approval always replays as the exact same answer even after a restart, and the reason a canceled run's open waits reliably get closed rather than orphaned. This is also the only terminalizer for tickets: ticket-state projection is folded directly into this always-on reconciler, so there's no second, narrower loop specifically for tickets — disabling the ticket dispatcher component (see Tickets & dispatch) does not risk killing the safety net that moves a ticket to needs_review, because that responsibility never lives there.

The same finalization moment is also where a run's durable per-node history gets frozen for good. agent/workflowrun/occurrence.Derive is called from exactly two places with identical semantics — live, while a run is still executing, so the workflow overview's current-attention view is never stale, and once more at this reconciler's finalization step, to write an immutable agent_workflow_run_node_occurrences row per node attempt before anything can reclaim the sources it reads from. Open human waits are cancelled before that freeze, not after — cancelling first is what stops a wait that outlived its build from freezing as permanently waiting — and the freeze itself runs before ticket projection, since it is "the only consumer that races GC for the run's evidence" (reconciler.go's own comment). Nothing locks that race at the database level: WorkflowRunTemplateLifecycle's retirement pass only admits a template once every citing run is terminal and every pipeline run finished more than the retirement period ago — hours, not seconds — and build-log reaping is separately retention-bounded, so the ordering is, in the code's own words, "a wide practical margin rather than a database-level guarantee." The freezer is deliberately never retried on a later claim of an already-terminal run: a second attempt made after GC had reclaimed the sources would write a degraded projection as permanent truth, which the design considers worse than leaving that run with no frozen history at all. This frozen (or, for an active run, live-derived) projection is exactly what the workflow overview and run-detail pages render — see The operator surface today.

Resource-source admission: a workflow can now auto-trigger off its own inputs Live

This is a real answer to "can a workflow auto-trigger the way a Concourse job does" — with an important scope limit: it's about one workflow's own declared resource inputs, not about one workflow's output triggering a different workflow.

A workflow definition can declare resource_sources alongside ordinary resources — the only place `resources:`/`resource_types:` are still legal in a v3 definition:

resources: - {name: repository, type: git, source: {uri: https://example.invalid/repository.git}} resource_sources: - {name: repository-source, resource: repository, type: repository/v1, trigger: true} plan: - agent: inspect function_id: inspect prompt: inspect inputs: [repository-source] input_types: {repository-source: {type: repository/v1}}

At promotion, this compiles into a plain, non-template Concourse pipeline with one job (admit) containing one get per declared resource source — this is a genuinely different, "standing" pipeline model from the workflow's own one-shot execution template, activated in the same transaction that flips the definition live. A partial unique index enforces at most one active standing pipeline per (team, workflow name) at a time; promoting a new revision demotes the previous one to draining rather than leaving two ambiguous admitters alive.

With trigger: true, that standing pipeline's own Concourse scheduler creates new builds exactly like any other triggered job when a new resource version appears; a background reconciler notices the successful build and drives capture-then-launch automatically. A manual fly agent workflows run against a resource-source-bearing definition still works too — it triggers the same standing pipeline's job inline rather than requiring you to wait for one. Either way, the winning selection is captured once, idempotently, into a Hangar-backed snapshot, and that exact same admission is reused — never re-derived — for the first run and for every retry, replay, or experiment child that follows from it.

The pre-existing, fully manual fly agent snapshots capture-resource is untouched and still the general-purpose, operator-initiated way to capture any resource version independent of any workflow's own declarations.

A pinned capture image is used directly, never re-resolved

capture-resource's seal task runs under whatever image --agent-step-image (CONCOURSE_AGENT_STEP_IMAGE) names, and agent/resourcecapture.registryImage pins it by digest whenever the reference includes one (repo@sha256:...). metadataFetchImage in atc/engine/build_step_delegate.go checks the get plan for a pinned version first and uses it directly when present, skipping any registry round-trip; only an unpinned reference falls through to the resource config scope and, failing that, an on-demand registry resolve of source["repository"]:source["tag"]. The scope is deliberately left unwritten when a pin is used — a pin is one caller's explicit choice, not the source's latest version, and writing it back would silently redirect unpinned callers to it.

Naming collision worth knowing

There are two unrelated components both informally called "the reconciler." This one is the durable-run engine's crash-safety net and covers every invocation origin, including resource-source admission. A separate reconciler (MonitorPipelineReconciler, agent/pullrequest/pipeline.go) drives the provider-native PR-monitoring standing pipeline (Provider-native PR publishing). The two share the same underlying registry table, agent_workflow_resource_source_pipelines, and the same active/draining/archived state machine — rows are discriminated by a nullable pr_binding_id column rather than split across separate tables, with partial unique indexes keeping a workflow-definition-keyed row and a PR-binding-keyed row from colliding.

Tickets & dispatch

The ticket is the human-facing queue entry. It is deliberately not the thing that actually runs.

A ticket carries title, body, its captured snapshot references, and the queue/dispatch/disposition controls a human operates. It is a projection shell — everything about actual execution (the review, the diff, the outcome) belongs to the durable run it dispatched into. The state machine is exactly draft → queued → running → needs_review → closed; there is deliberately no merged/sent-back/abandoned/failed state mirrored onto the ticket itself — those live only on the workflow run and its outcome (Workflow outcomes).

Ticket queue

The paused mode and the ticket mix shown are one deployment's state, not defaults; the queue controls are unused here.

One ticket, many runs

"The run it dispatched into" is singular phrasing but the relationship isn't: agent_workflow_runs.ticket_id is a plain foreign key on the run, not a unique one, so a ticket can carry a full history of runs across every dispatch attempt, retry, and requeue. What a ticket-scoped read reaches by default is a derived current run — whichever row's idempotency_key matches the ticket's live dispatch_reservation_key — and the full journal across every attempt is queryable via GET /api/v1/agent/tickets/:ticket_id/runs. Presenting that history is a UI concern out of scope for this section.

The ticket detail page presents that history as a chronological run journal Live

The UI half of the split just described lives on the ticket detail page itself, fetched separately from the ticket record (FetchAgentTicketRuns, alongside FetchAgentTicket, in web/elm/src/AgentTickets/AgentTicket.elm) and rendered by a small dedicated module (web/elm/src/AgentTicket/Journal.elm). Its own doc comment is explicit about what it is not: "deliberately NOT a graph. There is no composed cross-workflow DAG, no edge element, and no invented causality" — a ticket that drove small-fix, then pr-create, then small-fix again reads as three ordinary entries, ordered purely by the durable occurrence time the server sent. A retry is only ever grouped with the run it retried via a rendered "retry of <id>" label — never a causal edge the layout depends on. Each entry links straight into that run's own DAG detail page (described below, in The operator surface today), so opening a ticket and following a run goes directly to that specific run's graph rather than to a generic list. The server side (agent/api/ticketjournal) is one query, bounded to 500 rows and deliberately not paginated — "a journal is read as a whole story and a cursor would invite the caller to reassemble it out of order" — and each entry's outstanding flag reuses the exact same active/unresolved status vocabulary the run list's own attention lens uses, so the journal and the graph pages can't disagree about what still needs a human.

Only a title and a target repo are required to create a ticket; body may be left empty. There is no separate spec or task-plan submission surface — the ticket's markdown body is the single place ticket prose lives, and it is written by whoever calls the update route (a human, via fly or the web UI), not filled in progressively by an agent as it investigates.

Cost is not tracked against the ticket: agent_cost_ledger keys spend to the workflow run and the workflow function that spent it (workflow_run_id, function_id), and budget enforcement is a single global daily cap checked at dispatch time, not a per-ticket allowance. If you're reconciling spend, query the workflow run(s) a ticket dispatched into, not the ticket itself.

Ticket detail, no runs yet

An empty journal is a valid current state, not a missing screen. When a ticket has dispatch history, this same spot is the chronological run list described above; the queue view is where to find tickets that need attention.

For a dispatchable ticket, the selected workflow must declare exactly one work-item/v1 input and one repository/v1 input. There is no automated ticket ingestion from git or an issue tracker

The diff-derivation package (repodiff) is a diff-math library — given two already-local commit IDs it derives a repository diff; it never resolves a remote and never fetches. The only ways a ticket comes to exist are --origin web or --origin fly — both human-driven. The pull-request package might look like an ingestion path at a glance, but it starts downstream of an already-accepted review and has no code path that creates or updates a ticket — see Provider-native PR publishing. There is no origin for a platform-initiated follow-up ticket: ValidOrigin accepts only web and fly.

The journal fetch degrades to a stale banner, not a blank page

The journal is polled independently of the ticket record and its client state is one of four explicit variants — loading, failed, loaded, or stale (AgentTicket.JournalState) — rather than a bare loaded/error boolean. A poll that fails after a prior successful load does not blank the list: it keeps showing the last-known journal, marked stale, rather than discarding real history because one refresh hiccuped. Both the run-graph route and the ticket-journal route are classified ViewerRole reads in the accessor's default-role table and the auditor's action switch.

Auto-dispatch is a live runtime toggle Live

This is current, maintained code — not something superseded or on its way out; the Live pill means exactly that, distinct from the Parked/Dormant/Gap/Gated pills used elsewhere in this guide for things that aren't. Manual dispatch (fly agent tickets dispatch) always works regardless of any setting. Automatic dispatch of the whole queue is a three-state mode — off / paused / active — stored as a single hot-read settings row and changeable with no restart; there is no boot flag involved. The row is seeded to off by migration and is the sole source of truth for mode.

fly -t TARGET agent dispatcher resume # auto-dispatch every queued ticket fly -t TARGET agent dispatcher pause # stop new auto-dispatch, keep the always-on reconciler alive fly -t TARGET agent dispatcher off # fully dormant

Any transient error reading the setting fails safe to paused rather than silently resuming against an operator's explicit pause. The same three states are readable, and admin-settable, from a banner on the web UI's ticket-queue page.

A small advisory linter (WorkItemTextLint, server-side only) scans ticket text for phrasing known to trigger the Claude CLI's own usage-policy false refusals (certain security/surveillance-adjacent words, each backed by a documented real incident), surfacing warnings on the dispatch response rather than blocking anything.

Reviews & feedback

A first-class human-grading feature with its own routed web page — easy to miss, because everywhere else in this guide "review" only comes up as the review/v1 snapshot type.

Reviews and feedback are two related but distinct APIs. A review is an agent's own findings for a build or snapshot — and there is exactly one writer for it, by design: sealing a review/v1 snapshot. There is no separate "submit a review" HTTP route; a review comes into existence as a side effect of a step's typed output, attributed to whoever was already authorized to create the build that produced it. Feedback is a human grading one of those findings against a fixed verdict vocabulary — accurate, false_positive, noisy, overly_strict, partially_correct, missed_context. Both are wired into the web UI as their own routed page — /teams/:team/agent-reviews is a top-level nav destination alongside workflows, tickets, and experiments, not a tab folded into one page.

There is no verdict auto-classifier

Feedback verdicts are recorded only through human judgment: SubmitFeedback is the sole feedback-handler method, and it requires an authenticated reviewer and an explicit verdict on a specific finding. There is no keyword-based or automatic classifier, and no findings-lookup route independent of a review projection — a route-registration test in agent/api/feedback asserts that the old read/classify surface (/api/v1/agent/feedback, /api/v1/agent/feedback/summary, /api/v1/agent/feedback/classify, /api/v1/agent/reviews/:commit/findings) must never be registered.

Phase 2

Workflow outcomes

A durable disposition ledger for individual outputs — a different axis from both run status and the ticket-review split above, and worth not confusing with either.

A workflow outcome records the disposition of one specific output snapshot — accepted, rejected, merged, or abandoned — independent of whether the run that produced it succeeded. Because it's keyed to an output rather than to the run, a single run can carry several independent outcome rows. There's no fly command for it; the only surface is a read-only card on the durable-run detail page.

This is the third thing in this guide named "outcome," and none of them are the same

Watch the vocabulary: agent/schema's RunOutcome (ok / no_output / running / failed / errored / aborted / unrecorded) is the fused build-status-plus-run-status display truth fly agent runs renders as a badge — explicitly designed so it never shows green when the underlying build is red — a completely different axis from this section's Disposition vocabulary, and the two systems never read from or write to each other. There is no parked token in this vocabulary: a stray "parked" value in a results.json wire payload is just an unrecognized status that ThreeWayStatus folds into RunStatusError — agent/schema/status_test.go spells this out directly ("PARK-V2 is gone: 'parked' is now just an unknown wire value"), and web/elm/src/AgentBadge.elm's badge derivation carries the same seven-token set with no parked case.

This ledger is advisory record-keeping, not an enforcement layer. Marking an output rejected has no runtime effect on publication: publish_snapshot is gated entirely by its own await_snapshot/approval machinery (see Human approval & publishing), independent of this API. A human can PUT disposition=rejected here and an already-approved publish can still complete right alongside it. The publication-state field on an outcome row holds exactly one of two tokens, not_requested or published — a published row must carry a foreign-key-verified publication ID as evidence, and the schema rejects any other combination outright. The human-facing modify path covers disposition and labels only; it has no publication fields at all, so a human can never claim publication evidence through this route.

Dormant write path

Store.Record — the one method whose request type can set publication state directly — is fully implemented and unit-tested but never called in production: the HTTP handler method literally named Handler.Record is a false cognate that actually calls store.Modify, not store.Record.

Phase 2

Execution, budget & credentials

Two binaries, one image, one execution backend — funded by a single platform credential, checked against budget at three points that never double-count.

Two binaries, same pod model

The agent-runner image ships two Go binaries. agent-runner is the image's entrypoint and handles agent: steps: it waits for every declared capability sidecar to report healthy, then execs the Claude CLI with the step's budget slice, a generated strict MCP config (so a repo-committed project MCP file can't sneak in an undeclared tool), and a flight recorder capturing the transcript and cost. function-runner is a second binary that ordinary task: steps invoke by name for deterministic compute: the merge/direct-Git function described in Human approval & publishing, the dev-validation check catalog and review-measurement functions described below, and the pull-request response/materialization functions used by the publishing lane.

Neither is a separate execution backend. Both run as ordinary K8s-native pod-per-step tasks on the exact same image; the only difference is which step type a workflow author chose and which command line that pod ends up running.

Hermetic egress is proven before the model call, not after

An agent pod with networkPolicy.hermeticEgressTo unset (see Workflow definitions) fails within 10 seconds instead of hanging on its first model call under the deny-all egress NetworkPolicy. agent-runner probes the model endpoint in agent/runner/model_egress.go immediately before exec'ing the CLI (runner.go's step 3b, the last preflight before the CLI exec): it resolves the host, then dials TCP only — no TLS, no HTTP, no credential — so the probe itself burns no tokens and can't fail for any reason other than the one it's testing for. DNS and the endpoint are reported as two distinct failures, matching the two separate rules an operator has to open in hermeticEgressTo (cluster DNS on port 53, the endpoint on 443), so the error points at the rule that's actually missing instead of a generic network complaint. The probe is skipped entirely when HTTPS_PROXY/HTTP_PROXY/ALL_PROXY is set, since the CLI would talk to the proxy and a direct probe would prove nothing about the real path.

Budget: three checkpoints, one hard gate

Spend is checked at three points that never double-count. At workflow-run admission — before any template, secret, build, or agent side effect — the global daily budget admitter statically sums every agent: step's declared budget_slice_usd across the compiled plan and reserves that total, once, against the remaining daily cap; the reservation is a single atomic accept-or-deny, not a floor. Each admitted agent step's own declared slice then becomes the hard cap the Claude CLI enforces directly, passed through by agent-runner as --max-budget-usd. After the step completes, its actual observed cost lands as one append-only row in the cost ledger.

The hard gate is a separate mechanism: a deployment-wide daily cap (--agent-daily-budget-usd, 0 disables it) whose admission takes a single database-wide lock shared with ledger inserts, run-metrics ingestion, and experiment budget reservations, so multiple web nodes can never independently over-admit against the same remaining cap. With that cap enabled, every agent leaf in every workflow must declare a finite, positive budget up front, and an attempts/across block anywhere in the workflow becomes inadmissible — the budget admitter rejects the node type on sight, unconditionally, during that same static pass over the plan, so even one wrapping a plain task: or get: elsewhere in the same plan blocks the whole run, not just ones wrapping an agent.

The ledger is per-agent-step granularity, not per-run: one row per completed step, carrying separate input/output/cache-read/cache-creation token counts, turns, model, and a provider tag. The schema recognizes two spend sources — agent_step and ci_agent — but only agent_step is ever populated by production code today, written server-side by the agent step itself after flight-recorder ingestion. There is no route or tool that accepts an arbitrary ledger entry; the only externally exposed surface over the ledger is the read-only cost-rollup API, grouped by day, user, workflow, model, or step.

Flight recorder transcripts

Agent-runner writes the raw claude --output-format stream-json --verbose output to a transcript file; the web node ingests it keyed on (build, plan) with a bounded tail and a truncation marker past that. A wired API route serves it back, and the durable-run detail page's Elm viewer renders it: an "Agent transcripts" card lists one collapsible row per transcript, and opening a row renders the parsed entries (system/assistant/user/thinking/tool-call/tool-result/outcome) against a documented parsing contract — an unrecognized line degrades to a raw fallback rather than losing the rest of the transcript.

What the deterministic gate & judge functions actually do Live

Judge (function-runner's judge mode) is deterministic and model-free: it reads a sealed review/v1 record, derives a fixed, closed set of metrics from it — conclusion indicators, finding counts by severity, summary length — and seals a measurements/v1 record. It starts no model, resolves no remote, and consults no clock, which is what lets an experiment evaluator built on it (Experiments) stay reproducible and effectively free to run. It is not a rubric-scoring LLM judge; that kind of stochastic scoring belongs to an ordinary agent: node in a workflow, not to a function-runner mode.

Gates (function-runner's dev-validate mode) run a profile-declared check catalog of build/test/lint operations, each independently scoped full, required, or affected, with 0-2 retries and a per-check timeout bounded to 24h, and seal the result as a validation/v1 record. A workflow author opts a task: step into this behavior with the source-level dev_validation_profile field; the trusted schema-v3 renderer compiles it into the fixed task shape and a server-owned authority. The same mode validates a repository-change/v1 snapshot without publishing it — there is no separate "repository-validate" mode — and its passing validation/v1 record is what Human approval & publishing's merge gate requires before a merge proceeds.

Both are live cases in function-runner's mode-dispatch table alongside merge-preflight, merge-prepare, authorize-pr-response, and pr-monitor-materialize.

Credentials: one platform token funds every agent pod

Every agent-run pod's main container mounts its Anthropic token from exactly one Kubernetes secret — named by --agent-platform-token-secret, defaulting to agent-platform-credential — regardless of which user dispatched the run. A polling background component keeps that secret's contents mirrored from the platform service user's vaulted credential once a minute; deleting the platform credential deletes the secret, so no pod can mount a revoked token. An operator can point the flag at a hand-maintained secret instead, in which case admission takes its contents on faith and never reads Kubernetes to check them.

Ordinary users can vault, inspect, and delete their own Anthropic credential through the same fly agent auth CLI (below), but nothing in the run path resolves a dispatching user's own credential to fund their pods — a per-user vaulted row is stored and readable back to that user, not consumed by any agent run today. Only an admin vaulting the platform user's credential (fly agent auth --platform) changes what actually funds runs.

Admission fails a run closed — before any template, secret, build, or agent side effect — when the platform credential is missing or expired; there is no other source to fall back to. The credential itself lands as a Kubernetes secret reference on the main container only: sidecars, including a broker companion if one is present, never receive it.

Vaulting a credential in practice

fly agent auth is entirely client-driven — there's no server-side OAuth exchange. With no --token, it prints instructions to run claude setup-token in a separate terminal and reads the pasted result off stdin. Two credential kinds are supported: anthropic_oauth (the default, from claude setup-token) and anthropic_api_key; whichever row admission resolves, OAuth is tried before an API key.

fly -t TARGET agent auth # vault your own OAuth token fly -t TARGET agent auth --kind anthropic_api_key --token sk-ant-... fly -t TARGET agent auth --platform # admin only: the credential that actually funds runs fly -t TARGET agent auth --delete

Authorization here is looser than most of the agentic surface: the credential routes are gated by plain authentication, not the main-team-scoped check most other /api/v1/agent/* routes use (see Team scoping & authorization) — any authenticated user on any Concourse team can vault, inspect, or delete their own credential. The one exception is --platform, gated to admins, which targets the seeded, never-logs-in platform user.

Expiry is enforced silently at admission time: an expired vaulted credential is treated exactly like a missing one. Because admission only ever resolves the platform user's row, the fallback that matters is kind order within that one row — OAuth first, then API key — not a fallback to any other user's credential; the run is refused outright if neither kind is present and unexpired anywhere on that row.

Broker child credentials — a wholly separate, additive path

If an agent node declares broker_profiles (see Agent execution broker), its child executions use a completely different credential mechanism: operator-configured Helm secrets (agentBroker.credentials[], e.g. an OpenAI or Anthropic key) named by a credential_slot on the frozen profile, mounted as file-based Secret volumes onto the broker sidecar container only — never onto the main container, never derived from any user's vault. A given pod can therefore have the platform's Anthropic token on its main container from the platform-credential secret, and a completely independent, operator-managed credential on the broker sidecar, sourced from an entirely separate Helm config path.

Phase 2

Agent execution broker Gated · not promotion-ready

A sandboxed way for a running agent to synchronously call a second, operator-chosen model as a reviewer or consultant — fully implemented and wired, and explicitly, self-declaredly not safe to run in production yet.

The broker adds two synchronous MCP tools to an eligible agent node: request_review (a static review of an exact captured Git workspace) and consult_agent (a bounded answer to a caller-supplied question over declared snapshot attachments). The caller selects only a provider-neutral {tier: economy|balanced|frontier, effort: medium|high} pair — provider, model, native harness, credential slot, image, and limits are all operator-only and frozen at compile time (see broker profiles). Each child call gets a completely fresh harness context: no parent transcript, no user configuration, no live workspace — just its own image-owned instructions, the caller's prompt, and explicitly named attachments.

request_review doesn't require a commit — it captures the repository base plus staged/unstaged/deleted/renamed/executable/symlink/binary/nonignored-untracked state via a private Git index, verifies the result tree, then runs a deliberately static review: no tests, builds, formatters, or linters, the runtime image has no build toolchain, and every result records tests_run: false. Its output is exactly one validated review/v1 body — the same type the ordinary reviews/feedback subsystem already uses, so a broker-produced review can flow straight into publish/await snapshot steps naming it. consult_agent similarly returns exactly one validated consultation/v1 body.

Promotion blocker — this is a live, self-declared gap, not boilerplate caution

The broker's own documentation states plainly: the current child seccomp/process-group boundary is not yet accepted for deployment. A same-UID child may still be able to join the broker's process group and signal it through kill(0), and async-I/O ownership can provide another signal path. The packaged image is therefore build/test material, not promotion-ready, until that boundary receives human review, a code correction, and a live Linux regression on the managed cluster kernel/runtime. A seccomp filter does exist and is fairly extensive — it explicitly allows signaling one's own process/group while denying ptrace, process_vm_readv/writev, pidfd_*, kcmp, and arbitrary kill/tgkill targets — but the project's own review judged it insufficient to close the same-UID signaling class. Treat agentBroker.enabled as not cleared for production regardless of how complete the rest of the plumbing looks.

Deployment model & sandboxing

ATC owns catalog resolution, admission, short-lived capabilities, the durable child ledger, workspace/result sealing, and inspection. Jetbridge injects one managed companion sidecar only for an agent node whose frozen definition contains broker profiles — there is no broker Deployment or Service. The companion mounts the parent workspace read-only just long enough to capture it; the native harness then runs over that capture behind an unprivileged Landlock ABI 3+ filesystem boundary, able to write only its own per-call scratch and read only configured immutable runtime paths. The parent reaches the broker over loopback with a random per-parent bearer token; the child harness never receives a copy of it. Managed nodes require Linux 6.2+ with Landlock enabled, a compatible RuntimeDefault seccomp profile, and an immutable linux/amd64 broker image digest — a real infrastructure prerequisite most clusters won't already have.

Phase 2

Checkpoint & crash recovery Gated · scaffolding is live, recovery never succeeds today

Durable, fenced, well-tested crash-safety machinery around a recovery decision that — for the one adapter this platform actually ships — always ends in a human being paged.

Answering the obvious question directly: no, an interrupted agent step does not resume mid-transcript today. There are two different crash scenarios, and only one of them touches this feature at all.

ATC crashes, the agent's pod survives — the older, unrelated safety net

Every task/agent step already runs under a small in-pod shell supervisor (see the runtime section) that survives an ATC restart cleanly: the real process keeps running, and a freshly-reconnecting web replays the log and waits for the exit file rather than restarting the command. The gotcha: once a checkpoint-enabled step's durable attempt is marked running, it stops using that fallback-capable attach path and switches to an attach-only call that hard-fails for a still-live pod with no exit annotation yet. In practice, this means turning checkpointing on removes the pre-existing "ATC crashed, nothing was lost" safety net for the remainder of that step's runtime and replaces it with a hard step failure — and no reconciler sweeps a stuck running attempt back out of that state afterward. This is a real, unresolved rough edge worth knowing about before enabling the feature.

The pod or node is actually destroyed — the real checkpoint path

This is what the feature is actually for. On a genuine interruption (pod deleted, evicted, node lost, preempted), the step always allocates one brand-new, fresh replacement attempt — it never reattaches to or resumes a live process. Recovery then picks one of four modes, checked in order: native_resume (the LLM conversation itself continues — requires the adapter to prove session-export and resume capability), workspace_only (fresh pod, workspace restored from Hangar, brand-new call from turn one with a "this is a recovery" system-prompt note), checkpoint_zero (fresh pod, no archive restored, brand-new call from scratch), or manual_review_required (nothing automatic — a human decides).

For the shipped Claude adapter, the answer is always manual_review_required

The composition root hardcodes the recovery authority to nil for the production Claude integration, with the comment: "Production legacy adapters intentionally have no complete journal or recovery proof, so every interrupted source fails closed." The concrete adapter implements only the plain provider interface, not the recovery one — it has no Resume method and reports every capability as false. The recovery-adapter interface (Resume plus RecoveryProof) has zero production implementations anywhere in the codebase; the only type that satisfies it is a test fake. So regardless of how clean the effect journal is or whether a good checkpoint exists, every genuine pod-level interruption of a checkpoint-enabled Claude step ends the same way: the step is marked for human review and stops, with zero automatic replays. Even in the modes that would trigger for a hypothetical capable adapter, "resume" only ever restores the on-disk workspace — the model's own memory of the conversation is never restored, only a system-prompt note telling it this is a recovery attempt.

What is real and load-bearing: the crash-safety machinery around that failure. Every checkpoint mutation requires a fenced capability tied to one execution attempt, with the fence's authority timestamp sampled only after the relevant row lock is acquired — specifically so a lease can't be granted based on a stale, pre-lock-wait clock read. Interrupted attempts are immutable evidence; recovery always allocates a new, sequentially-numbered row rather than resurrecting the old one, enforced by a database trigger, not just application code. Retention is generous and correctly scoped: a source archive stays pinned for as long as any live recovery attempt still references it, even after it's been superseded, and diagnostic metadata survives 30 days past termination.

Enabling it, and what you get to observe

Off by default, gated behind two independent flags (--agent-checkpoint-enabled requires --agent-snapshot-enabled), and scoped only to schema-v3 hermetic agent steps that belong to a workflow run — ordinary ad-hoc pipeline agent: steps never touch it regardless of the flags. There is no dedicated Helm value block for this; a real deployment passes the flags through the chart's web.extraArgs escape hatch.

There is no UI element and no public API route — this is purely a backend-plus-metrics feature today. A real Prometheus alert set exists and is worth wiring up regardless of whether you trust automatic recovery: ConcourseAgentCheckpointCaptureFailures, ConcourseAgentRecoveryManualReviewRequired (severity critical — given the above, this is effectively "any checkpoint-enabled agent step was interrupted at all"), and ConcourseAgentCheckpointRestoreFailures. The operations guide's own runbook is explicitly a manual, log-and-database-inspection procedure — there is no dashboard for it.

Phase 2

Team scoping & authorization

There is no agent principal identity in this platform. Authorization runs through ordinary Concourse team RBAC and a small set of team-less routes hardcoded to team main.

No bot/service-account identity exists

Agent principals — a closed-scope bearer-token identity (reviews:write, tickets:read/write, metrics:write, costs:write) with admin mint/list/revoke — do not exist in this codebase. The backing table is dropped; its down-migration restores only the empty schema shape with zero rows, by design ("Deliberately do not restore any row, sentinel, token, or usable authority"). There is no fly agent principals command, no route in the API, and no admin UI for it. A design-doc invariant states it plainly: "agent principals do not exist." If you're looking for a bot/service-account identity anywhere in this platform, there isn't one.

How each write path is actually authorized

Reviews aren't "posted" by anyone; a review comes into existence as a side effect of sealing a review/v1 snapshot, attributed to whoever was already authorized to create the underlying build. Reading a review by snapshot or by durable-run is a team-less route authorized against team main only. Human feedback is submitted through an ordinary per-team route (/api/v1/teams/:team_name/agent/feedback), requiring Member role on the snapshot's own team — not hardcoded to main. Identity comes from the caller's own OIDC claims via the accessor, the same mechanism used everywhere else in Concourse; the handler's identity function carries an explicit comment that production wiring must supply real identity "so caller-controlled JSON cannot impersonate or overwrite another reviewer's feedback." Tickets are a team-less route requiring Member (create/update/transition/dispatch) or Viewer (read) on team main specifically. Metrics and cost-ledger writes have no HTTP route at all — they're server-internal bookkeeping the ATC process performs as a side effect of running a build it already controls; there is no external write boundary to authorize.

The hardcoded-main-team claim, and its two exceptions

Most team-less /api/v1/agent/* routes — workflows, workflow runs, waits, outcomes, transcripts, experiments, tickets, and read-only metrics/costs — are authorized against a single Concourse team, compared on every HTTP request against the atc.DefaultTeamName constant ("main"), not resolved once and cached. A user who's a Member or Owner of some other team but not of main gets a flat 403 on all of it.

Snapshots and human feedback are the two exceptions. Snapshots carry a mandatory team_id column directly on the manifest and are authorized the ordinary Concourse way, through a real, dynamic :team_name path — not hardcoded to main. Feedback submission is likewise routed under :team_name and scoped to the snapshot's own team. In practice, because the ticket/workflow dispatch pipeline itself is still wired to always operate as team main, every snapshot the pipeline produces today ends up owned by main anyway — but the authorization mechanism for snapshots and feedback is genuinely team-generic, capable of a different team owning its own snapshots and feedback the moment something drives that pipeline under a different team identity.

Phase 2

Human approval & publishing

The one primitive allowed to have an outbound side effect, and the trust boundary that governs it.

ATC holds the real write credential directly

ATC (the web node) mounts the destination write credential itself — there is no separate deployment-owned gateway service holding it outside ATC's trust boundary. The Helm chart hard-fails the render if a values file still sets the retired agentPublisherGateway key at all, with the message "has been removed; use agentPublisher." The publisher policy document and the write credential live in two structurally separate Secrets: the chart refuses to render if they, or any other reserved Secret it manages, ever alias each other.

await_snapshot is a durable human wait tied to an exact run, build, and question/answer snapshot pair. publish_snapshot is the only workflow primitive that performs an outbound side effect. Every durable-store call an await_snapshot wait depends on uses the step's live context up until the wait's own deadline; once the deadline has elapsed, the call switches to a short 5-second detached budget so a human answer or an on_timeout: default substitute that lands in the final poll window still gets persisted, while a genuine abort (a non-deadline cancellation) still interrupts the wait immediately.

A workflow author cannot forge the approval

For a merge, a workflow must name a non-optional human-answer wait — but the approval question itself is server-generated, not author-supplied. Once the change snapshot exists, the server binds the concrete definition, run, build, and content digest, and seals a strict question that includes the publisher, mode, destination, target branch, and an intent digest over the full parameter map. Only a non-timeout answer that's exactly "approve," from the actual resolving human, is accepted. The base-commit assertion is derived server-side from the change snapshot's own sealed metadata and can never be authored in workflow YAML, so the approval question and the eventual publish call are mathematically guaranteed to agree.

Direct-Git delivery: real syntax, excerpted

The merge-delivery-v3 seed's await_snapshot/publish_snapshot pair is live and not gated behind anything except --agent-publisher-direct-git-enabled (and the baseline --agent-publisher-enabled/--agent-snapshot-enabled requirements every publisher mode shares):

Ticket state is not a publication record

Provider-native PR publishing Gated · unconditionally refuses to start

A large, thoroughly tested, real subsystem for opening and maintaining a GitHub/Azure DevOps pull request — and something you structurally cannot turn on.

The design: publish_snapshot with mode: pull-request creates or updates a source branch and a PR idempotently; a separate, reusable pr-monitor-v3 workflow then owns a genuinely standing Concourse pipeline per binding — a read-only forge-pr resource polling every 5 minutes by default — that reacts to submitted review batches by revising the branch, re-validating, and replying, all without Jetbridge ever completing or abandoning the PR itself; the forge and its branch policies remain the final merge authority.

This cannot be enabled today, on purpose

Setting --agent-publisher-pull-requests-enabled unconditionally fails ATC's own config validation and refuses to start, with an explicit message naming exactly what's still missing: authoritative impact evaluation, action-bound initial publication composition, approved-baseline materialization and advancement, and full lifecycle wiring. The standing PR-monitor pipeline mechanism described above is fully built and unit-tested, but the production composition call that wires the main dispatch graph passes zero monitor policy resolvers, so it stays inert in the running binary even independent of the startup refusal. There is no fly command and no web UI page for any of this — an operator "pausing" or "resuming" a binding, as described in the feature's own operations runbook, is a database-layer capability with no exposed way to invoke it today.

Two things are worth being precise about since they're easy to conflate: first, the feature's own docs describe publish-pr-v3 as a workflow boundary parallel to pr-monitor-v3 — it isn't one. No such workflow YAML exists anywhere in the repo; the initial-publish side is implemented as a plain Go coordinator invoked directly from ATC, with no author-facing YAML at all. Second, direct-Git publishing (above) is completely unaffected by any of this — it's a separate, non-gated adapter mode through the same router, and it's the only "agent publisher" path that actually works in a real deployment right now.

What's genuinely usable even while gated: publish-impact/v1 is a real sealed-record type computing changed files, validation deltas, and deterministic pass/fail rule results for a candidate versus a baseline — with a hard invariant that an agent's own impact assessment can only escalate a reapproval requirement, never waive one a deterministic rule already set. GitHub is the live, integration-tested provider; Azure DevOps is contract-tested against its REST API but has not been validated against a real tenant.

Phase 2

Experiments

A/B testing for workflow variants, built as a thin admission gate on top of the same durable run engine — not a parallel implementation.

An experiment pins two or more candidate variants (one designated control), a set of snapshot fixtures, and a pinned evaluator workflow, then materializes the full fixture × variant × repetition matrix as individually admitted cells. Both the candidate and evaluator executions for a cell are ordinary durable workflow runs — same admission, same output validation, same cancellation semantics as any other invocation — routed through an extra gate that checks the experiment and cell are still genuinely open before admitting a new child.

A variant doesn't have to be a whole workflow — this is the actual answer to "how do I iterate on one step of a chain without re-running everything upstream of it." Every node's output is already its own addressable snapshot the moment it seals, whether or not it's one of the workflow's declared top-level outputs (see Durable workflow runs). So to compare two versions of, say, a downstream validate node against the exact same upstream output: pin that upstream snapshot as the experiment's fixture, then add each candidate as an extracted single function rather than a full workflow, using workflow@version#function_id:

fly -t TARGET agent experiments add-variant EXPERIMENT v1=my-workflow@3#validate --control fly -t TARGET agent experiments add-variant EXPERIMENT v2=my-workflow@4#validate

Each extracted target is rendered and admitted as its own standalone durable run against the pinned fixture — same guarantees as any other cell, just scoped to one function instead of the whole DAG. This is the same node-extraction mechanism described in Workflow definitions, not something specific to experiments — experiments are simply its main consumer today.

Node targets Live

A third target kind grades a reusable node directly rather than a workflow or an extracted function: TargetKind is workflow, function, or node (agent/experiment/types.go:88-95). A node run is already an ordinary durable workflow run discriminated by workflow.DefinitionKindNode, so a node target selects no function implementation and instead varies the node's own NodeParameters — a turn cap, a model, a prompt — between variants while the node definition itself stays fixed. This is the direct answer to A/B-testing one reusable node's prompt or model without wrapping it in a throwaway workflow.

The mechanism is fully wired, not a stub. Migration 1773106159 added node_parameters and evaluator_node_parameters JSONB columns and widened the target_kind/evaluator_target_kind CHECK constraints to admit 'node', with a paired constraint that a node row's function_id must stay NULL. atc/db/agent_experiments_factory.go persists and reads NodeParameters on both the variant and the evaluator, and loadAuthoritativeExperimentNodeTarget freezes a node target by reading the same compiled-node row the binder resolves from and instantiating it with the frozen parameters, refusing to proceed if the resolved identity doesn't match. agent/workflowrun/binder.go carries a narrow, deliberate exception for this: a node request may carry a frozen definition ID and target-config hash only when it's accompanied by an experiment admission — an ordinary (non-experiment) node request that tries the same is still rejected, because freezing a node mid-run against its own in-flight replacement would make the comparison meaningless outside a controlled A/B.

No CLI shorthand for node variants

fly agent experiments add-variant cannot construct a node target. parseAgentExperimentVariantReference (fly/commands/agent_experiments.go:652) only parses label=workflow@version or label=workflow@version#function-id, and resolveAgentExperimentVariant always resolves the reference against the workflow-versions API, producing a TargetWorkflow or TargetFunction — there's no node syntax and no --node-param flag anywhere in the command. The only way to add a node variant is hand-authoring the JSON body passed to fly agent experiments create or experiments update, setting "kind": "node", the node's frozen definition_id/version, and node_parameters directly in a Variant (or the experiment's Evaluator) — the server accepts it because Target.Validate() (agent/experiment/types.go:119) explicitly admits TargetNode, it's only the ergonomic CLI path that hasn't been extended.

That gate matters because of a specific race: without it, a scheduler admitting a new cell and a concurrent cancellation of the parent experiment could interleave such that a child gets created for an experiment that's simultaneously being torn down, leaving an orphaned run that keeps consuming budget after the experiment is nominally stopped. A database lock held across the check-and-admit step closes that window.

Budget is reserved once per cell, up front, covering both its candidate and evaluator together — so an experiment child deliberately skips the ordinary per-run budget check that ticket and manual runs go through, to avoid reserving the same dollar amount twice.

Scorecards aren't computed lazily on read. The moment an experiment reaches a terminal state, its scorecard is built once from every settled cell's telemetry and frozen immutably in the same transaction — a later metric arriving out of order cannot rewrite a result you've already looked at.

fly -t TARGET agent experiments create definition.json fly -t TARGET agent experiments start EXPERIMENT --revision=REVISION fly -t TARGET agent experiments scorecard EXPERIMENT

Enabling the experiment runner requires snapshot storage to be enabled — fixtures and measurements are snapshot-backed, so there's no meaningful "experiments without snapshots" state. Disabled by default; start/validate fail closed with service-unavailable rather than quietly queuing work nothing will claim. Server-enforced bounds keep any one experiment reasonable: 16 variants, 256 fixtures, 1,000 repetitions, 2,000 cells, 32 measurements.

Operating & deploying

The Helm chart is the deployment surface for both phases. It carries its own regression tests against the ATC binary, so drift between the chart and the flags the binary actually accepts fails the chart's test suite rather than surfacing as a crash loop after deployment.

Chart-level regression guards
  • Flag-parser guard. No PVC-based artifact/cache-store flags or values exist anywhere in the tree. The chart carries a regression test that instantiates the real ATC flag parser and asserts every flag the chart renders for the web Deployment actually exists on the binary, plus a hardcoded list of retired strings it asserts never reappear in values.yaml or the rendered templates — a structural guard against this class of drift, not a one-time cleanup.
  • Signing-key reuse. With the default secrets.create: true, the chart uses Helm's lookup to reuse an existing signing key across upgrades (minted once, kept via helm.sh/resource-policy: keep), so web.replicas > 1 works out of the box. lookup is a no-op during a cluster-less helm template render (a template-then-apply GitOps flow), so that flow must set secrets.signingKeySecret explicitly rather than relying on secrets.create. Two more chart-generated Secrets depend on the same lookup no-op — the artifact-daemon's TLS CA/certificates (artifactDaemon.tls.existingSecret) and its resolve-capability HMAC key (artifactDaemon.resolveCapability.existingSecret). The resolve-capability key is the sharper case: it renders whenever artifactDaemon.enabled is true, which the Kubernetes runtime requires, so it re-mints on every cluster-less GitOps sync regardless of replica count or whether daemon TLS is on. The ATC and each daemon pod read the key once at process start, so nothing breaks at the sync itself, but the next restart of either side lands on material its peers don't share and fetch-inputs init containers fail closed until both the web Deployment and the whole DaemonSet have rolled. deploy/chart/README.md's ArgoCD quickstart hands over literal kubectl create secret commands to pre-create the signing key and the resolve-capability key before the first sync, since neither can be minted durably by a helm template-only render; the TLS CA has no such one-liner because it's a keypair, not a single value, and is left to whatever internal-CA tooling the operator already runs.
  • Fail-closed ServiceMonitor/NetworkPolicy pairing. The artifact-daemon's Prometheus metrics are scraped by a dedicated ServiceMonitor, on by default whenever the top-level serviceMonitor.enabled switch is on. If an operator enables both a NetworkPolicy and this ServiceMonitor without also setting serviceMonitor.scrapeFrom, the Helm render fails outright rather than producing a Prometheus target whose scrapes get dropped by the policy.
  • Frontend bundle freshness. A dedicated build-frontend task runs before the image build and hard-fails the whole job if it produces no output, closing the //go:embed web/public trap where a stale UI could ship. The hardened pipeline's frontend build step and the simpler chain's own Dockerfile frontend stage remain two separate, manually-synchronized pieces of config with a comment explaining why they aren't unified — a change to one can still drift from the other unless someone remembers both.
Web metrics are opt-in and validated at render time

The ATC serves the Prometheus text format only from a dedicated listener it starts when both --prometheus-bind-ip and --prometheus-bind-port are set (atc/metric/emitter/prometheus.go's PrometheusConfig.IsConfigured); the API port serves no /metrics route at all, so an unmatched path there returns the web UI's HTML with a 200 rather than a 404. The chart wires this behind an opt-in web.metrics block (web.metrics.enabled, default false) that sets the two flags plus a named metrics container port and a matching Service port when enabled. serviceMonitor.web.enabled defaults to unset and follows web.metrics.enabled; the render fails only when an operator explicitly sets it true against metrics that are still off. The bundled Prometheus alerts select series that match what the exporter actually emits — ConcoursePodStartupSlow reads the histogram under its real name, concourse_k8s_pod_startup_duration_milliseconds_bucket (deploy/chart/templates/prometheusrule.yaml) — and the DB-connection-depth metric backing ConcourseDBConnectionPoolExhausted is a Float64Gauge reflecting current pool depth rather than a running sum.

Self-hosting: two release pipelines exist

There are two independent pipelines in deploy/ that can build and deploy this project against itself — confirm with whoever operates a given cluster which one is actually authoritative there:

  • The hardened chain — build, native agent review, unit tests, K8s runtime tests, a release-candidate tag, image build (including the frontend-rebuild task above), self-upgrade, a post-upgrade verification pass, live K8s tests, then release. It carries concrete, comment-documented guards for the historically recurring failure modes in a chain like this: retries around single-node flakiness, the RBAC grant that lets the post-upgrade rollout check actually complete instead of hanging, and an image-existence check before the release job's git tag/push so a failed build can never leave a phantom release tag behind. The tag-rc job also reserves an immutable, source-bound RC tag: overlapping candidates allocate distinct patch versions instead of moving a live-tested candidate's version authority.
  • The simpler chain — build, test, build an image tagged :latest, a short-lived pod that restarts the live deployment, then promote to main. No release-candidate dance.

Building the agent-runner image

Ships both binaries described in Execution, budget & credentials, plus a full Go toolchain and a pinned Claude Code CLI. It intentionally runs as root — jetbridge's shared host-path step volumes are created by the kubelet as root-owned and a pod's fsGroup is ignored for host-path mounts, so this is a considered trust boundary, not an oversight. The workflow overview page: a coupled semantic graph and run list Live

The /agent/workflows/:name route pairs a redacted semantic DAG of the workflow's promoted definition with a chronological, filterable list of its runs, backed by a dedicated endpoint (GET /api/v1/agent/workflows/:workflow_name/overview, atc.GetAgentWorkflowOverview, agent/api/workflowoverview). The page's own doc comment states its scope on purpose: "shape, state, and runs… no metrics strip, no KPI grid, and no per-node chart" (web/elm/src/AgentWorkflow/AgentWorkflow.elm) — those would compete with the graph for attention. Definition management (starting a run, promoting a revision, comparing revisions) is deliberately pushed behind two header actions, Start and Versions, that open URL-addressable overlay panels (?panel=start / ?panel=versions) rather than sitting on the page as permanent furniture.

The graph itself is derived structurally, not by convention: agent/workflow/graph walks a compiled v3 function into eight node kinds (input, resource_source, load, agent, task, await, publish, output) and prompts/task configs/broker profiles simply have no field on the resulting types, so a call site cannot forget to redact them — the package comment calls this "structural" redaction. Every filter and the open panel live in the URL (window, scope, status, q, node, node_status, version, origin, panel — Routes.elm's agentWorkflowQuery), with defaults omitted so a shared link only carries what the sharer actually changed. window and scope are shared vocabulary between the graph and the run list beneath it, validated identically by both endpoints on purpose: window is 24h, 7d, or 30d (default 7d, agent/api/workflowruns/types.go's Windows map), and scope is operational / experiment / all (default operational, db.AgentWorkflowRunScope) — without that sharing, a request for scope=experiment could leave the DAG painted with operational-run failures while the list below it showed an unrelated experiment population.

Per-node state is two independent counts, never one fused status word: ActiveCounts (running/waiting/pending, counted only across runs that are themselves still executing) and HistoryCounts (terminal outcomes inside the window), plus a retry-chain-resolved needs_attention boolean (agent/api/workflowoverview/types.go). The type's own comment is explicit about why: "several concurrent runs of one node have no canonical status, and inventing one — worst-wins, latest-wins, anything — would be a fact the platform does not have." needs_attention comes from occurrence.ResolveEffective (agent/workflowrun/occurrence/attention.go) — the same retry-closure resolution the run list's attention lens uses — so a node that failed and was then successfully retried clears the canvas without erasing the failure from HistoryCounts. The rendering follows the same discipline: node bodies stay colour-neutral, state is a glyph and a count and a word so the canvas survives greyscale or a screen reader, and there is deliberately no --failed/--running fill on a node itself — selection is a border and halo, never a colour swap (web/elm/src/AgentGraph/View.elm). Only the five execution kinds (load/agent/task/await/publish) carry state or are clickable; input/output/resource-source endpoint nodes render neutral because they never run and have nothing an occurrence could describe.

The overview also reports revision_boundaries — the earliest run of each promoted revision present in the window — and a has_historical_only_nodes flag when runs in the window touched a node the promoted graph no longer contains (a retired await_snapshot gate, say). The canvas never draws a union graph across revisions to cover that case; the flag instead drives a discovery affordance inside the Versions panel, which points at the specific older revision that still has the node. If graph.Build can't derive the promoted definition's DAG at all — an unrecognised step kind, most likely — the response degrades to graph_unavailable: true with an empty graph rather than failing the whole page; the run list and every other affordance keep working. The run list itself is intentionally thin — effective-state glyph, run ID, relative time, duration, ticket reference when there is one, and an attention cue, per row (web/elm/src/AgentWorkflow/RunList.elm) — cost and full outcome detail live behind opening a run. Selecting a node on the canvas filters the list and refetches only the list; the DAG never redraws for a selection, which the page's own doc comment calls out as a deliberate choice against a flicker that would buy nothing.

Appendix

A worked example, end to end

Everything above explains the mechanism. This walks one real seed workflow — version-upgrade-v3 — through all six stages with real commands, real node names, and real snapshot types, so the abstract shape in How a change gets made has something concrete to hang on.

version-upgrade-v3 takes a repository/v1 and an upgrade-request/v1, and produces an approved repository-change/v1 plus an upgrade-report/v1. Its plan has five nodes: two agents that draft and refine the change (upgrade, review), an authoritative validation task (validate) that runs the change through a dev-validation profile, a small agent (prepare-question) that turns the validation result into a question for a human — gated on that validation having run — and a durable human wait (approval) that the run cannot complete without.

1–2. Capture, then bind & admit

Seal the two inputs as immutable snapshots, then bind them to a definition version and create a durable run:

# capture a live pipeline resource version as a typed snapshot
fly -t TARGET agent snapshots capture-resource \ --pipeline=repo --resource=source \ --version=ref:0123456789abcdef... --type=repository/v1 # seal an ad-hoc value with no live source — a hand-authored request
fly -t TARGET agent snapshots create --type=upgrade-request/v1 --from=./upgrade-request # import + promote the definition (once, or skip if already live)
fly -t TARGET agent workflows import agent/workflow/seeds/version-upgrade-v3 --set-live # bind the two snapshot IDs above and admit a durable run
fly -t TARGET agent workflows run version-upgrade \ --input=repository=101 --input=request=102 --follow

3–4. Render & execute, sealing as it goes

The definition renders into a one-shot Concourse pipeline and each node runs as its own pod. upgrade produces a draft change and a report; review re-examines the draft against the immutable repository and request, sealing a candidate — its own inputs: list names both the original bound inputs and upgrade's freshly-sealed draft and report, the "output becomes the next input" chaining from the overview made concrete:

- agent: review function_id: review prompt: Review and correct draft; write candidate only. inputs: [repository, request, draft, report] # draft + report came from "upgrade" outputs: [candidate]

The validate task runs the candidate through the repository-gates dev-validation profile and seals a validation/v1 record (rev3 today — with a compiled attestation block, see Snapshots). prepare-question declares that validation as its own required validation input, so it cannot run until validation has sealed, and it in turn seals a question/v1 asking whether the change may go out. Each of these is sealed the moment its node finishes, not when the run finishes; watch it happen live with --follow, or after the fact with:

fly -t TARGET agent workflows runs version-upgrade fly -t TARGET agent workflows show-run version-upgrade RUN-ID

Execution then reaches the definition's await_snapshot node — the one piece of syntax here with no stock-Concourse equivalent at all:

- await_snapshot: approval question: approval-question type: human-answer/v1 on_timeout: fail timeout: 72h

This stops the run cold — a durable wait, not a running pod. There's no fly command to resolve it: an authorized main-team member answers it from the web console's durable-run detail page, in the human-waits card described in The operator surface today; the browser sends only the chosen answer, and Jetbridge seals it as the human-answer/v1 artifact itself. This node carries no merge_approval or pr_approval intent — unlike the merge-gated wait covered in Human approval & publishing, the platform does not force its accepted answers to be exactly "approve" or "reject"; prepare-question is free to choose what it offers, and any answer that matches the sealed question lets the plan finish. If nobody answers within 72 hours, on_timeout: fail fails the run outright, and neither declared output is promoted.

5. Promote

If every node succeeds, the run's two declared outputs — change and report — flip from intermediate to public. Everything else this run sealed along the way stays sealed and inspectable, but was never a declared output and never becomes "the result."

fly -t TARGET agent workflows show-run version-upgrade RUN-ID --outputs fly -t TARGET agent snapshots show SNAPSHOT-ID

6. Publish — not this workflow

version-upgrade-v3 stops at step 5 on purpose — it produces an approved change, not a delivered one. Actually landing it is a separate concern, handled by a workflow that declares publish_snapshot (see Human approval & publishing for the direct-Git path that works today, and Provider-native PR publishing for the pull-request lane), taking this run's change output as its own input and resolving its own, separate, merge-gated approval wait.

Two further worked examples worth reading once you're comfortable with this one, each demonstrating a genuinely new mechanism: the Reusable nodes section walks a single-step node.yaml from import through composition into a parent workflow; the resource-source admission subsection shows the resource_sources: syntax that lets a workflow auto-trigger the way a Concourse job does.
