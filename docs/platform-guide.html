Internal platform guide

JetBridge / orientation & architecture

A Kubernetes-native backend and an agentic workflow platform, both grafted onto stock Concourse. This assumes you already know Concourse well — it covers what's different, why it's shaped this way, and what to know before you operate, deploy, or extend it.

lives on jetbridge re-audited at cb92f2c6e7 · 2026-07-30 grounded in a direct code audit, not the existing docs

JetBridge started from a simple itch: Concourse tasks already look like functions — inputs in, outputs out — so a Kubernetes-native backend seemed like a natural rewrite, and that same function shape looked like a good fit for agentic CI. Everything in the fork is agentically coded: the author specified outcomes, not implementations, and treated it as an open question how far that could go.

This edition of the guide follows a "semantic rebase" — 1,312 files changed against the previous audited state, most of it the agentic half. Team-scoped bearer-token principals were removed outright; the deployment-owned publisher gateway was removed and replaced by credentials mounted directly into ATC; and four substantial new subsystems landed — durable GCS-backed snapshot storage ("Hangar"), a sandboxed agent execution broker for synchronous sub-agent calls, a crash-recovery/checkpoint layer, and a provider-native pull-request publishing lane. Several of the newest pieces are fully implemented, wired, and covered by tests, but explicitly self-declared not safe for production by their own first-party docs — this guide is direct about which is which. Orientation

What JetBridge is

Two additions sit on top of stock Concourse, built in sequence and now deeply intertwined.

Phase 1 replaces the worker/Garden/TSA/BaggageClaim stack with direct execution against the Kubernetes API: the web node talks to the cluster itself, and every step — task, check, get, put — becomes a pod. There is no concourse worker binary anymore.

Phase 2 builds an agentic workflow platform on top of that runtime: AI coding agents (and a few deterministic compute functions) run as typed, versioned workflow definitions — informally "workflow functions," since each has a typed input/output signature like a function call — over immutable, content-addressed inputs and outputs called snapshots. A ticket queue feeds work in; a durable run engine tracks execution independent of the disposable Concourse machinery that carries it out. One thing worth internalizing up front: an agent: node's output is stochastic — the same inputs can produce a different diff, review, or answer on a different run. Nothing downstream treats an agent's output as trustworthy just because the step exited zero; that's why validation, review, and human approval are load-bearing rather than decorative, and it's why an entire experiments subsystem exists — you can't unit-test a stochastic step the way you'd unit-test a deterministic one, only measure it statistically across repeated trials.

If a Concourse task is already a pure function — inputs in, outputs out — phase 2 just makes that literal for agents: a typed signature, a pinned version, immutable values on both sides.

That last divergence is also the deepest one, and it's worth naming directly rather than leaving implicit. Stock Concourse is fundamentally convergent: a fixed set of inputs, checked and re-checked, reduces deterministically to the same container image or deployment every time you run it. The agentic side is fundamentally generative: a snapshot of some state gets rendered, stochastically, into a candidate diff, review, or PR that has to earn its way to being trusted rather than being trusted by construction. That inversion is the reason the platform has machinery a plain deterministic pipeline wouldn't need — independent re-verification before promotion (a run isn't "done" just because the build exited zero, see Durable workflow runs), a human-approval gate a workflow author structurally cannot forge (Human approval & publishing), and a whole experiments subsystem for statistically comparing stochastic output across repeated trials (Experiments). None of it is ceremony for its own sake — it's what a generative step needs that a deterministic one doesn't.

The two phases share one execution backend. An agent: step and a plain task: step both come down to a pod scheduled by the same K8s-native runtime — the "agentic platform" is a control-plane layer (definitions, snapshots, runs, dispatch, approval, publication) sitting on top of ordinary pod-per-step execution, not a second runtime.

Two things are easy to miss and matter for operating this cluster:

  • The artifact daemon is load-bearing for both phases, and its role just split in two. It started as phase 1's answer to "how do pods pass artifacts to each other" — that story is unchanged for ordinary pipeline artifacts, which stay node-local and peer-mirrored. But agentic snapshots (and checkpoint archives) now treat the daemon's local disk as a disposable cache, with an opt-in GCS-backed store called Hangar as the actual durable authority behind it. See the runtime section for exactly where that split is enforced.
  • ATC now holds real provider credentials directly — the old separate publisher gateway is gone. A prior design kept a deployment-owned HTTPS service outside ATC's trust boundary as the only thing that could reach a live Git host. That gateway has been fully removed, its reintroduction is blocked by both a Helm hard-fail and a CLI flag regression test, and ATC (the web node) now mounts the real write credential directly, in a Secret kept structurally isolated from every other credential the chart manages. This is a real, deliberate trust-boundary change, not an oversight — see Human approval & publishing.
Phase 1

The Kubernetes-native runtime

Pod-per-step execution, a mandatory node-local artifact cache with an optional durable backing store, and everything a `kubectl` reflex needs to keep working.

Pod-per-step, no workers

The web node registers itself as a synthetic worker named k8s-<namespace>, written directly into the database rather than negotiated over an SSH/TSA tunnel, and heartbeats it every 15 seconds against a 30-second TTL. Every step — task, check, get, put — becomes one pod, named deterministically from pipeline metadata and labelled with concourse.ci/pipeline, concourse.ci/job, concourse.ci/build, and concourse.ci/step for easy kubectl filtering. Pods idle on a pause loop so the web node can exec the real command via the Kubernetes exec API — this is what gives full stdin/stdout/stderr separation and makes fly intercept work: it execs a new shell into the same still-running pause pod.

A small in-pod shell supervisor wraps every task/agent command specifically so a build survives a web restart: if the web pod dies mid-step, the exec session's pty closes and the child gets SIGHUP, but the supervisor keeps the real process running and a freshly-reconnecting web replays the log from the start and waits for the exit file, rather than restarting the command from scratch. This is real, load-bearing crash safety that predates and is independent of the newer checkpoint/recovery feature described in Checkpoint & crash recovery — though that section also covers a real gotcha where checkpoint-enabled steps opt out of it.

The artifact daemon Live · mandatory

A DaemonSet — one pod per node — runs a small HTTP server over node-local storage and acts as the artifact cache for the whole cluster. It is not optional; the web node refuses to start the Kubernetes runtime at all without it configured (--kubernetes-artifact-daemon-host-path).

For ordinary pipeline artifacts (task/check/get/put outputs), the story is unchanged from the original design: the daemon holds content independently of any producing pod, so a downstream step's input fetch never depends on an upstream pod still existing, and content is peer-mirrored to a configurable number of nodes after every write — no cluster-wide read-write-many storage class is required.

For agentic snapshots and checkpoint archives, the daemon's role has changed: its local disk is now explicitly a node-local, on-use cache, not the durable authority. The daemon reserves a separate snapshots/ key namespace with its own handlers — snapshot PUT/GET/DELETE never triggers the ordinary peer-mirror path at all — and, if configured, backs that namespace with Hangar, a durable, provider-neutral (GCS-backed today) object store.

Hangar: what it actually solves

Hangar exists because node-local-plus-peer-mirror is not durable enough for content you can never afford to lose — a sealed snapshot, or a checkpoint archive that's the only copy of an interrupted agent's workspace. Object identity is the SHA-256 of the uncompressed canonical content, stored zstd-compressed under a deterministic key (hangar/v1/<kind>/sha256/<digest>.tar.zst). Writes are create-only (a GCS conditional write that only succeeds if nothing exists at that key yet); a write that loses the race re-verifies the winning object is bit-identical rather than erroring, so retrying the same content is always safe. Every read and delete is generation-pinned — scoped to one exact GCS object version, with a second read-back check to catch a concurrent mutation mid-verification — so an "immutable" object can't be silently swapped out from under a reader. The daemon verifies restored bytes against the requested digest a second time on its own side before trusting Hangar's response.

Enabling it is a chart-enforced pairing — agentSnapshots.enabled: true requires artifactDaemon.hangar.bucket, or the Helm render fails outright:

agentSnapshots: enabled: true artifactDaemon: serviceAccount: annotations: iam.gke.io/gcp-service-account: concourse-hangar@project.iam.gserviceaccount.com # workload identity — never mount a static key hangar: bucket: concourse-agent-snapshots networkPolicy: enabled: true hangarEgressTo: - ipBlock: {cidr: 198.51.100.32/32} # operator-specific GCS Private Service Connect address
Fixed: the daemon used to crash-loop on an unset zstd level

Until fix(hangar): default an unset zstd level instead of failing closed, the daemon's zstd encoder was configured without a compression level — cmd/artifact-daemon/main.go constructs hangar.GCSConfig{} without setting ZstdLevel, leaving it at Go's zero value, which the store's own startup probe rejected as "unknown encoder level", fatal via os.Exit(1). Every Hangar-enabled daemon crash-looped immediately under precisely the configuration docs/operations/hangar.md describes as correct, and no existing test caught it since every test set the level explicitly. The fix treats an unset level as "use the default" inside newGCSStore itself — not just at the one call site that happened to omit it — so a future caller can't reintroduce the same crash. If you're running an older build, this is exactly the symptom to look for.

Two deferred gaps are worth monitoring rather than blocking on: a daemon PUT can commit an immutable Hangar object and then crash before ATC durably records its location, leaving a harmless-but-unreachable orphan object (no reconciliation job exists yet to reclaim these); and hangarEgressTo is only enforced when the operator also turns on artifactDaemon.networkPolicy.enabled — leaving that off (the default) means Hangar egress is unrestricted by design, with no "hardened profile" that forces it.

Garbage collection

A reaper component runs on the default 10-second component-polling interval (it has no dedicated flag of its own) and deletes pods the database has marked for destruction. Artifact cleanup is an HTTP delete against the owning node's daemon rather than an exec-based rm inside a live pod.

Security posture & RBAC

The web pod's namespaced role covers the obvious pod lifecycle permissions (get/list/watch/create/update/patch/delete on pods, pod exec, and pod logs), plus several things worth knowing about explicitly: it can create and delete secrets (used for per-run agent credentials, described in Execution, budget & credentials), read PVCs, and patch both Deployments (its own, for the worker-registrar heartbeat) and DaemonSets (so a self-upgrade rollout check on the artifact-daemon doesn't hang). A separate cluster-scoped role grants read-only access to secrets and nodes, used for cross-namespace credential resolution and artifact-daemon peer IP lookup. The chart disables ambient service-account token automount on the web pod and instead projects a bounded, roughly one-hour API token, CA, and namespace directly into the web container — init containers never receive that credential at all.

Phase 2

How a change gets made

Every agentic execution — a ticket, a manual run, a retry, an experiment cell — moves through the same six-stage shape. The sections that follow work through these same stages in roughly the same order, though a few — Bind & admit spans Durable workflow runs and Tickets & dispatch; Render & execute spans Workflow definitions and Execution — each cover more than one stage, so don't expect a section titled exactly after a stage name.

Six stages sounds like a lot, but in practice a human only ever touches two of them directly: you capture whatever inputs the change needs (or a ticket, or a declared resource source, does it for you), and — if the workflow declares one — you resolve a publish approval at the end. Bind, render, seal, and promote all happen automatically once a run is admitted. Mapped onto the get/task/put comparison above: capturing a repo's current commit as a snapshot is the get; the workflow's nodes running end to end and sealing their outputs is the task (repeated, chained, however many nodes the definition declares); and — only if the workflow author bothered to declare it, and only through a lane that isn't gated closed — an approved, published change is the put.

  1. 1
    Capture

    Live or mutable state — a pipeline resource version, a ticket's current text — is sealed into an immutable, typed snapshot. This is the only door from the outside world into the agentic platform; nothing downstream ever reads a live system directly.

  2. 2
    Bind & admit

    A durable workflow run is created, binding exact snapshot IDs to a pinned, promoted workflow definition version via an opaque, tamper-evident launch envelope. One admission engine handles every origin — manual, ticket dispatch, retry, experiment cell, automatic resource-source trigger — so they all get the same guarantees.

  3. 3
    Render & execute

    The definition renders into an ordinary one-shot Concourse pipeline. Every declared node — a deterministic task: or an LLM agent: — runs as its own pod, using the same K8s-native execution described above.

  4. 4
    Seal

    Each node's output is captured, content-addressed, validated against its type, and sealed as a new snapshot the moment its producing node finishes — not when the whole run finishes, and not only for outputs the definition declares publicly.

  5. 5
    Promote

    Only once the entire run succeeds — re-verified against durable evidence, not just trusted from the build's exit code — do its declared outputs become the run's public, durable result set. A failed or partial run leaves its intermediates invisible forever, even though the bytes still exist.

  6. 6
    Publish (optional)

    A workflow that declares a publish_snapshot node — gated by a durable human-approval wait — hands its result off for delivery to a real git host. Most workflows stop at step 5.

A quick-reference glossary before the deep dive:

Snapshot
An immutable, typed, content-addressed value. The only unit of data that crosses a workflow's typed boundaries.
Workflow definition
A versioned, typed function signature plus a Concourse DAG that implements it. Imported, then promoted to "live."
Reusable node
A separately versioned, single-step function a workflow can compose in by reference — a shared library of typed functions.
Durable workflow run
The crash-survivable execution identity for one invocation — outlives the disposable build that carries it out.
Ticket
A mutable work-item queue entry. Not an execution identity — it dispatches into a durable run and stays a thin projection shell.
Dispatch
The act of turning a queued ticket into a bound, admitted workflow run. Manual always works; auto-dispatch is a runtime toggle.
Publish
The one side-effecting primitive. Direct-Git works today; the newer provider-native PR lane is implemented but gated off.
Experiment
A/B comparison of workflow (or single-node) variants against pinned fixtures, using the exact same run engine with an extra admission gate.

"Admission" does double duty below — at promotion time it means passing the compiler's type-checking proof (a workflow definition is "admitted" into the live/promoted state); at run time it means passing the durable-run engine's binding and budget checks (an invocation is "admitted" into a run). Same word, two different gates on two different objects at two different times.

Phase 2

Snapshots

The immutable, typed value that everything else in the agentic platform is built around — think of it as an extension of the resource-version idea you already know, not a new concept from scratch.

If you already know Concourse resources, start from what's the same: like a resource version, a snapshot is a specific, immutable, pinned "version" of some content that a step declares as an input or output, and that you can reference by an exact ID later. A workflow's repository input and an ordinary pipeline's source resource are conceptually the same kind of thing — a versioned view of a git repo at some commit. Now the differences, which matter more than the similarity: a resource version is usually a lightweight pointer at external state, fetched by a check loop the pipeline itself runs. A snapshot is the opposite — the platform actually stores the content, content-addressed by its own digest, and it's sealed once by an explicit act (see "Resource capture" below) rather than continuously re-checked. Once sealed, a snapshot never changes and is never re-fetched.

A snapshot is a typed, content-addressed blob — its identity is really a (type, digest) pair, where the digest is a hash of the canonicalized content rather than the raw upload, so semantically identical output converges on one digest no matter how the producer happened to write it. Sealing a duplicate is cheap: if a verified copy of that exact digest already exists, it's reused and nothing is re-uploaded. Concurrent producers of the same content are serialized so two racing steps can't corrupt shared storage.

Storage rides the node-local artifact-daemon fleet described in the runtime section, under its own reserved key namespace and mandatory TLS — snapshot bytes never cross the cluster network unauthenticated — with an opt-in durable Hangar/GCS backing store behind it.

The type registry is fixed, not configurable — 20 types today

Every snapshot type is a compiled-in Go validator, built identically into both the web binary and the standalone function-runner binary. There is no runtime or configuration path that registers a new type; adding one is still a code change and a coordinated redeploy of both binaries. The current, exact, full list of 20:

opaque/v1 repository/v1 repository-change/v1 review/v1 work-item/v1 log-bundle/v1 measurements/v1 validation/v1 upgrade-request/v1 upgrade-report/v1 database-snapshot/v1 deployment-snapshot/v1 audit-findings/v1 diagnosis/v1 consultation/v1 question/v1 human-answer/v1 pull-request/v1 pull-request-response/v1 publish-impact/v1

Four of these are new since the platform's last major audit — consultation/v1, pull-request/v1, pull-request-response/v1, and publish-impact/v1 — all added for the agent-broker and PR-publishing work below. selection/v1 is gone: its one load-bearing role (the candidate subject) was folded into measurements/v1 some time ago and that hasn't changed.

Sealed records: one validation core for nine types Live

Nine of the twenty types — review/v1, diagnosis/v1, validation/v1, repository-change/v1, measurements/v1, consultation/v1, pull-request/v1, pull-request-response/v1, and publish-impact/v1 — share a common envelope (a record version, type, schema reference, subject list, and body) and a two-layer validator: a generic, JSON-schema-driven core checks structural shape before a much smaller hand-written Go layer checks type-specific business rules. This generalizes the validation engine for these nine record-shaped types — it doesn't touch the registration model above.

Evolving one of these types' shape appends a new schema-digest revision rather than editing in place: the previous revision is retained as superseded; reads accept either digest; a fresh seal only accepts the current one. This two-gate split exists because a single exact digest checked everywhere — including on read — would turn a schema bump into a silent data-loss event, failing every already-sealed record's re-validation instead of treating it as "an older but still valid version."

validation/v1 is now on revision 3 — a real trust upgrade, not a cosmetic bump

Revision 3 adds a required body.attestation block — the candidate digest, base inputs, the validation profile's digest, the pinned capability image and its digest, the workflow definition ID/version, and the toolchain string. This attestation is compiled by the server, not asserted by the agent: it's derived from a workflow's pinned dev_validation profile at admission time and hashed into a provenance value; a sealed rev3 record's attestation fields must match that server-held authority byte-for-byte, or the seal is refused. Revision 3 also requires every per-check log to be independently reopened and re-hashed against its declared digest and size at seal time — revision 2 never verified logs existed at all. Old rev2 records stay readable forever (they're simply never asked to produce an attestation or logs they never had); a rev3 record must have both.

Resource capture: the only door for live data

Because typed workflow nodes reject get, put, load_var, and top-level resources outright, there has to be some sanctioned way to pull an existing pipeline resource version into the typed world. That's resource capture: given an exact, already-known (team, pipeline, resource, version), the web node runs a small one-shot pipeline that fetches it and seals the result as a typed snapshot — reusing the same sealing path any workflow output goes through, so captured content gets identical validation and dedup. It's idempotent by a content-addressed operation key, so repeating the same capture call is safe.

# seal an existing pipeline resource version as a typed snapshot
fly -t TARGET agent snapshots capture-resource \ --pipeline=repo --resource=source \ --version=ref:0123456789abcdef... --type=repository/v1

A declared resource_sources: input on a workflow definition (new; see Durable workflow runs & resource-source admission) reuses this exact same capture machinery under the hood, just triggered automatically by a standing pipeline instead of a manual CLI call.

Retention is reference-counted across five classes (a binding, a run, a workflow promotion, an experiment fixture, or an explicit pin) that together decide when a digest's physical replicas can be reclaimed — the manifest and lineage stay as durable history regardless; only the physical bytes have a retention-governed lifetime.

Team ownership is now direct, and cross-team grants are gone

A snapshot's manifest now carries a mandatory team_id column directly — content deduplication is team-scoped, not global, so two teams producing bit-identical output each get their own manifest row (the underlying bytes still dedup once at the storage layer, so equal content is never physically stored twice). The old cross-team agent_snapshot_grants sharing table — previously modeled in the schema but never wired to anything — has been dropped outright, not merely left unused. If you want cross-team snapshot sharing, it doesn't exist in any form today; don't describe it as dormant scaffolding, describe it as removed.

New authoring/derivation packages worth knowing about

Two packages new since the last audit are infrastructure for how outputs actually get produced and reasoned about, not optional add-ons:

  • The managed output builder

    A fixed, non-authoritative authoring surface an agent pod uses to stage and preflight a typed output before the step ends — it reopens and re-hashes its own inputs against server-declared digests, stages writes atomically with rollback on any failure, and structurally cannot seal anything itself. The real seal always happens later, independently, when ATC reopens and re-validates the produced tree after the pod has exited. This is a hard trust-boundary split: the in-pod tool gives an agent fast local feedback on its own mistakes; only ATC's own independent re-validation can actually mint a snapshot.

  • Deterministic offline repository diffing

    Derives repository-change projections (the file list, +added/-removed counts, the unified diff the web UI renders) from already-local immutable Git objects only — it never resolves a remote and never fetches, replacing an older, now-retired web-node mirror/fetch mechanism. This is what actually powers the in-app diff viewer described in The operator surface today.

Phase 2

Workflow definitions

A versioned function signature, compiled from a directory of prompt/skill/config files into an ordinary Concourse DAG — plus a type-checker that treats admission as a proof obligation, not a lint pass.

Source, import, and promotion

A workflow's source is a directory: a workflow.yaml plus whatever prompt, system-prompt, context, and skill files it references. workflow.yaml is now the preferred filename; the legacy workflow.yml still works, but if a directory somehow has both, .yaml wins outright and the .yml content is never even consulted. Every seed workflow in the repo has already been renamed to .yaml. fly agent workflows import packages that directory and compiles it — resolving file references into literal content, expanding any declared capabilities and broker profiles into sidecars (below), and marking every node hermetic. Import is deliberately permissive: it only has to compile and type-check, so an author can inspect a draft that couldn't actually run yet. Promotion is strict: --set-live additionally fully renders the definition, re-validates every runtime dependency is immutable (no file-backed task configs, no unresolved variables), and only then can a version become live — backed by a database constraint that makes it structurally impossible for a pre-v3 definition to ever be promoted again.

Here's what's actually inside that directory — trimmed from the real version-upgrade-v3 seed (its full plan has three more nodes; see the worked example for the whole thing):

# agent/workflow/seeds/version-upgrade-v3/workflow.yaml schema_version: 3 name: version-upgrade signature_version: 1 inputs: - name: repository type: repository/v1 - name: request type: upgrade-request/v1 outputs: - name: change type: repository-change/v1 from: approved-change # must match an output name below plan: - agent: upgrade function_id: upgrade # stable identity — addressable for extraction / experiments budget_slice_usd: 10 prompt_file: prompts/upgrade.md inputs: [repository, request] outputs: [candidate-change, report] input_types: repository: {type: repository/v1} request: {type: upgrade-request/v1} output_types: candidate-change: repository-change/v1 report: upgrade-report/v1 # ...review, validate-and-ask, await_snapshot, enforce-approval follow
fly -t TARGET agent workflows import agent/workflow/seeds/version-upgrade-v3 --set-live

Two things to notice against the get/task/put comparison in the overview: inputs/outputs at the top are the workflow's own typed signature (what a caller binds snapshot IDs to, and what gets promoted on success) — everything under plan is the actual Concourse-shaped DAG that computes them, node by node, exactly like a pipeline's plan:. function_id is what makes a node individually addressable later (see Experiments) — it has to be stable and unique within the definition, but otherwise means nothing to the compiler.

Typed nodes are the whole admission model

Every task: or agent: step in a workflow is a "typed node": it declares a stable, unique function_id and must have exact type coverage between its artifacts and its declared input/output types. The compiler's type-checker walks the entire DAG — through do, in_parallel, try, retries, timeouts, hooks, everything — proving that snapshot data actually flows the way the signature claims, and it rejects, structurally, anything that would break that proof: top-level resources or variable sources, get, load_var, put, set_pipeline, and across (rejected specifically because it mints new runtime plan IDs after admission, which would break exact frozen provenance). A prototype run: step gets its own explicit, purpose-built rejection message rather than falling through to a generic error, for the same underlying reason — Concourse plans a prototype run without a resolvable source identity, which can't meet the frozen-provenance bar either. There's no untyped island possible in an admitted v3 workflow — it's proven, not just conventionally true.

Under the hood this reuses Concourse's own machinery rather than inventing a parallel runtime: promotion literally compiles a definition into a content-hash-named, one-shot Concourse pipeline template — identical content always reuses the identical template rather than minting a new one every single admission. "Workflow" is a control-plane concept layered on ordinary pipelines, not a separate execution engine.

Capability sidecars & hermetic execution

A workflow grants an agent tool access by declaring a named capability — an exact-digest-pinned container image plus one TCP port. The compiler expands each declared capability into a real sidecar and a generated <NAME>_MCP_URL environment variable; an author cannot author their own MCP endpoint, inject a sidecar directly, or reuse a reserved name (dev, platform, gateway — retired privileged runtime roles) to smuggle in undeclared access. Every task and agent node is unconditionally hermetic — deny-egress network policy applied at compile time, not something an author can opt out of.

That raises an obvious question: if egress is denied, how does an agent: node ever reach Anthropic's API? Two exceptions exist, and only one of them is automatic. The platform itself carves out the same-node path to the local artifact daemon, which is what lets a hermetic pod fetch its own inputs — that one requires no configuration. Reaching any external HTTPS endpoint, including the model provider, is not automatic: the chart's hermetic-egress policy is emitted with a hard-deny (egress: []) unless an operator explicitly sets networkPolicy.hermeticEgressTo. The documented pattern is to point that at a single in-cluster egress proxy rather than opening a raw internet-wide allow-list from every hermetic pod. Whether this is enforced in practice depends on the cluster's CNI actually implementing NetworkPolicy; on a CNI that doesn't, the object is created but has no effect. Skipping this configuration on a policy-enforcing CNI doesn't break something subtly — it means no agent step can call the model at all.

A second, independent tool-access mechanism: broker profiles

Since the last audit, an agent node gained a second way to get extra capability — declaring a broker_profiles: entry, which lets it synchronously call out to a completely separate, sandboxed child agent for a static review or a bounded consult. This is a materially different mechanism from a capability sidecar, not a variant of it:

plan: - agent: implement function_id: implement prompt: implement broker_profiles: - {tool: consult_agent, tier: balanced, effort: high} - agent: review function_id: review prompt: review broker_profiles: - {tool: request_review, tier: frontier, effort: medium}

An author supplies only a neutral {tool, tier, effort} selector — never an image, model, or provider. Those get resolved server-side, at compile time, against an operator-only deployment catalog; if no catalog is configured, compiling a definition with any broker_profiles fails outright with "workflow: broker catalog is required". The resolved profile (model, provider, harness, worker image, credential slot) is frozen by content hash into the compiled definition, so a later catalog edit can never silently change what an already-promoted workflow does. See Agent execution broker for the full mechanism, including a real, self-declared reason not to turn this on in production yet. There are no seed workflows using broker_profiles in the repo today — it's fully implemented and compiler-tested, but with zero first-party worked examples.

Worth knowing
  • A single top-level task or agent node can be extracted out of its parent workflow into its own standalone, independently renderable target, addressed as workflow@version#function_id. This isn't a curiosity — it's exactly how you iterate on one step of a chain without re-running everything upstream of it: pin an earlier node's output snapshot as an experiment fixture, then compare two extracted versions of a downstream node against that same fixture. See Experiments. This is a genuinely different mechanism from reusable nodes below — extraction pulls a leaf back out of an already-compiled workflow with no prior declaration required; a reusable node is composed into one or more workflows and has its own independent, versioned identity. Both are real and coexist.
  • Two step-level keys from the pre-v3 grammar, a gate policy and a judge reference, still fail to compile if an author writes them on a step — but the mechanism changed: there's no longer a bespoke shape-checker for either, only the same generic strict-unknown-field rejection every other unrecognized key gets. The visible behavior (compile failure) is unchanged.
  • A disposition_output field is compiled, validated, and authored by most of the seed workflows, but nothing in the live dispatch or ticket code reads it yet.
Phase 2

Reusable nodes Live

An immutable, independently versioned single-step function that workflows can compose by exact reference.

A reusable node packages one typed task, agent, or publish_snapshot leaf with its prompts and assets. Create or capture exact typed input snapshots, import the package and retain the exact returned version, then run that unreleased version through the ordinary durable admission engine. Inspect show-run, follow its exact fly watch -b build hint, download and inspect the sealed typed output, and only then release the tested version.

Released nodes compose into workflows as uses: NAME@EXACT-INTEGER; there is no latest channel. Consumer discovery and explicit upgrades create new unpromoted workflow revisions without rewriting existing definitions or historical runs. See the reusable-node operations guide for the runnable lifecycle, portability and budget rules, release compatibility, and upgrade procedure.

Phase 2

Durable workflow runs & resource-source admission

A crash-survivable execution identity, deliberately separate from the disposable Concourse build that actually carries it out — plus a genuinely new way for a workflow to auto-trigger off its own declared resource inputs.

Deleting the build, pipeline-run, or instance-pipeline behind a workflow run doesn't delete the run — those links are nullable, and the run keeps its own captured copy of the plan and config it executed. This is what makes the run ID a stable thing to link to, cite in an audit log, or retry against, independent of whatever GC has done to the disposable execution plumbing underneath. The same durability extends one level up: a workflow definition version can only ever be deprecated, never deleted — there is no exposed delete operation for one at all — and the database enforces this structurally (a run's foreign key to its definition version is ON DELETE RESTRICT). A run you dispatched against a since-deprecated or since-superseded workflow version stays exactly as viewable as one from five minutes ago.

One admission engine — a restartable, crash-resumable state machine — serves every invocation origin: a manual run, a ticket dispatch, a retry, an experiment cell, or an automatic resource-source trigger (below). That's a deliberate design choice: every origin gets identical guarantees around idempotency, budget admission, and secret preparation.

The launch envelope: binding trusted config to a caller's params

Launching a run requires an opaque ExecutionEnvelope minted only from a trusted, already-rendered definition — its canonical config bytes and content hash are private fields no outside package can read or forge. This closes two distinct threats: a caller can't pair the params from one render with the persisted config of a different definition (a zero-value or mismatched envelope is rejected outright, proven by a direct regression test), and a caller can't substitute their own value for a parameter a trusted resource-source binding already fixed — the binder unconditionally overlays server-selected values and errors if the caller's own value disagrees. This is a different, complementary mechanism to the one that protects which Kubernetes secret gets mounted for a live agent step (see Execution, budget & credentials) — one protects admission-time launch integrity, the other protects runtime credential identity.

Public output promotion isn't just "the build passed"

Every output snapshot gets bound to the run the moment its producing node finishes, but it stays invisible — an intermediate candidate — until the entire run succeeds. At that point the platform independently re-verifies the declared outputs against durable evidence (does a real, unambiguous producer exist for each one, is the content actually available, is retention correctly claimed) before flipping them public. A run whose build technically exited zero can still terminate as failed or errored if that re-verification doesn't check out.

A failed or partial run's outputs simply never get promoted. The bytes aren't deleted — they remain visible through snapshot history — but nothing treats them as the run's result.

The reconciler Live

A background component polls for runs stuck mid-admission, drains pending human-wait resolutions, and finalizes cancellation — closing the crash windows an in-memory-only state machine would otherwise leave open. It's the reason a resolved approval always replays as the exact same answer even after a restart, and the reason a canceled run's open waits reliably get closed rather than orphaned. This is also now the only terminalizer for tickets: ticket-state projection was folded directly into this always-on reconciler, so there's no longer a second, narrower loop specifically for tickets — disabling the ticket dispatcher component (see Tickets & dispatch) no longer risks killing the safety net that moves a ticket to needs_review, because that responsibility never lived there in the first place.

Resource-source admission: a workflow can now auto-trigger off its own inputs Live

This is genuinely new, and it's a real answer to "can a workflow auto-trigger the way a Concourse job does" — with an important scope limit: it's about one workflow's own declared resource inputs, not about one workflow's output triggering a different workflow.

A workflow definition can declare resource_sources alongside ordinary resources — the only place `resources:`/`resource_types:` are still legal in a v3 definition:

resources: - {name: repository, type: git, source: {uri: https://example.invalid/repository.git}} resource_sources: - {name: repository-source, resource: repository, type: repository/v1, trigger: true} plan: - agent: inspect function_id: inspect prompt: inspect inputs: [repository-source] input_types: {repository-source: {type: repository/v1}}

At promotion, this compiles into a plain, non-template Concourse pipeline with one job (admit) containing one get per declared resource source — this is a genuinely different, "standing" pipeline model from the workflow's own one-shot execution template, activated in the same transaction that flips the definition live. A partial unique index enforces at most one active standing pipeline per (team, workflow name) at a time; promoting a new revision demotes the previous one to draining rather than leaving two ambiguous admitters alive.

With trigger: true, that standing pipeline's own Concourse scheduler creates new builds exactly like any other triggered job when a new resource version appears; a background reconciler notices the successful build and drives capture-then-launch automatically. A manual fly agent workflows run against a resource-source-bearing definition still works too — it triggers the same standing pipeline's job inline rather than requiring you to wait for one. Either way, the winning selection is captured once, idempotently, into a Hangar-backed snapshot, and that exact same admission is reused — never re-derived — for the first run and for every retry, replay, or experiment child that follows from it.

The pre-existing, fully manual fly agent snapshots capture-resource is untouched and still the general-purpose, operator-initiated way to capture any resource version independent of any workflow's own declarations.

Naming collision worth knowing

There are two unrelated components both informally called "the reconciler." This one is the durable-run engine's crash-safety net and covers every invocation origin, including resource-source admission. A separate reconciler drives the provider-native PR-monitoring standing pipeline (Provider-native PR publishing) — architecturally the same underlying registry mechanism (the `active`/`draining`/`archived` state machine), just keyed by a PR binding instead of a workflow definition. They operate on different tables for different consumers.

Phase 2

Tickets & dispatch

The ticket is the human-facing queue entry. It is deliberately not the thing that actually runs.

A ticket carries title, body, a structured spec/plan/tasks breakdown, its captured snapshot references, and the queue/dispatch/disposition controls a human operates. It is a projection shell — everything about actual execution (the review, the diff, the outcome) belongs to the durable run it dispatched into, reached only through a canonical link. The state machine is exactly draft → queued → running → needs_review → closed; there is deliberately no merged/sent-back/abandoned/failed state mirrored onto the ticket itself — those live only on the workflow run and its outcome (Workflow outcomes).

Not all of those fields are required up front: creating a ticket only ever needs a title and body. The spec and the plan's tasks are separate, later submissions — in practice, something an agent fills in progressively as it investigates the ticket, not a form a human has to complete before filing one.

Cost is the one deliberate exception to the projection-shell split: spend is tracked against agent_cost_ledger.ticket_id directly, not against the run. TicketRemaining is computed as the ticket's budget minus the sum of ledger rows for that ticket ID — so cost accumulates across every dispatch attempt a ticket has ever had, rather than resetting each time a new run gets bound to it. If you're reconciling spend, query by ticket, not by run.

# real, verbatim CLI fly -t TARGET agent tickets create --title "Fix flaky worker GC test" \ --repo tdmtrader/concourse --target-branch main --dispatch # → created ticket #42 (draft) # → ticket #42 is now queued # → dispatched ticket #42 as workflow run <id> (pipeline run 118) fly -t TARGET agent tickets dispatch --id 42 --workflow code-review-v3 fly -t TARGET agent tickets list --state needs_review --repo tdmtrader/concourse
There is no automated ticket ingestion from git or an issue tracker

The diff-derivation package (renamed from gitcheck to repodiff since the last audit, capability unchanged) is a diff-math library — given two already-local commit IDs it derives a repository diff; it never resolves a remote and never fetches. The only ways a ticket comes to exist are --origin web or --origin fly — both human-driven. A prior, larger pull-request package might look like an ingestion path at a glance, but it starts downstream of an already-accepted review and has no code path that creates or updates a ticket — see Provider-native PR publishing. A prior retrospective origin (for a platform-initiated follow-up ticket) has been retired outright along with the principal identity that would have filed it — it is no longer a valid origin at all, not merely unused.

Auto-dispatch is a live runtime toggle Live

This is current, maintained code — not something superseded or on its way out; the Live pill means exactly that, distinct from the Parked/Dormant/Gap/Gated pills used elsewhere in this guide for things that aren't. Manual dispatch (fly agent tickets dispatch) always works regardless of any setting. Automatic dispatch of the whole queue is a three-state mode — off / paused / active — stored as a single hot-read row, changeable with no restart. There is no longer a boot flag for this at all (the old --agent-dispatcher-enabled/-max-attempts flags were deleted outright) — the database row is now the single source of truth for mode, seeded to off by migration.

fly -t TARGET agent dispatcher resume # auto-dispatch every queued ticket fly -t TARGET agent dispatcher pause # stop new auto-dispatch, keep the always-on reconciler alive fly -t TARGET agent dispatcher off # fully dormant

Any transient error reading the setting fails safe to paused rather than silently resuming against an operator's explicit pause. The same three states are readable, and admin-settable, from a banner on the web UI's ticket-queue page.

A small advisory linter — renamed from SpecLint to WorkItemTextLint, and now server-side only — scans ticket text for phrasing known to trigger the Claude CLI's own usage-policy false refusals (certain security/surveillance-adjacent words, each backed by a documented real incident), surfacing warnings on the dispatch response rather than blocking anything.

Dead config, and a stale help string

A configured max-attempts flag for the dispatcher is accepted and threaded through but not currently consulted anywhere — a terminal run always requires human review instead of an automatic retry ceiling. Separately, the fly CLI's own --origin flag help text on agent tickets list still advertises a retired retrospective value; the server now rejects it outright (ValidOrigin only accepts web/fly), so that help text is simply wrong and should read (web, fly).

Phase 2

Reviews & feedback

A first-class human-grading feature with its own routed web page — easy to miss, because everywhere else in this guide "review" only comes up as the review/v1 snapshot type.

Reviews and feedback are two related but distinct APIs. A review is an agent's own findings for a build or snapshot — and there is exactly one writer for it, by design: sealing a review/v1 snapshot. There is no separate "submit a review" HTTP route; a review comes into existence as a side effect of a step's typed output, attributed to whoever was already authorized to create the build that produced it. Feedback is a human grading one of those findings against a fixed verdict vocabulary — accurate, false_positive, noisy, overly_strict, partially_correct, missed_context. Both are wired into the web UI as their own routed page — /teams/:team/agent-reviews is a top-level nav destination alongside workflows, tickets, and experiments, not a tab folded into one page.

The verdict auto-classifier is gone by deletion, not merely dormant

A prior audit of this guide flagged a fully-wired-but-zero-caller auto-classifier endpoint as dead code worth cleaning up. It's since been deleted outright, along with a companion findings-lookup route, as part of a broader teardown of an older, now-retired agent surface — there is exactly one feedback handler method left (SubmitFeedback), and a route-registration test explicitly asserts the old routes must never come back. If you're looking for a keyword-based auto-classifier here, it no longer exists in any form.

Phase 2

Workflow outcomes

A durable disposition ledger for individual outputs — a different axis from both run status and the ticket-review split above, and worth not confusing with either.

A workflow outcome records the disposition of one specific output snapshot — accepted, rejected, merged, or abandoned — independent of whether the run that produced it succeeded. Because it's keyed to an output rather than to the run, a single run can carry several independent outcome rows. There's no fly command for it; the only surface is a read-only card on the durable-run detail page.

This is the third thing in this guide named "outcome," and none of them are the same

Watch the vocabulary: agent/schema's RunOutcome (ok / no_output / running / parked / failed / errored / aborted / unrecorded) is the fused build-status-plus-run-status display truth fly agent runs renders as a badge — explicitly designed so it never shows green when the underlying build is red — a completely different axis from this section's Disposition vocabulary, and the two systems never read from or write to each other.

This ledger is advisory record-keeping, not an enforcement layer. Marking an output rejected has no runtime effect on publication: publish_snapshot is gated entirely by its own await_snapshot/approval machinery (see Human approval & publishing), independent of this API. A human can PUT disposition=rejected here and an already-approved publish can still complete right alongside it — this hasn't changed. What has changed: the publication-state vocabulary was narrowed to just not_requested/published after a migration made the old pending/failed tokens permanently rejectable, and the human-facing modify path was tightened to disposition/labels only — it has no publication fields at all, so a human can never claim publication evidence through this route.

Dormant write path — unchanged

Store.Record — the one method whose request type can set publication state directly — is fully implemented and unit-tested but never called in production: the HTTP handler method literally named Handler.Record is a false cognate that actually calls store.Modify, not store.Record. This is unchanged from the last audit.

Phase 2

Execution, budget & credentials

Two binaries, one image, one execution backend — and a credential story that's still simple for the main agent step, now sitting alongside a wholly separate one for broker child calls.

Two binaries, same pod model

The agent-runner image ships two Go binaries. agent-runner is the image's entrypoint and handles agent: steps: it waits for every declared capability sidecar to report healthy, then execs the Claude CLI with the step's budget slice, a generated strict MCP config (so a repo-committed project MCP file can't sneak in an undeclared tool), and a flight recorder capturing the transcript and cost. function-runner is a second binary that ordinary task: steps invoke by name for deterministic compute — today that's the merge/direct-Git function described in Human approval & publishing.

Neither is a separate execution backend. Both run as ordinary K8s-native pod-per-step tasks on the exact same image; the only difference is which step type a workflow author chose and which command line that pod ends up running.

Budget: three checkpoints, one hard gate

Spend is checked at three points that never double-count: a fast pre-check at dispatch time, a per-step clamp right before an agent pod starts (floored to whatever headroom the ticket has left), and an append-only ledger write after the step completes. The actual hard gate — a deployment-wide daily cap — is a separate mechanism: when set to a nonzero amount, admitting a new run takes a single database-wide lock shared with ledger ingestion and experiment budgets, so multiple web nodes can never independently over-admit against the same remaining cap. With that cap enabled, every agent leaf in every workflow must declare a finite, positive budget up front, and a attempts/across block anywhere in the workflow becomes inadmissible — the compiler rejects the node type on sight, unconditionally, so even one wrapping a plain task: or get: elsewhere in the same plan blocks the whole run, not just ones wrapping an agent.

The ledger is per-agent-step granularity, not per-run: one row per completed step, carrying separate input/output/cache-read/cache-creation token counts, turns, model, and a provider tag. It's also a genuinely generalized ledger — a live route accepts an arbitrary ledger entry from any authorized writer, tagged with one of six recognized spend sources, though in current practice only the ordinary agent-step source is ever actually populated by production code.

Flight recorder transcripts: captured, and now genuinely viewable

Agent-runner writes the raw claude --output-format stream-json --verbose output to a transcript file; the web node ingests it keyed on (build, plan) with a bounded tail and a truncation marker past that. A live, wired API route serves it back — and unlike a prior audit's finding, there is now a real, tested Elm viewer on the durable-run detail page: an "Agent transcripts" card lists one collapsible row per transcript, and opening a row renders the parsed entries (system/assistant/user/thinking/tool-call/tool-result/outcome) with a documented total-parsing contract — an unrecognized line degrades to a raw fallback rather than losing the rest of the transcript. If you were told transcripts have no UI consumer, that's now out of date.

What the dormant deterministic functions actually do Dormant

The maturity map calls gate/judge/repository-validate functions "fully implemented and tested" without explaining what capability is being left on the table. Gates run a policy-declared command catalog (build/test/lint) with 0-2 retries and a per-gate timeout, only in a workspace scoped full, producing a validation/v1 sealed record. Judge pins an evaluator version, a rubric, a pass threshold, and a budget, execs the claude CLI once with JSON output, and hard-fails unless the response covers every rubric dimension exactly — producing a measurements/v1 record consumed by experiment scorecards. Repository-validate typechecks a repository-change snapshot without publishing it. None of the three has a case in function-runner's mode-dispatch table today; wiring one up is real, unclaimed follow-up work.

Credentials: still simple for the parent agent step

The only credential ever injected into an agent-run pod's main container is an Anthropic token — resolved from a per-user vault, falling back to a shared platform service credential if the dispatching user hasn't vaulted their own. There is no per-run git credential anymore. Source arrives pre-captured as an immutable snapshot before the pod ever starts. That's unchanged, and it's worth being precise about the boundary: this credential lands as a Kubernetes secret reference on the main container only — sidecars, including a broker companion if one is present, never receive it.

The credential itself is wired in only after the server independently verifies the plan-declared run identity actually belongs to this build — closing a spoofing path where a crafted pipeline could otherwise claim another run's credential or misattribute spend to someone else's budget.

Vaulting a credential in practice

fly agent auth is entirely client-driven — there's no server-side OAuth exchange. With no --token, it prints instructions to run claude setup-token in a separate terminal and reads the pasted result off stdin. Two credential kinds are supported: anthropic_oauth (the default, from claude setup-token) and anthropic_api_key; admission tries OAuth first, then falls back to an API key.

fly -t TARGET agent auth # vault your own OAuth token fly -t TARGET agent auth --kind anthropic_api_key --token sk-ant-... fly -t TARGET agent auth --platform # admin only: the shared fallback credential fly -t TARGET agent auth --delete

Authorization here is looser than most of the agentic surface: the credential routes are gated by plain authentication, not the main-team-scoped check most other /api/v1/agent/* routes use (see Team scoping & authorization) — any authenticated user on any Concourse team can vault, inspect, or delete their own credential. The one exception is --platform, gated to admins, which targets the seeded, never-logs-in platform user.

Expiry is enforced silently at admission time: an expired vaulted credential is treated exactly like a missing one, and admission falls through — first to the user's other credential kind, then to the platform credential — only erroring the run outright if nothing unexpired is found anywhere.

Broker child credentials — a wholly separate, additive path

If an agent node declares broker_profiles (see Agent execution broker), its child executions use a completely different credential mechanism: operator-configured Helm secrets (agentBroker.credentials[], e.g. an OpenAI or Anthropic key) named by a credential_slot on the frozen profile, mounted as file-based Secret volumes onto the broker sidecar container only — never onto the main container, never derived from any user's vault. A given pod can therefore have the parent's Anthropic OAuth token on its main container from the per-user vault, and a completely independent, operator-managed credential on the broker sidecar, with the chart structurally forbidding the two Secret objects from ever being the same one.

Phase 2

Agent execution broker Gated · not promotion-ready

A sandboxed way for a running agent to synchronously call a second, operator-chosen model as a reviewer or consultant — fully implemented and wired, and explicitly, self-declaredly not safe to run in production yet.

The broker adds two synchronous MCP tools to an eligible agent node: request_review (a static review of an exact captured Git workspace) and consult_agent (a bounded answer to a caller-supplied question over declared snapshot attachments). The caller selects only a provider-neutral {tier: economy|balanced|frontier, effort: medium|high} pair — provider, model, native harness, credential slot, image, and limits are all operator-only and frozen at compile time (see broker profiles). Each child call gets a completely fresh harness context: no parent transcript, no user configuration, no live workspace — just its own image-owned instructions, the caller's prompt, and explicitly named attachments.

request_review doesn't require a commit — it captures the repository base plus staged/unstaged/deleted/renamed/executable/symlink/binary/nonignored-untracked state via a private Git index, verifies the result tree, then runs a deliberately static review: no tests, builds, formatters, or linters, the runtime image has no build toolchain, and every result records tests_run: false. Its output is exactly one validated review/v1 body — the same type the ordinary reviews/feedback subsystem already uses, so a broker-produced review can flow straight into publish/await snapshot steps naming it. consult_agent similarly returns exactly one validated consultation/v1 body.

Promotion blocker — this is a live, self-declared gap, not boilerplate caution

The broker's own documentation states plainly: the current child seccomp/process-group boundary is not yet accepted for deployment. A same-UID child may still be able to join the broker's process group and signal it through kill(0), and async-I/O ownership can provide another signal path. The packaged image is therefore build/test material, not promotion-ready, until that boundary receives human review, a code correction, and a live Linux regression on the managed cluster kernel/runtime. A seccomp filter does exist and is fairly extensive — it explicitly allows signaling one's own process/group while denying ptrace, process_vm_readv/writev, pidfd_*, kcmp, and arbitrary kill/tgkill targets — but the project's own review judged it insufficient to close the same-UID signaling class, and no later commit revisits it. Treat agentBroker.enabled as not cleared for production regardless of how complete the rest of the plumbing looks.

Deployment model & sandboxing

ATC owns catalog resolution, admission, short-lived capabilities, the durable child ledger, workspace/result sealing, and inspection. Jetbridge injects one managed companion sidecar only for an agent node whose frozen definition contains broker profiles — there is no broker Deployment or Service. The companion mounts the parent workspace read-only just long enough to capture it; the native harness then runs over that capture behind an unprivileged Landlock ABI 3+ filesystem boundary, able to write only its own per-call scratch and read only configured immutable runtime paths. The parent reaches the broker over loopback with a random per-parent bearer token; the child harness never receives a copy of it. Managed nodes require Linux 6.2+ with Landlock enabled, a compatible RuntimeDefault seccomp profile, and an immutable linux/amd64 broker image digest — a real infrastructure prerequisite most clusters won't already have.

Inspection

There is no fly command and no web UI page for it today; an operator inspects a child execution with a raw GET or not at all.

Phase 2

Checkpoint & crash recovery Gated · scaffolding is live, recovery never succeeds today

Durable, fenced, well-tested crash-safety machinery around a recovery decision that — for the one adapter this platform actually ships — always ends in a human being paged.

Answering the obvious question directly: no, an interrupted agent step does not resume mid-transcript today. There are two different crash scenarios, and only one of them touches this feature at all.

ATC crashes, the agent's pod survives — the older, unrelated safety net

Every task/agent step already runs under a small in-pod shell supervisor (see the runtime section) that survives an ATC restart cleanly: the real process keeps running, and a freshly-reconnecting web replays the log and waits for the exit file rather than restarting the command. The gotcha: once a checkpoint-enabled step's durable attempt is marked running, it stops using that fallback-capable attach path and switches to an attach-only call that hard-fails for a still-live pod with no exit annotation yet. In practice, this means turning checkpointing on removes the pre-existing "ATC crashed, nothing was lost" safety net for the remainder of that step's runtime and replaces it with a hard step failure — and no reconciler was found that sweeps a stuck running attempt back out of that state afterward. This is a real, unresolved rough edge worth knowing about before enabling the feature.

The pod or node is actually destroyed — the real checkpoint path

This is what the feature is actually for. On a genuine interruption (pod deleted, evicted, node lost, preempted), the step always allocates one brand-new, fresh replacement attempt — it never reattaches to or resumes a live process. Recovery then picks one of four modes, checked in order: native_resume (the LLM conversation itself continues — requires the adapter to prove session-export and resume capability), workspace_only (fresh pod, workspace restored from Hangar, brand-new call from turn one with a "this is a recovery" system-prompt note), checkpoint_zero (fresh pod, no archive restored, brand-new call from scratch), or manual_review_required (nothing automatic — a human decides).

For the shipped Claude adapter, the answer is always manual_review_required

The composition root hardcodes the recovery authority to nil for the production Claude integration, with the comment: "Production legacy adapters intentionally have no complete journal or recovery proof, so every interrupted source fails closed." The concrete adapter implements only the plain provider interface, not the recovery one — it has no Resume method and reports every capability as false. Searching the entire codebase, the recovery-adapter interface has zero implementations, in production or in tests. So regardless of how clean the effect journal is or whether a good checkpoint exists, every genuine pod-level interruption of a checkpoint-enabled Claude step ends the same way: the step is marked for human review and stops, with zero automatic replays. Even in the modes that would trigger for a hypothetical capable adapter, "resume" only ever restores the on-disk workspace — the model's own memory of the conversation is never restored, only a system-prompt note telling it this is a recovery attempt.

What is real and load-bearing: the crash-safety machinery around that failure. Every checkpoint mutation requires a fenced capability tied to one execution attempt, with the fence's authority timestamp sampled only after the relevant row lock is acquired — specifically so a lease can't be granted based on a stale, pre-lock-wait clock read. Interrupted attempts are immutable evidence; recovery always allocates a new, sequentially-numbered row rather than resurrecting the old one, enforced by a database trigger, not just application code. Retention is generous and correctly scoped: a source archive stays pinned for as long as any live recovery attempt still references it, even after it's been superseded, and diagnostic metadata survives 30 days past termination.

Enabling it, and what you get to observe

Off by default, gated behind two independent flags (--agent-checkpoint-enabled requires --agent-snapshot-enabled), and scoped only to schema-v3 hermetic agent steps that belong to a workflow run — ordinary ad-hoc pipeline agent: steps never touch it regardless of the flags. There is no dedicated Helm value block for this yet; a real deployment passes the flags through the chart's web.extraArgs escape hatch.

There is no UI element and no public API route — this is purely a backend-plus-metrics feature today. A real Prometheus alert set exists and is worth wiring up regardless of whether you trust automatic recovery: ConcourseAgentCheckpointCaptureFailures, ConcourseAgentRecoveryManualReviewRequired (severity critical — given the above, this is effectively "any checkpoint-enabled agent step was interrupted at all"), and ConcourseAgentCheckpointRestoreFailures. The operations guide's own runbook is explicitly a manual, log-and-database-inspection procedure — there is no dashboard for it.

Phase 2

Team scoping & authorization

Agent principals — a whole separate bearer-token identity system — have been removed outright. What's left is simpler, and mostly still pinned to one hardcoded team.

Principals are gone, not just undocumented

A prior edition of this guide described "agent principals" — a closed-scope bearer-token identity (reviews:write, tickets:read/write, metrics:write, costs:write) with admin mint/list/revoke. That entire system has been removed: the table is dropped by a migration whose own comment reads "preserving these rows would leave credentials that no current code is allowed to use," its down-migration deliberately restores only the empty schema shape with zero rows, there is no fly agent principals command, no route in the API, and no admin UI for it. A design-doc invariant states it plainly: "agent principals do not exist." If you're looking for a bot/service-account identity anywhere in this platform, there isn't one anymore.

What replaced each of the old write paths

There is no direct replacement mechanism — the paths principals used to gate collapsed into two categories. Reviews aren't "posted" by anyone; a review comes into existence as a side effect of sealing a review/v1 snapshot, attributed to whoever was already authorized to create the underlying build. Human feedback and tickets now require an ordinary authenticated Concourse user holding Member role (or admin) on team main — identity comes from the caller's own OIDC claims, the same mechanism used everywhere else in Concourse, with an explicit code comment warning that production wiring must supply real identity "so caller-controlled JSON cannot impersonate or overwrite another reviewer's feedback." Metrics and cost-ledger writes have no HTTP route at all anymore — they're purely server-internal bookkeeping the ATC process performs as a side effect of running a build it already controls; there was never really an external "write" boundary to authorize in the first place, and it's gone now in name as well as in practice.

The hardcoded-main-team claim is still true — for most of it

In practice, because the ticket/workflow dispatch pipeline itself is still wired to always operate as team main, every snapshot the pipeline produces today ends up owned by main anyway — but the authorization mechanism for snapshots is now genuinely team-generic, capable of a different team owning its own snapshots the moment something drives that pipeline under a different team identity.

Phase 2

Human approval & publishing

The one primitive allowed to have an outbound side effect — and a trust boundary that moved, on purpose, since the last audit.

The publisher gateway is gone. ATC now holds the real write credential directly.

A prior design kept publication credentials in a deployment-owned HTTPS service, deliberately outside ATC's own trust boundary — the framing was "ATC never holds a real GitHub/GitLab/Jira credential." That's no longer true, and it's a deliberate architectural change, not drift: the gateway transport, service, flags, and operator topology have been fully removed. A regression test asserts all nine of the old gateway flags are now unknown to the binary, and the Helm chart hard-fails the render if a values file still sets the old agentPublisherGateway key at all, with the message "has been removed; use agentPublisher." ATC (the web node) now mounts the real destination write credential directly, from a Secret kept structurally isolated at render time from every other Secret the chart manages — the policy document and the credential are two separate Secrets, and the chart refuses to render if they, or any other reserved Secret, ever alias each other.

await_snapshot is a durable human wait tied to an exact run, build, and question/answer snapshot pair. publish_snapshot is still the only workflow primitive that performs an outbound side effect — that core fact hasn't changed, only who holds the credential behind it and what destinations exist.

A workflow author cannot forge the approval

For a merge, a workflow must name a non-optional human-answer wait — but the approval question itself is server-generated, not author-supplied. Once the change snapshot exists, the server binds the concrete definition, run, build, and content digest, and seals a strict question that includes the publisher, mode, destination, target branch, and an intent digest over the full parameter map. Only a non-timeout answer that's exactly "approve," from the actual resolving human, is accepted. The base-commit assertion is derived server-side from the change snapshot's own sealed metadata and can never be authored in workflow YAML, so the approval question and the eventual publish call are mathematically guaranteed to agree.

Direct-Git delivery works today — real, verbatim syntax

The merge-delivery-v3 seed still works exactly as before, extended rather than replaced. Its await_snapshot/publish_snapshot pair, unchanged in shape, is real, live, and not gated behind anything except --agent-publisher-direct-git-enabled:

# agent/workflow/seeds/merge-delivery-v3/workflow.yaml - await_snapshot: merge-approval merge_approval: input: merged-change publisher: git-publisher/v1 destination: git.example/acme/widget parameters: {target_branch: main} approval_policy_version: engineering/v1 prompt: Land this rebased change on main? type: human-answer/v1 on_timeout: fail timeout: 72h - publish_snapshot: land-merge publisher: git-publisher/v1 input: merged-change input_type: repository-change/v1 destination: git.example/acme/widget mode: merge parameters: {target_branch: main} approval_policy_version: engineering/v1 approval: merge-approval
Operational trap — unchanged

Clicking Merge or Merge with fixes on a ticket in the web UI is pure bookkeeping today — it only flips the ticket's own state column. It does not call publish_snapshot, does not touch the target repository. Actual delivery only happens by separately running a workflow that declares publish_snapshot and resolving its own approval wait. An operator can mark a ticket "merged" while the target repository is completely untouched.

Phase 2

Provider-native PR publishing Gated · unconditionally refuses to start

A large, thoroughly tested, real subsystem for opening and maintaining a GitHub pull request — and, as of this writing, something you structurally cannot turn on.

The design: publish_snapshot with mode: pull-request creates or updates a source branch and a PR idempotently; a separate, reusable pr-monitor-v3 workflow then owns a genuinely standing Concourse pipeline per binding — a read-only forge-pr resource polling every 5 minutes by default — that reacts to submitted review batches by revising the branch, re-validating, and replying, all without Jetbridge ever completing or abandoning the PR itself; the forge and its branch policies remain the final merge authority.

# agent/workflow/seeds/pr-monitor-v3/workflow.yaml (excerpt, real syntax) - await_snapshot: reapproval pr_approval: binding_id: 1 observation: pull-request candidate: candidate impact: publish-impact destination: github.example/acme/widget approval_policy_version: engineering/v3 prompt: Approve this exact revised pull-request branch? type: human-answer/v1 on_timeout: fail timeout: 72h - publish_snapshot: publish-revision publisher: git-publisher/v1 input: candidate input_type: repository-change/v1 destination: github.example/acme/widget mode: pull-request parameters: {source_branch: refs/heads/agent/pr-revision, target_branch: refs/heads/main} approval: reapproval pr_approval: {binding_id: 1, observation: pull-request, impact: publish-impact}
This cannot be enabled today, on purpose

Setting --agent-publisher-pull-requests-enabled unconditionally fails ATC's own config validation and refuses to start, with an explicit message naming exactly what's still missing: authoritative impact evaluation, action-bound initial publication composition, approved-baseline materialization and advancement, and full lifecycle wiring. Each of those has real code behind the interface (a fully-implemented pure decision function, a carefully-hardened credential-to-mutator resolver, a durable binding store) but zero production implementation or caller wiring — confirmed by grepping for callers outside test files and finding none at every layer. The standing PR-monitor pipeline mechanism described above is fully built and unit-tested, but the composition call that would supply it a policy resolver passes none, so it is currently inert in the running binary even independent of the startup refusal. There is no fly command and no web UI page for any of this — an operator "pausing" or "resuming" a binding, as described in the feature's own operations runbook, is a database-layer capability with no exposed way to invoke it today.

Two things are worth being precise about since they're easy to conflate: first, the feature's own docs describe publish-pr-v3 as a workflow boundary parallel to pr-monitor-v3 — it isn't one. No such workflow YAML exists anywhere in the repo; the initial-publish side is implemented as a plain Go coordinator invoked directly from ATC, with no author-facing YAML at all. Second, direct-Git publishing (above) is completely unaffected by any of this — it's a separate, non-gated adapter mode through the same router, and it's the only "agent publisher" path that actually works in a real deployment right now.

What's genuinely new and useful even while gated: publish-impact/v1 is a real sealed-record type computing changed files, validation deltas, and deterministic pass/fail rule results for a candidate versus a baseline — with a hard invariant that an agent's own impact assessment can only escalate a reapproval requirement, never waive one a deterministic rule already set. GitHub is the only supported forge; the provider-neutral adapter seam is retained but no second adapter ships.

Phase 2

Experiments

A/B testing for workflow variants, built as a thin admission gate on top of the same durable run engine — not a parallel implementation.

An experiment pins two or more candidate variants (one designated control), a set of snapshot fixtures, and a pinned evaluator workflow, then materializes the full fixture × variant × repetition matrix as individually admitted cells. Both the candidate and evaluator executions for a cell are ordinary durable workflow runs — same admission, same output validation, same cancellation semantics as any other invocation — routed through an extra gate that checks the experiment and cell are still genuinely open before admitting a new child.

A variant doesn't have to be a whole workflow — this is the actual answer to "how do I iterate on one step of a chain without re-running everything upstream of it." Every node's output is already its own addressable snapshot the moment it seals, whether or not it's one of the workflow's declared top-level outputs (see Durable workflow runs). So to compare two versions of, say, a downstream validate node against the exact same upstream output: pin that upstream snapshot as the experiment's fixture, then add each candidate as an extracted single function rather than a full workflow, using workflow@version#function_id:

fly -t TARGET agent experiments add-variant EXPERIMENT v1=my-workflow@3#validate --control fly -t TARGET agent experiments add-variant EXPERIMENT v2=my-workflow@4#validate

Each extracted target is rendered and admitted as its own standalone durable run against the pinned fixture — same guarantees as any other cell, just scoped to one function instead of the whole DAG. This is the same node-extraction mechanism described in Workflow definitions, not something specific to experiments — experiments are simply its main consumer today.

That gate matters because of a specific race: without it, a scheduler admitting a new cell and a concurrent cancellation of the parent experiment could interleave such that a child gets created for an experiment that's simultaneously being torn down, leaving an orphaned run that keeps consuming budget after the experiment is nominally stopped. A database lock held across the check-and-admit step closes that window.

Budget is reserved once per cell, up front, covering both its candidate and evaluator together — so an experiment child deliberately skips the ordinary per-run budget check that ticket and manual runs go through, to avoid reserving the same dollar amount twice.

Scorecards aren't computed lazily on read. The moment an experiment reaches a terminal state, its scorecard is built once from every settled cell's telemetry and frozen immutably in the same transaction — a later metric arriving out of order cannot rewrite a result you've already looked at.

fly -t TARGET agent experiments create definition.json fly -t TARGET agent experiments start EXPERIMENT --revision=REVISION fly -t TARGET agent experiments scorecard EXPERIMENT

Enabling the experiment runner requires snapshot storage to be enabled — fixtures and measurements are snapshot-backed, so there's no meaningful "experiments without snapshots" state. Disabled by default; start/validate fail closed with service-unavailable rather than quietly queuing work nothing will claim. Server-enforced bounds keep any one experiment reasonable: 16 variants, 256 fixtures, 1,000 repetitions, 2,000 cells, 32 measurements.

Operating & deploying

The Helm chart is the deployment surface for both phases. The four blockers a prior audit found here are all fixed — the chart now actively tests itself against the binary to keep it that way.

Four previously-documented blockers are now fixed
  • The PVC-flag crash-loop is gone. The old artifact/cache-store PVC flags and their chart values don't exist anywhere in the tree anymore — not retired-but-lingering, actually deleted, template and all. The chart now carries its own regression test that instantiates the real ATC flag parser and asserts every flag the chart renders for the web Deployment actually exists on the binary, plus a hardcoded list of retired strings it asserts never reappear anywhere in values.yaml or the rendered templates. This is a real, structural guard against this exact class of drift recurring, not just a one-time fix.
  • The multi-replica signing-key gotcha is fixed via a lookup-or-generate pattern: with the default secrets.create: true, the chart uses Helm's lookup to reuse an existing signing key across upgrades (minted once, kept via helm.sh/resource-policy: keep) rather than generating a fresh, unshared one on every pod start. web.replicas > 1 now works out of the box. The one residual, clearly-documented caveat: lookup is a no-op during a cluster-less helm template render (a template-then-apply GitOps flow), so that flow must set secrets.signingKeySecret explicitly rather than relying on secrets.create.
  • The artifact-daemon's Prometheus metrics are now scraped by a dedicated ServiceMonitor, on by default whenever the top-level serviceMonitor.enabled switch is on. The interesting part is a genuinely new fail-closed guard: if an operator enables both a NetworkPolicy and this ServiceMonitor without also setting serviceMonitor.scrapeFrom, the Helm render itself fails outright — rather than silently producing a Prometheus target whose scrapes get dropped by the policy, which is exactly what used to happen silently.
  • The hardened release chain's stale-frontend-bundle bug is fixed. A dedicated build-frontend task now runs before the image build and hard-fails the whole job if it produces no output — closing the exact //go:embed web/public trap that once shipped a stale UI. The one residual soft spot: the hardened pipeline's frontend build step and the simpler chain's own Dockerfile frontend stage are two separate, manually-synchronized pieces of config with a comment explaining why they aren't unified — a future change to one could still drift from the other unless someone remembers both.

What's new in the chart since the last audit

Three substantial new configuration surfaces landed alongside the features they support — each is covered in depth in its own section, linked below, but here's what an operator deploying today needs to know exists:

  • Hangar (artifactDaemon.hangar.*) — durable GCS-backed snapshot/checkpoint storage, chart-enforced pairing with agentSnapshots.enabled. See the runtime section for the real config and a live deploy-blocker in the current daemon wiring.
  • Agent execution broker (agentBroker.*) — extensively validated at render time (exact-digest images, absolute-HTTPS endpoint, unique credential slots), but its own docs say the security sandbox isn't accepted for production yet regardless of how complete the chart plumbing is. See Agent execution broker.
  • Agent publisher / PR publishing (agentPublisher.*) — the old agentPublisherGateway key is now a hard chart-render tombstone (fails with "has been removed; use agentPublisher" if set), and a PR-only publisher can now be configured independently of direct-Git. See Human approval & publishing and Provider-native PR publishing.

That render-time tombstone pattern — fail loudly on a retired key rather than silently ignoring it — is the chart's general strategy for retiring configuration now, and it's worth recognizing elsewhere in values.yaml if you're upgrading across a few versions at once.

Self-hosting: two release pipelines exist

There are two independent pipelines in deploy/ that can build and deploy this project against itself — confirm with whoever operates a given cluster which one is actually authoritative there:

  • The hardened chain — build, native agent review, unit tests, K8s runtime tests, a release-candidate tag, image build (now including the dedicated frontend-rebuild task above), self-upgrade, a post-upgrade verification pass, live K8s tests, then release. It has concrete, comment-documented guards for most of the historically recurring failure modes: retries around single-node flakiness, the RBAC grant that lets the post-upgrade rollout check actually complete instead of hanging, and an image-existence check before the release job's git tag/push so a failed build can never leave a phantom release tag behind. The earlier tag-rc job also reserves an immutable, source-bound RC tag: overlapping candidates allocate distinct patch versions instead of moving a live-tested candidate's version authority.
  • The simpler chain — build, test, build an image tagged :latest, a short-lived pod that restarts the live deployment, then promote to main. No release-candidate dance.

Building the agent-runner image

Ships both binaries described in Execution, budget & credentials, plus a full Go toolchain and a pinned Claude Code CLI. It intentionally runs as root — jetbridge's shared host-path step volumes are created by the kubelet as root-owned and a pod's fsGroup is ignored for host-path mounts, so this is a considered trust boundary, not an oversight. Building this image is an explicit manual release gate: trigger it only after tag-rc is green for the intended commit, because its version comes from that source-bound RC tag and self-upgrade requires the same repository version to pass both image jobs. An Elm build toolchain was deliberately removed from this image because the build pod's egress to external package hosts was unreliable — any agent ticket that needs to compile the Elm frontend will fail at that step until that changes. A separate, similarly manual pipeline job now exists for the agent-broker image, and another for the forge-pr-resource image the PR-publishing lane depends on — both print the exact pinned digest to paste into the chart.

A worked example, end to end

Everything above explains the mechanism. This walks one real seed workflow — version-upgrade-v3 — through all six stages with real commands, real node names, and real snapshot types, so the abstract shape in How a change gets made has something concrete to hang on.

version-upgrade-v3 takes a repository/v1 and an upgrade-request/v1, and produces an approved repository-change/v1 plus an upgrade-report/v1. Its plan has five nodes: three agents (upgrade, review, validate-and-ask), one durable human wait, and a final small agent (enforce-approval) that only emits its output if the wait resolved as an approval.

1–2. Capture, then bind & admit

Seal the two inputs as immutable snapshots, then bind them to a definition version and create a durable run:

# capture a live pipeline resource version as a typed snapshot
fly -t TARGET agent snapshots capture-resource \ --pipeline=repo --resource=source \ --version=ref:0123456789abcdef... --type=repository/v1 # seal an ad-hoc value with no live source — a hand-authored request
fly -t TARGET agent snapshots create --type=upgrade-request/v1 --from=./upgrade-request # import + promote the definition (once, or skip if already live)
fly -t TARGET agent workflows import agent/workflow/seeds/version-upgrade-v3 --set-live # bind the two snapshot IDs above and admit a durable run
fly -t TARGET agent workflows run version-upgrade \ --input=repository=101 --input=request=102 --follow

3–4. Render & execute, sealing as it goes

The definition renders into a one-shot Concourse pipeline and each node runs as its own pod. upgrade produces a candidate change and a report; review re-examines the candidate against the immutable repository and request, sealing a reviewed-change — its own inputs: list names both the original bound inputs and upgrade's freshly-sealed outputs, the "output becomes the next input" chaining from the overview made concrete:

- agent: review function_id: review inputs: [repository, request, candidate-change, report] # candidate-change + report came from "upgrade" outputs: [reviewed-change]

validate-and-ask runs tests against the reviewed change, seals a validation/v1 record (rev3 today — with a compiled attestation block, see Snapshots), and seals a question/v1 value asking whether the change may go out. Each of these is sealed the moment its node finishes, not when the run finishes; watch it happen live with --follow, or after the fact with:

fly -t TARGET agent workflows runs version-upgrade fly -t TARGET agent workflows show-run version-upgrade RUN-ID

Execution then reaches the definition's await_snapshot node — the one piece of syntax here with no stock-Concourse equivalent at all:

- await_snapshot: approval question: approval-question type: human-answer/v1 on_timeout: fail timeout: 72h

This stops the run cold — a durable wait, not a running pod. There's no fly command to resolve it: this happens in the web console's durable-run detail page, in the human-waits card described in The operator surface today. Only an exact "approve" answer, from the human actually resolving it, lets the run continue. Once resolved, enforce-approval runs last and only on an explicit approval does it copy reviewed-change forward into approved-change — if the answer rejects it, this node deliberately emits nothing, so the workflow fails closed rather than silently producing a change nobody approved.

5. Promote

If every node succeeded and the platform's own re-verification checks out, the run's two declared outputs — change and report — flip from intermediate to public. Everything else this run sealed along the way stays sealed and inspectable, but was never a declared output and never becomes "the result."

fly -t TARGET agent workflows show-run version-upgrade RUN-ID --outputs fly -t TARGET agent snapshots show SNAPSHOT-ID

6. Publish — not this workflow

version-upgrade-v3 stops at step 5 on purpose — it produces an approved change, not a delivered one. Actually landing it is a separate concern, handled by a workflow that declares publish_snapshot (see Human approval & publishing for the direct-Git path that works today, and Provider-native PR publishing for the newer, currently-gated pull-request lane), taking this run's change output as its own input and resolving its own, separate approval wait.

Two further worked examples worth reading once you're comfortable with this one, each demonstrating a genuinely new mechanism: the Reusable nodes section walks a single-step node.yaml from import through composition into a parent workflow; the resource-source admission subsection shows the resource_sources: syntax that lets a workflow auto-trigger the way a Concourse job does.
