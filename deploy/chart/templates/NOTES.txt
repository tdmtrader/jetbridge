  `lookup` returns nothing when the chart is rendered WITHOUT a cluster
  connection. Argo CD does exactly that by default, as does
  `helm template | kubectl apply`. Those pipelines mint brand-new material on
  every render, and with automated sync they apply it.

  Nothing breaks at the moment of the sync -- the web node and the artifact
  daemons all read this material once at process start and never reload it.
  The damage lands at the next restart of either side: that pod comes up on the
  new CA or the new resolve key and is permanently mismatched against every pod
  still holding the old one. ATC-to-daemon mTLS fails in both directions, and
  resolve capabilities are rejected, so fetch-inputs init containers fail
  closed -- until BOTH the web Deployment and the whole DaemonSet have rolled.

  If this release is managed by Argo CD or any other render-only pipeline, set
  the values listed above to Secrets you manage outside the chart. See the
  GitOps caveat in the chart README.

  Do not commit rendered manifests either way: a cluster-less render embeds
  these private keys in the manifest as ordinary base64.
{{- end }}

{{- if and .Values.alertingRules.enabled (not .Values.web.metrics.enabled) }}

WARNING: alertingRules.enabled is true but web.metrics.enabled is false.

  The concourse_k8s_*, concourse_db_* and concourse_workers_* alerts in
  {{ include "concourse.fullname" . }} read series that exist only on the web
  node's Prometheus listener, which the ATC starts only when it is given
  --prometheus-bind-ip and --prometheus-bind-port. With web.metrics.enabled
  false those flags are not rendered, no exporter publishes the series, and
  those alerts evaluate over an empty vector forever. Prometheus reports no
  error for that, so they read as healthy while the conditions they describe
  go unnoticed.

  Set web.metrics.enabled=true (and serviceMonitor.enabled=true to scrape it),
  or disable alertingRules.
{{- end }}
