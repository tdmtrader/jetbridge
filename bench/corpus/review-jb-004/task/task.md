# Review request: terminal-ticket pipeline archiving + build-page agent spend chip

Two commits are stacked on `main` and not yet pushed. Please review them together
before they go out.

## The change

`task/change.diff` is the combined diff of both commits against their merge base.
The repository is checked out with the change already applied, so you can read any
file at its post-change state and follow anything the diff touches.

Commit 1 — `feat(web): agent cost chip on the build page`

> Fetch the new `/api/v1/builds/:id/agent-metrics` once per build alongside the
> review fetch; sum run costs into an "agent spend" chip on the ticket-context bar
> (or a slim cost-only bar for non-ticket builds with recorded spend).

Commit 2 — `feat(atc): archive terminal agent-ticket pipelines`

> The `pipeline_run_lifecycler` now archives every attempt's run instance plus the
> base template once the owning ticket reaches a terminal state (`merged`,
> `merged_with_fixes`, `abandoned`, `concluded` — new `tickets.TerminalStates()`
> single source of truth). Reconciler over the existing 10s pass rather than a
> transition hook: catches every `Transition` writer, survives restarts, can never
> block a transition. Runs still aggregate-running are held back for the Finish
> pass; `to_regclass` probe no-ops on a pre-ticket-core DB.

Both are motivated by the same dashboard complaint: a ticket that is finished still
leaves `agent-ticket-<id>` cards sitting on the dashboard forever, and there was no
way to see what a build actually cost without leaving the build page.

## What I want out of the review

An adversarial pass, not a style pass. Assume the happy path works — it was
exercised by hand and both suites are green. The usual lenses, in the order I care
about them:

1. **Security and authorization.** Trust boundaries, who can influence what,
   whether a privilege one endpoint grants is bounded where it is finally spent.
2. **Correctness under the conditions the happy path does not cover.** A real
   deployment is not a single-threaded walkthrough; consider what it does to this
   code that a manual exercise does not.
3. **Silent wrongness over loud wrongness.** Prefer findings where the operator or
   the user gets a plausible-looking result and never learns it was wrong.
4. **Contracts with the code these commits attach to.** Both additions bolt onto
   existing machinery; check the assumptions they inherit actually hold.
5. **Tests.** Judge the added specs as evidence: how much of these two commits do
   they actually establish?

For each finding: say what breaks, name the file and the function or query it lives
in, give the concrete sequence that produces the bad outcome, and rate it
major/minor. If you conclude something is fine, say so plainly rather than padding
the list — I would rather have two real findings than fifteen.
